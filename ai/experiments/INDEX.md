# 측정 카탈로그

수치의 정본. `CLAUDE.md`나 `README.md`에 수치를 복사하지 말고 여기를 가리킨다 — 두 곳에 적으면
한 곳이 낡는다.

```bash
uv run python experiments.py            # 전체 표
uv run python experiments.py <slug>     # 하나 자세히
uv run python compare.py <slug-a> <slug-b>
uv run python graph_api.py --experiment <slug> --port 8000   # + viewer/
```

## 구조

실험 1개 = 디렉터리 1개.

```
experiments/<slug>/
  manifest.json   언제·무엇으로·왜 + 어느 코드가 만들었나 (guideSha·schemaSha)
  report.json     backend_sim 산출
  notes.md        무엇을 재려 했고 무엇이 나왔나. 판정
  data/           저장소 루트 (wiki/ work/ .llmwiki/)
```

`backend_sim.py --experiment <slug> --purpose "..."` 가 이 구조를 만든다. 이미 `report.json`이
있으면 거부한다 — 한 시간짜리 측정은 되돌릴 수 없다.

`manifest.json`의 `code`가 있는 이유: 이 세션에서 두 번 손해를 봤다. 12건 런 하나가 프롬프트
수정 **전** 코드로 돌았다는 걸 파일 mtime 비교로 뒤늦게 알아냈고, 워크스페이스 하나가 스키마
변경 전이라는 것도 열다가 터져서 알았다. git이 없으니 리포트가 자기 출처를 들고 있어야 한다.

## 지금까지 확정된 것

**이전 spike(`spikes/wiki-convert-loop`)의 실패가 뒤집혔다.** 조각 13/26 → 0/20, 카테고리
1개 붕괴 → 5개, 페이지간 관계 0 → 69, create 우세 → update 우세.

**근거가 기계 검증된다.** 각주 616개 전부 위치가 있고 613개가 원문을 그대로 인용하며, `lint`가
원본과 문자열 대조한다 (FR-WIKI-001 · NFR-AI-002).

**재처리가 안전하다.** 같은 문서를 다시 올려도 중복이 생기지 않는다 (FR-DOC-012).

**위키 크기는 비용이 아니다.** 시간은 문서 크기가 지배한다:

```
시간 = 1.9분(고정비) + 5.0분 × (크기/1만자)     R² = 0.853
```

고정비는 `guide` 읽기 + 검색 + `lint` 2회. 위키 크기 항이 없다 — 주입이 아니라 검색이라서.

## 미해결

**시간 상한.** ("문서당 2만 토큰 상한"은 요구사항에 없는 오기였다 — 실제 상한은 파일당 20MB.)
회귀식이면 고정 10분에서 실질 한계가 **약 1만6천자**이고 12건 중 3건이 이미 초과했다(전부 정상
처리). 크기 비례 상한(예상×1.5, 최대 30분)으로 백엔드와 합의했고 `runtime/limits.py`가 구현이다.
3만6천자 초과는 파싱 후 변환 직전에 실패 처리. 한국어 실문서는 같은 토큰에 바이트가 3배라
한계가 더 빨리 온다 — 미측정.

**아직 안 돌린 것**: sonnet-4-6 12건 (guide가 어디까지 떠받치는지), deepagents 스모크
(프로덕션 런타임이고 우리 서버로는 검증 안 됨).

### 한국어 검색 — 색인·질의 방식 (질의 40개 전체, dev/test 분리 이전)

`corpus-ko/evaluate_sqlite.py --split all` 로 재현한다.

| 색인 · 질의 | R@5 | 정확어 R@5 | 자연어 R@5 | 0건 |
| --- | --- | --- | --- | --- |
| `unicode61` AND — **현행 구현** | 0.33 | 0.65 | 0.00 | 26/40 |
| `unicode61` OR | 0.38 | 0.65 | 0.10 | 19/40 |
| `trigram` AND | 0.30 | 0.60 | 0.00 | 28/40 |
| `trigram` OR | 0.35 | 0.60 | 0.10 | 26/40 |
| **2글자 분해 OR — 채택** | **0.60** | **0.95** | **0.25** | **7/40** |
| 2글자 분해, 어절 phrase 를 OR | 0.57 | 0.95 | 0.20 | 9/40 |
| 2글자 분해 AND | 0.47 | 0.95 | 0.00 | 20/40 |
| 2글자 분해, 어절 phrase 를 AND | 0.47 | 0.95 | 0.00 | 20/40 |

어절 단위 phrase 묶음을 쓰려던 설계를 측정이 뒤집었다. `P@5` 가 0.12 로 같고 재현율만
0.60 → 0.57 로 떨어진다. bigram 이 이미 연속 부분문자열이라 순서가 뒤집힌 오탐이 생기지
않는다 — 질의 `"차연"` 의 bigram 은 `[차연]` 이고 본문 `"연차를"` 의 색인은 `[연차, 차를]`
이라 애초에 맞지 않는다.

배포되는 경로(`SpringVaultFS` 하이드레이션 + `search_chunks`)로 잰 값이다.
회귀 테스트가 이것을 지킨다 (`tests/mcp/test_korean_search.py`).

| 분할 | R@5 | 정확어 R@5 | 자연어 R@5 | 0건 |
| --- | --- | --- | --- | --- |
| `dev` | 0.60 | 1.00 | 0.20 | 3/20 |
| `test` | 0.55 | 0.90 | 0.20 | 4/20 |

조사·어미가 붙어 공백 분리 색인이 실패한다 ("연차" 로 "연차를" 을 못 찾는다). 3글자는
한국어 핵심어(연차·이월·승인·부여)를 놓쳐 현행보다 **나쁘다.**

현행이 AND 인 이유는 `vaultfs/local.py` 의 `search_chunks` 가 에이전트 질의 문자열을
`MATCH ?` 에 그대로 넘기고 FTS5 가 맨 term 을 AND 로 읽기 때문이다.

> **정정 (2026-07-30).** 앞 판본의 표는 세 줄이 서로 다른 조건이었다 — `unicode61 0.38` 은
> 40개 세트의 **OR** 변형이고, `trigram 0.50 / 24건` 은 폐기한 **48개** 세트 값이며,
> 2글자만 40개 세트 AND 계열이었다. 색인 방식의 차이로 보고한 것에 질의 방식과 질의셋의
> 차이가 섞여 있었다. 위 표는 한 조건에서 다시 측정한 것이다.
>
> 결론은 그대로다 — 2글자 OR 가 최선이고, 차이는 보고했던 것보다 **크다** (현행 0.33 대비
> 0.60). `trigram` 은 보고했던 0.50 이 아니라 0.30~0.35 다.
>
> 참고로 폐기한 48개 세트에서는 현행 AND 0.62 · 2글자 OR 0.90 이었다. 같은 순서지만
> 절대값이 훨씬 높다 — **두 세트의 수치를 나란히 두면 안 된다.**

### MySQL 8.4.11 `ngram` — 질의 방식 (같은 셋)

| 질의 방식 | 정확어 R@5 | 자연어 R@5 | 0건 |
| --- | --- | --- | --- |
| `natural` | 0.90 | 0.20 | 7 |
| `boolean` phrase | 0.95 | 0.15 | 10 |
| `boolean +req` (모든 어절 AND) | 0.95 | **0.00** | 20 |

`ngram_token_size = 2` 는 서버 변수라 DDL 로 못 정한다 — `my.cnf` 에 넣어야 한다.
`+req` 는 쓰지 않는다. 자연어 질의가 전멸한다.

**연결 charset 주의.** 클라이언트가 `utf8mb4` 가 아니면 한국어가 이중 인코딩되어 저장되고
(`C3AC E28094` mojibake) 그 상태에서 검색이 **조용히** 실패한다. 첫 MySQL 측정 결과 전체를
이것 때문에 폐기했다.

**FULLTEXT 진단.** 삽입 직후 색인이 메모리 캐시에 있어 `information_schema.innodb_ft_index_table`
에 보이지 않는다. `innodb_optimize_fulltext_only=ON` + `OPTIMIZE TABLE` 로 flush 해야 보인다.

### 이 수치의 한계

코퍼스·질의·정답 라벨을 한 사람이 작성했다. 블라인드 재라벨과 hard negative 보강이 남았다
(`corpus-ko/README.md` 「아직 안 된 것」). 그때까지 절대 수치를 목표로 쓰지 않는다.

**질의 방식과 질의셋을 항상 함께 적는다.** 위 정정이 그것을 안 적어서 생겼다.

SQLite 하네스는 `corpus-ko/evaluate_sqlite.py` 로 옮겼다. MySQL 하네스와 임베딩 하네스는
아직 저장소에 없다 — MySQL 은 컨테이너가 필요하고 임베딩은 GMS 키가 소진됐다.

## 측정을 막고 있는 것 (2026-07-30)

`stream-json` 전환이 이것을 드러냈다. 첫 스모크 실행에서 에이전트가 MCP 툴을 **하나도**
부르지 못하고 `Bash`·`Edit` 로 19턴을 헤매다 제한 시간에 걸렸다. 총계만 보던 앞 판본에서는
「툴 호출 0」까지만 보였고 그 이유를 알 수 없었다.

원인이 둘이었고 **하나는 고쳤다.**

### 고쳤다 — `uv run --project` 가 MCP 스폰에 너무 느리다

```
system/init  mcp_servers: [{"name": "wiki", "status": "pending"}]
             mcp tools: []
result       "No MCP tools currently available (wiki server still connecting)."
```

매 스폰마다 프로젝트를 재해석해서 CLI 클라이언트가 핸드셰이크를 끝내기 전에 포기한다.
서버 자체는 정상이다 — 같은 명령을 직접 띄우면 즉시 기동한다. `MCP_TIMEOUT=60000` 은
효과 없었다.

`sys.executable -m wiki_mcp.local_server` 로 바꿨다 (`claude_code.py` 트랩 5,
`deep_agents.py` 도 같이). 해석 단계가 없고 `uv` 가 PATH 에 있을 필요도 없다. `env` 를
덮지 않는다 — 이 파일을 돌리는 인터프리터가 이미 의존성을 갖고 있고, 그것이 바로 `env`
override 가 파괴하는 성질이다 (`telemetry.py`).

확인: 툴 10개가 붙고 실제 호출이 서버측 집계까지 도달한다.

```
스트림측 tool_use   ['ToolSearch', 'mcp__wiki__guide', 'mcp__wiki__list_scopes']
서버측 집계         ['guide', 'list_scopes']
```

### 남았다 — 스폰된 CLI 에서 MCP 툴이 지연 로딩된다

위 확인은 프롬프트에 `mcp__wiki__guide` 라고 **정식 이름을 적었을 때**다. 지시문처럼
`` `guide` `` 로만 쓰면 에이전트가 찾지 못한다. `ToolSearch` 로 검색해야 하는 상태이고,
haiku 는 그 단계에서 헤매다 위키를 건드리지 않고 답한다.

```
프롬프트 "`guide` 를 부른 뒤 `search` 로 …"
스트림측 툴집계   {"Bash": 4, "ToolSearch": 2, "Monitor": 2, "Read": 1}
서버측 툴집계     {}
수집된 검색어      []
```

`--setting-sources ""` 를 추가해 운영자 설정 상속을 줄였다 (트랩 6). `CronCreate`·
`DesignSync`·`EnterWorktree`·`Skill` 같은 개발자 세션 툴은 사라졌지만 `ToolSearch`·
`Monitor` 는 남는다 — 지연 로딩이 사용자 설정이 아니라 CLI 자체 구성에서 온다.

`--bare` 는 쓸 수 없다. 로그인 세션을 안 읽어 구독 과금이 깨진다 (트랩 1).

**Task 6(`--effort` 대조)과 Task 7(`deepagents`)이 여기서 막힌다.** 2026-07-27 측정은
정상적으로 툴을 불렀으므로 그 사이 CLI 판본이 바뀌었다.

시도해 볼 것이 남아 있다 — 지시문에 툴 정식 이름(`mcp__wiki__guide`)을 쓰면 통한다.
다만 그것은 **프롬프트 변경이라 과거 측정과의 비교를 깨뜨린다.** 별도 판단이 필요하고
이 계획의 범위가 아니다.

**측정 결과가 측정한 사람의 환경에 의존한다.** `manifest.json` 에 CLI 판본과 설정 출처를
함께 적어야 한다.
