## 도구 전송 대조 — MCP 하위 프로세스 vs in-process (2026-08-01)

**왜 쟀나.** S15P11B106-152 로 배송 경로가 stdio MCP 하위 프로세스에서 in-process 로 바뀌었다.
그 전까지의 측정은 전부 MCP 경로로 잰 것이라 **재는 것과 배송되는 것이 갈렸다.**

```bash
uv run python experiments/backend_sim.py \
    experiments/corpus/01-training.md experiments/corpus/02-side-gigs.md \
    --experiment <slug> --runtime deepagents --model openai:gpt-5.4 \
    --transport {mcp|in-process}
```

같은 문서 2건 · 같은 모델 · 전송만 다르게 **각 3회**.

| | 시간(중앙) | 시간 범위 | 입력토큰(중앙) | 입력토큰 범위 | 턴(중앙) | 반영 성공 |
| --- | --- | --- | --- | --- | --- | --- |
| MCP 하위 프로세스 | 93.0s | 89.8~97.5 | 150k | 124k~153k | 18 | 6건 중 5 |
| **in-process (배송)** | **55.9s** | 52.6~67.1 | 214k | 127k~244k | 21 | 6건 중 6 |

**시간만 갈린다.** 두 범위가 겹치지 않는다 — **40% 빠르다.**

**기제**: MCP 경로는 **툴 호출마다 하위 프로세스를 새로 띄운다.** 문서 1건을 따로 돌려 세었다
(`2026-08-01-gpt54-spawncount`) — 툴 호출 12회에 「MCP 서버 시작」 13회
(`ListToolsRequest` 13 · `CallToolRequest` 12, 첫 1회는 툴 목록 조회).

**토큰·턴은 못 가른다.** 범위가 크게 겹치고(in-process 최저 127k < MCP 최고 153k) 턴 수를
따라 움직인다(16턴 127k · 24턴 244k). n=3 으로는 전송 효과와 실행 편차를 나눌 수 없다.
「대조 규칙」 절의 10~30% 규칙이 그대로 적용된다.

**성공률 차이도 근거가 아니다.** MCP 의 실패 1건은 lint `citation-quote-not-found`
(모델이 원문에 없는 문장을 인용) — 전송과 무관한 생성 품질 문제다.

**이번에 드러난 하네스 결함**: `backend_sim` 의 MCP 경로가 `runtime.run` 을 직접 불렀는데
`DeepAgentsRuntime.run` 은 안에서 `asyncio.run` 을 쓴다. 이미 도는 루프 안이라
`asyncio.run() cannot be called from a running event loop` 로 죽었다 — **이 경로가 deepagents
로 한 번도 안 돌아 본 것이다** (claude-code 는 subprocess 라 문제가 없었다).
`asyncio.to_thread` 로 띄워 고쳤다.

## 위키 1단계 선택의 천장 (2026-08-01)

**왜 쟀나.** 위키 변환을 호출 1회로 합치는(에이전트가 조회 API 로 직접 읽는) 리팩토링의 근거는
「1단계가 놓치면 에이전트가 회복할 수 없다」다. 그 실패가 실재하는지 확인하지 않으면 근거가 없다.

**먼저 기존 실측을 다시 봤다.** `2026-07-27-opus46-12docs` 와 `2026-07-29-sonnet46-12docs` 에서
**중복 페이지 0건**(새로 만든 페이지와 그 시점 기존 페이지의 단어 Jaccard 최댓값 0.09~0.21),
**「자료가 없다」류 발언 0건**(24문서). 즉 **그 조건에서는 선택이 실패하지 않았다** — 문서 12건이
주제가 서로 다르고 위키가 20장이라 쉬운 조건이었다.

**어려운 조건을 만들어 다시 쟀다** (`experiments/selection_ceiling.py`).
**그 스크립트는 S15P11B106-175 에서 삭제됐다** — 1단계 선택 경로 자체가 사라져 다시 돌릴
대상이 없다. 수치는 `experiments/selection_ceiling_result.json` 에 남아 있고 아래 표가
그것이다. 재현하려면 삭제 이전 커밋에서 꺼내야 한다. 위키 100장
(`corpus-ko`)의 목차를 실서비스 모양(`- [제목](pages/{숫자}.md) — 요약`)으로 만들고, 정답을
사람이 정한 문서 5건으로 **선택 단계만** 호출했다.

| 사례 | gpt-4o-mini | gpt-4o |
|---|---|---|
| 1. 문서 제목이 목차 제목과 그대로 겹친다 | 맞힘 | 맞힘 (군더더기 0) |
| 2. **주제는 같고 어휘가 다르다** (「미사용 휴가 이월·반일 근무」 ↔ 「연차 휴가」) | **놓침** | 맞힘 (+1) |
| 3. 두 페이지에 걸친다 | 맞힘 | 맞힘 |
| 4. 목차에 없는 주제다 (아무것도 고르지 않아야 맞다) | **2장 고름** | **2장 고름** |
| 5. 한 페이지를 정확히 가리킨다 | 맞힘 (+1) | 맞힘 **(+4)** |
| 놓친 사례 | **1/5** | 0/5 |

**두 가지를 구분해야 한다.**

* **놓침은 모델 값에 달렸다.** 배포 모델(gpt-4o-mini)은 어휘가 다른 개정 문서에서 정답을
  놓쳤고, 더 센 모델은 놓치지 않았다. 「설계가 원천적으로 불가능」이 아니다
* **군더더기는 두 모델 다 심하고 이건 설계 쪽이다.** 5건 중 4건에서 무관한 페이지를 골랐고
  gpt-4o 는 한 사례에서 5장(정답 1 + 군더더기 4)을 골랐다. **목차 요약만으로는 「관련 없음」을
  확신할 수 없어** 넉넉히 고르는 것이 합리적 행동이 된다. 사례 4 가 그 증거다 — 목차에 없는
  주제인데 둘 다 골랐다. 즉 **선택 단계는 「없음」을 답하지 못한다**

**대가.** 이 코퍼스는 페이지당 약 8KB다. 군더더기 2장이면 16KB 가 요청에 실리고, 그것이
**에이전트 턴마다 다시 실린다**(실측 턴 18~59). 반대로 에이전트가 직접 읽으면 필요한 시점에
들어오고, 안 필요한 것은 아예 안 들어온다.

**이 수치의 한계.** 사례 5건 · 합성 코퍼스 1개 · 각 1회 실행이다. 재현율의 추정이 아니라
**실패 방식이 실재함을 보인 것**이다. 문서 5건은 정답을 사람이 정했고 코퍼스에 「이월 잔액
처리」(예산)처럼 제목이 헷갈리는 페이지가 있어 어려움이 실제보다 클 수 있다.

**방법에서 두 번 틀렸고 둘 다 결과를 뒤집었다** — 남겨 둔다.

1. `wikiId` 를 파일 이름(`annual-leave`)으로 만들었다. Spring 은 목차를 자기가 다시 렌더링하고
   (`WikiTransformationApplier.writeIndex` → `WikiIndex.render`) 그 형식이 `pages/(\d+).md` 만
   허용한다 — 실서비스 목차는 **항상 숫자**다. 모델이 번호로 답하는 것이 맞는데 그것이 「목차에
   없는 ID」로 버려져, 선택 성능이 아니라 내 형식 오류를 재고 있었다
2. 목차 요약이 전부 `---` 였다 (frontmatter 를 걷지 않고 첫 줄을 집었다). 모델이 **제목만** 보고
   골랐고, 실서비스보다 정보가 적은 조건이었다. 고친 뒤 gpt-4o 의 놓침이 2/5 → 0/5 로 바뀌었다

## ⚠️ 코퍼스가 영어다

모든 위키 변환 측정이 `corpus/` 12건을 쓰고 **그것은 전부 영어다** (PostHog 핸드북, 한글
0자). 실서비스는 한국어 원본 → 한국어 위키다.

따라서 이 문서의 **시간·토큰·크기 수치는 실서비스 조건이 아니다.** 특히 각주 인용은 영어
문장을 영어로 인용한 결과이며, 한국어는 조사·어미 때문에 `lint` 의 문자열 대조가 더 자주
어긋날 수 있다. `corpus/README.md` 에 영향받는 수치를 정리해뒀다.

한국어 코퍼스 측정은 **미실시**다.

## 대조 규칙

CLI 수치는 CLI 수치끼리만 비교한다 (하네스마다 토큰 집계가 다르다).

**같은 조건 1회 비교는 근거가 안 된다.** 2026-07-29 실측 — 같은 문서·같은 모델·같은 guide 가
2배로 흔들렸다:

```
01-training.md (sonnet-4-6, guide b5444b72e5a4)
  sonnet46-2docs  런 : 134.8초 · 툴 15회 · $0.53
  sonnet46-12docs 런 :  72.0초 · 툴  7회 · $0.31
```

에이전트 루프라 `search` 한 번이 read·edit 을 끌고 온다. **시간·비용의 10~30% 차이는
판정 근거로 쓰지 않는다.** 구조적 지표(각주 수, 페이지간 링크 0 여부, 조각 수, lint error)만
1회 측정으로 읽는다. 카테고리 이름도 실행마다 달라진다 — 같은 opus 두 번이 서로 달랐다.

**`guideSha` 가 `사후기록` 인 실험을 기준선으로 쓰지 않는다.** 판본을 증명할 수 없어 모델
차이와 guide 개정 차이가 섞인다. 필요하면 기준선을 다시 측정한다 (CLI, 크레딧 0).

## 지금까지 확정된 것

**이전 spike(`spikes/wiki-convert-loop`)의 실패가 뒤집혔다.** 조각 13/26 → 0/20, 카테고리
1개 붕괴 → 5개, 페이지간 관계 0 → 69, create 우세 → update 우세.

**근거가 기계 검증된다.** 각주 616개 전부 위치가 있고 613개가 원문을 그대로 인용하며, `lint`가
원본과 문자열 대조한다 (FR-WIKI-001 · NFR-AI-002).

**재처리가 안전하다.** 같은 문서를 다시 올려도 중복이 생기지 않는다 (FR-DOC-012).

**위키 크기는 비용이 아니다.** 시간은 문서 크기가 지배한다:

```
시간 = 1.9분(고정비) + 5.0분 × (크기/1만자)     R² = 0.853
```

고정비는 `guide` 읽기 + 검색 + `lint` 2회. 위키 크기 항이 없다 — 주입이 아니라 검색이라서.

| `unicode61` OR | 0.38 | 0.65 | 0.10 | 19/40 |

### Spring 실경로 — 코퍼스 측정 (2026-08-05)

같은 코퍼스·같은 질의·같은 지표를 **MySQL `ngram` + `wiki_search_chunk`** 경로로 쟀다
(`experiments/corpus-ko/evaluate_mysql.py`). 색인은 `WikiSearchIndexer::chunkMarkdown` 의
헤딩 분할을 이식했다 — 위 SQLite 값은 ~512토큰·~128겹침이라 **청킹이 다르다.** 청크 2,338개.

`InternalWikiQueryService::search` 의 질의 방식만 바꿔 대조했다.

| 분할 | 질의 방식 | R@5 | R@20 | 정확어 R@5 | 자연어 R@5 | 0건 |
| --- | --- | --- | --- | --- | --- | --- |
| `dev` | phrase (앞 판본) | 0.50 | 0.50 | 1.00 | **0.00** | **10/20** |
| `dev` | terms (현행) | 0.60 | 0.65 | 1.00 | 0.20 | 5/20 |
| `test` | phrase (앞 판본) | 0.45 | 0.50 | 0.90 | **0.00** | **10/20** |
| `test` | terms (현행) | 0.45 | 0.55 | 0.80 | 0.10 | 5/20 |

**어절 수가 전부를 설명한다** (앞 판본, `dev`):

```
1어절: 0/10 0건      2어절 이상: 10/10 0건
```

앞 판본이 질의를 통째로 큰따옴표로 감싸 **정확 구문**으로 물었다. ngram 색인에 연속 문자열을
요구하는 것이라, 「출장비(여비) 정산 안내」 페이지가 있는데도 `출장비 정산` 이 0건이었다.

**판정은 「0건 절반」 하나다.** `test` 에서 R@5 는 0.45 로 그대로고 정확어는 0.90→0.80 이다.
같은 조건 4회 반복에서 3회가 동일하고 1회가 질의 1건만큼 흔들렸으므로 **±1건은 잡음**이고,
정확어 변화(1건)는 그 안이다. 0건 10→5(5건)만 잡음 밖이다.

그래도 이 수정이 필요한 이유는 **에이전트가 겪는 실패가 순위가 아니라 0건**이라서다.
정답이 1위일 필요는 없고 무엇이든 나와야 추측을 멈춘다. 실측(job 33)에서 에이전트는 `search`
35회 중 대부분을 "없다"로 받고 쓰기를 한 번도 못 한 채 턴 상한에 걸렸다 — 137만 토큰 중
$0.495 를 그렇게 썼다.

`terms` 의 `dev` 값이 위 SQLite 표의 `dev`(0.60 · 1.00 · 0.20)와 **일치한다.** 두 검색 경로가
같은 품질로 맞춰졌다는 뜻이다. 앞 판본에서는 자연어가 0.00 대 0.20 으로 갈려 있었다.
`test` 는 0.45 대 0.55 로 아직 벌어져 있고, 남은 차이는 청킹(헤딩 분할 vs 512토큰 겹침)이
후보다 — 아직 분리해 재지 않았다.

> **주의.** `test` 분할은 판정용으로 한 번만 본다는 규칙(`corpus-ko/README.md`)이 있다.
> 위 `test` 값은 수정 전·후를 한 실행에서 함께 잰 것이고, 이 수치를 보고 구현을 더 손대면
> 그 질의들은 `dev` 로 강등해야 한다.

조사·어미가 붙어 공백 분리 색인이 실패한다 ("연차" 로 "연차를" 을 못 찾는다). 3글자는
한국어 핵심어(연차·이월·승인·부여)를 놓쳐 현행보다 **나쁘다.**

현행이 AND 인 이유는 `vaultfs/local.py` 의 `search_chunks` 가 에이전트 질의 문자열을
`MATCH ?` 에 그대로 넘기고 FTS5 가 맨 term 을 AND 로 읽기 때문이다.

> **정정 (2026-07-30).** 앞 판본의 표는 세 줄이 서로 다른 조건이었다 — `unicode61 0.38` 은
> 40개 세트의 **OR** 변형이고, `trigram 0.50 / 24건` 은 폐기한 **48개** 세트 값이며,
> 2글자만 40개 세트 AND 계열이었다. 색인 방식의 차이로 보고한 것에 질의 방식과 질의셋의
> 차이가 섞여 있었다. 위 표는 한 조건에서 다시 측정한 것이다.
>
> 결론은 그대로다 — 2글자 OR 가 최선이고, 차이는 보고했던 것보다 **크다** (현행 0.33 대비
> 0.60). `trigram` 은 보고했던 0.50 이 아니라 0.30~0.35 다.
>
> 참고로 폐기한 48개 세트에서는 현행 AND 0.62 · 2글자 OR 0.90 이었다. 같은 순서지만
> 절대값이 훨씬 높다 — **두 세트의 수치를 나란히 두면 안 된다.**

### MySQL 8.4.11 `ngram` — 질의 방식 (같은 셋)

| 질의 방식 | 정확어 R@5 | 자연어 R@5 | 0건 |
| --- | --- | --- | --- |
| `natural` | 0.90 | 0.20 | 7 |
| `boolean` phrase | 0.95 | 0.15 | 10 |
| `boolean +req` (모든 어절 AND) | 0.95 | **0.00** | 20 |

`ngram_token_size = 2` 는 서버 변수라 DDL 로 못 정한다 — `my.cnf` 에 넣어야 한다.
`+req` 는 쓰지 않는다. 자연어 질의가 전멸한다.

> **놓친 것 (2026-08-05 에 알아챘다).** 위 표의 `boolean phrase` 행이 **0건 10 · 자연어 0.15**
> 다. 그런데 운영 코드(`InternalWikiQueryService::quotePhrase`)가 **바로 그 방식**이었다.
> 표를 보고 내린 결론은 「`+req` 를 쓰지 않는다」 하나였고, **이미 쓰고 있던 phrase 가 두 번째로
> 나쁘다는 것은 아무도 연결하지 않았다.** 측정이 있었는데 운영과 대조하지 않아 두 달 가까이
> 남아 있었다 — 수치를 재는 것과 그 수치가 지금 코드의 어느 줄에 해당하는지 적는 것은 다른
> 일이다. 상세는 아래 「Spring 실경로」 절.

**연결 charset 주의.** 클라이언트가 `utf8mb4` 가 아니면 한국어가 이중 인코딩되어 저장되고
(`C3AC E28094` mojibake) 그 상태에서 검색이 **조용히** 실패한다. 첫 MySQL 측정 결과 전체를
이것 때문에 폐기했다.

**FULLTEXT 진단.** 삽입 직후 색인이 메모리 캐시에 있어 `information_schema.innodb_ft_index_table`
에 보이지 않는다. `innodb_optimize_fulltext_only=ON` + `OPTIMIZE TABLE` 로 flush 해야 보인다.

### 이 수치의 한계

코퍼스·질의·정답 라벨을 한 사람이 작성했다. 블라인드 재라벨과 hard negative 보강이 남았다
(`corpus-ko/README.md` 「아직 안 된 것」). 그때까지 절대 수치를 목표로 쓰지 않는다.

**질의 방식과 질의셋을 항상 함께 적는다.** 위 정정이 그것을 안 적어서 생겼다.

SQLite 하네스는 `corpus-ko/evaluate_sqlite.py`, **MySQL 하네스는 `corpus-ko/evaluate_mysql.py`**
다 (2026-08-05 에 다시 씀). 임베딩 하네스는 아직 없다.

### 랭킹 함수 — 두 경로가 다르다, 그리고 둘 다 우리 것이 아니다 (2026-08-05)

**어느 경로의 수치인지 먼저 보라.** 위 「색인·질의 방식」 표(R@5 0.60 등)는 **SQLite 경로**를
잰 것인데, 그 경로는 **이번 작업이 방금 쓴 초안**만 담는다. 기존 페이지 찾기와 챗봇 답변 —
실질적으로 중요한 검색 — 은 전부 MySQL 이다 (`FederatedVaultFS.search_chunks` 는 작업층은
SQLite, 라이브는 조회 API 로 나눠 가져온다. 챗봇 `search_wiki` 는 MySQL 만 쓴다).

| 경로 | 담는 것 | 랭킹 | 구현 |
| --- | --- | --- | --- |
| 작업 층 (SQLite FTS5) | 이번 작업의 초안 | **BM25** | SQLite 내장 (`rank` 기본값 = `bm25()`) |
| 라이브 위키 (MySQL InnoDB) | 서비스 중인 전부 | **TF-IDF** | MySQL 내장 |

**랭킹 코드는 우리 것이 한 줄도 없다.** `wiki_mcp` 에서 랭킹 관련은 `local.py` 의
`"rank AS score"`(:343)와 `"ORDER BY rank"`(:356) 두 줄뿐이고, `bm25()` 에 가중치를 넘기는
곳도 없다. 우리가 만든 것은 **토큰화와 질의 조립**이다 — `search_tokens`/`search_query`
(SQLite 쪽)와 `booleanTerms`(MySQL 쪽). MySQL 은 2글자 분해조차 `WITH PARSER ngram` 이 한다.

#### MySQL 은 BM25 가 아니다 — 문서에 BM25 가 나오지만

MySQL 문서는 InnoDB 전문검색이 Sphinx 를 모델로 했고 그 알고리즘이 "BM25 와 TF-IDF 에
기반"한다고 서술한다. 그래서 「MySQL 도 BM25」라고 읽기 쉽다. 같은 문서가 실제 가중치는
**"TF-IDF 가중치 체계의 변형"** 이라고 적는다. 8.4.11 에서 직접 재면 후자다.

같은 실험(같은 단어를 N번 반복한 문서, 안 걸리는 채움 문서 5건):

| 단어 빈도 | MySQL 점수 배율 | SQLite 점수 배율 |
| --- | --- | --- |
| 1 | ×1.00 | ×1.00 |
| 2 | ×2.00 | ×1.12 |
| 4 | ×4.00 | ×1.19 |
| 8 | ×8.00 | ×1.23 |
| 16 | ×16.0 | ×1.25 |
| 32 | **×32.0** | **×1.26** |

**BM25 의 핵심은 포화다** — 같은 단어가 32번 나온 문서가 1번 나온 문서보다 32배 관련 있지
않으므로 `k1` 이 기여를 누른다. SQLite 는 1.26배에서 멈추고, MySQL 은 정확히 32배가 된다.

**길이 정규화도 없다.** 같은 빈도(1회)로 길이만 2자·203자·2,003자로 바꾸면 MySQL 점수가
**셋 다 0.090619** 로 동일하다. BM25 의 `b` 가 하는 일이 없다.

IDF 는 로그 비율이다 — 모든 문서가 그 단어를 가지면 점수가 **0** 이 된다(`log10(N/nf)`,
`N=nf`). 처음 이 실험을 채움 문서 없이 돌려 전부 0 이 나온 것이 그 증거다.

#### 그래서 무엇을 뜻하나

- **길이 정규화가 없는 것이 우리 청킹과 나쁘게 맞물린다.** Spring 은 헤딩 단위로 자르고 크기
  상한이 없어 두 줄짜리 절과 2천 자 절이 섞인다. 밀도가 같아도 긴 절이 빈도만으로 앞선다.
- **다만 지금 병목은 아니다.** 아래 「검색 깊이」 측정대로 R@5→R@500 이 평평하다 — 정답이
  순위가 낮은 게 아니라 아예 안 걸린다. 랭킹 함수를 바꿔도 안 걸린 것을 걸리게 못 한다.
- **MySQL 에서 BM25 로 바꿀 스위치는 없다.** `k1`·`b` 도 노출돼 있지 않다. 바꾸려면 전문검색
  엔진을 갈아야 한다 (상류 llmwiki 의 호스티드 경로가 PGroonga 를 쓴 이유로 보인다).

#### 검색 깊이 — 랭킹 개선의 천장 (`terms` 방식, 2026-08-05)

| 분할 | R@5 | R@20 | R@100 | R@500 |
| --- | --- | --- | --- | --- |
| `dev` | 0.60 | 0.65 | 0.65 | 0.65 |
| `test` | 0.45 | 0.55 | 0.60 | 0.60 |

20위 이후 평평하다. 정답이 500위 안에도 없는 질의가 `dev` 7/20, `test` 8/20 이고 **전부
자연어다** (`쉬는 날 며칠 받나`·`다른 데서 알바해도 되나`·`나갈 때 뭐 해야 하나` …).
위키 용어(`연차유급휴가`·`부업(Side Gig)`·`퇴직 절차`)와 2글자 조각조차 겹치지 않는다.

**따라서 랭킹·리랭커·BM25 도입으로 얻을 수 있는 최대는 `dev` +0.05, `test` +0.15 다.**
남은 0.35~0.40 은 사전 일치 방식으로 닿을 수 없다.

#### MySQL 내장 질의 확장은 못 쓴다 (`dev`, 2026-08-05)

| 방식 | R@5 | 0건 | 정확어 | 자연어 |
| --- | --- | --- | --- | --- |
| `boolean` terms (현행) | **0.60** | 5 | **1.00** | 0.20 |
| `natural language` | 0.45 | 3 | 0.90 | 0.00 |
| `WITH QUERY EXPANSION` | **0.00** | 3 | 0.00 | 0.00 |

`WITH QUERY EXPANSION` 은 1차 검색 상위 문서에서 관련어를 뽑아 재검색한다. **ngram 색인에서는
그 「관련어」가 2글자 조각**이라 무의미한 파편이 질의에 쏟아지고 순위가 무너진다 — 결과는
내놓지만(0건 3) 전부 틀린다(R@5 0.00). InnoDB 에 유의어 사전 기능은 없다.

#### 소비자별로 갈린다 — 위키 에이전트는 이미 1.00, 챗봇이 0.20 이다

챗봇의 `search_wiki`(`wiki_api/answer_tools.py`)는 위키 에이전트와 **같은 엔드포인트**를
부르므로 위 수치가 그대로 적용된다. 질의 성격만 다르다.

| 소비자 | 질의 성격 | 수정 전 R@5 | 수정 후 R@5 |
| --- | --- | --- | --- |
| 위키 편집 에이전트 | 원본문서 용어를 그대로 씀 (정확어) | 1.00 | **1.00** |
| 사원 챗봇 | 일상어 (자연어) | **0.00** | 0.20 (`dev`) / 0.10 (`test`) |

**수정 전 자연어 20개 중 20개가 0건이었다** (`dev` 10/10 · `test` 10/10). 자연어 질의는 전부
두 어절 이상이라 예외 없이 정확 구문으로 굳었다. 즉 챗봇은 본문을 못 보고 목차만으로 답하고
있었을 가능성이 크다. 수정으로 0건이 절반(5/10)이 됐다.

**따라서 검색 품질 개선은 위키 에이전트가 아니라 챗봇의 과제다.** 에이전트 쪽 실패(2026-08-05
job 32·33)는 품질이 아니라 (1) 이 구문 버그로 0건, (2) 목록에 요약이 없어 검색을 남발한 것이
원인이었고 둘 다 고쳤다.

남은 자연어 0건은 랭킹으로 못 고친다(위 「검색 깊이」). 수단은 둘이다 — **질의 확장**(사람이
쓰는 사전은 끝이 없으므로, 챗봇 프롬프트에 이미 실려 있는 **목차의 제목·요약**을 모델이 용어
사전으로 쓰게 하는 쪽이 낫다. `answer_guide.py` 가 이미 "목차는 검색어를 고르는 데 쓴다"고
지시하지만 **실측이 없다** — 오늘까지 챗봇 실행 0회)과 **의미 검색**(ERD·Spring 색인 변경이
필요해 팀 합의 사안. MySQL 8.4 에 ANN 색인이 없어 전수 스캔이다).

상류 llmwiki 에서 베낄 것은 없다 — 임베딩 설정(`TURBOPUFFER_API_KEY`·`EMBEDDING_MODEL`)이
`config.py` 에 선언만 되어 있고 **읽는 코드가 한 줄도 없다**(`.env.example` 에 "optional for
v1"). 상류도 순수 사전 검색이며 질의 변환이 0 이다(`params = [query]` 로 FTS5 에 직행).

## 조회 API 어댑터 검색 응답 (2026-07-30)

`FederatedVaultFS`(Wiki 조회 API 경로)의 상한 두 개를 정하기 위한 측정이다. 재현:

```bash
mkdir -p /tmp/ajt-corpus/wiki/ALL
ln -sfn "$(pwd)/experiments/corpus-ko/pages" /tmp/ajt-corpus/wiki/ALL/pages
uv run python experiments/measure_federated.py --corpus /tmp/ajt-corpus --scope ALL \
    --limit 20 --drafts 12
```

**가짜 게이트웨이(`query_gateway.py`)로 잰 값이라 네트워크 지연이 포함되지 않았다.**
진짜 백엔드가 아니다. `nextCursor` 가 항상 `null` 이라 커서 페이지네이션은 한 바퀴만
돌았고, 라이브 행의 `snippet` 은 게이트웨이가 본문 앞 120자를 자른 값이다 — 실제
백엔드의 스니펫 길이는 다를 수 있다. 코퍼스는 `corpus-ko`(합성 한국어 100장)다.

| 항목 | 값 |
| --- | --- |
| 위키 장수 (라이브) | 100 |
| 작업층 초안 장수 | 12 |
| 질의 수 | 5 |
| 검색 `limit` | 20 (= `tools/helpers.MAX_SEARCH`) |
| 검색 응답 행 수 — 라이브만 (최대 / 평균) | 20 / 10.2 |
| 검색 응답 문자 수 — 라이브만 (최대 / 평균) | 2,400 / 1,224 |
| 검색 응답 행 수 — 작업층 무제한 (최대 / 평균) | 7 / 4.8 |
| 검색 응답 문자 수 — 작업층 무제한 (최대 / 평균) | 25,674 / 14,228 |
| 검색 응답 행 수 — 합친 것 (최대 / 평균) | 20 / 13.6 |
| 검색 응답 문자 수 — 합친 것 (최대 / 평균) | 27,234 / 15,284 |
| 본문 적재 횟수 | 5 |
| 조회 API 호출 수 | 23 (하이드레이션 3 + 검색 15 + 본문 5) |

초안을 40장(12문서 작업의 3배 규모)으로 늘린 대조 (`--drafts 40`):
작업층 무제한 최대 **13행 · 73,116자**, 합친 응답 최대 20행 · 68,423자, 조회 API 호출 22회.

**행당 문자 수가 층마다 다르다.** 작업층 행은 청크 전문(행당 3~5천자)이고 라이브 행은
게이트웨이 스니펫(120자)이다. 그래서 행 수 상한은 작업층에만 의미가 있다. 다만
에이전트가 실제로 보는 문자열은 `search` 툴이 행마다 240자로 잘라 렌더링한 것이다
(`tools/search.py` 의 `_CONTEXT_CHARS = 120`) — 위 문자 수는 툴 층 이전의 원본 크기다.

### ⚠️ 위 표만 보면 안 된다 — 이 코퍼스에는 내부 위키 링크가 0건이다

`corpus-ko/pages/*.md` 에는 페이지끼리 가리키는 마크다운 링크가 하나도 없다. 그래서 위
표에는 **`read` 한 번의 fan-out 이 통째로 빠져 있다.** 아래 「read fan-out」 절이 그것을
따로 잰 것이고, 조회 예산은 그 값으로 정했다. 위 표는 검색 응답 **크기**의 근거일 뿐이다.

### read fan-out — 사슬 링크 코퍼스 (2026-07-30)

```bash
uv run python experiments/measure_federated.py --corpus /tmp/ajt-corpus --scope ALL \
    --link-density 1 --pages 100 --phases de     # 150 도 같은 방법
```

`--link-density 1` 은 각 페이지가 다음 1장을 링크하는 사슬을 만든다(연결 성분 = 전체).
`--phases de` 로 좁히는 이유는 A~C 를 링크 있는 코퍼스에서 돌리면 fan-out 이 곱해져 아주
느리기 때문이다.

| 항목 | 100장 | 150장 |
| --- | --- | --- |
| 하이드레이션 조회 API 호출 | 3 | 3 |
| **`read` 1회의 조회 API 호출** | **100** | **150** |
| 같은 `read` 의 본문 적재 | 100 | 150 |
| 두 번째 `read` (같은 페이지) | 0 (캐시) | 0 (캐시) |
| read 1회까지의 누적 호출 | 104 | 154 |
| 카탈로그 연동 예산 | 305 | 405 |
| 예산 켠 시나리오(read 1 + 검색 5) | ok, 108회 사용 | ok, 158회 사용 |
| **같은 시나리오를 고정 예산 105 로** | **QueryBudgetExceeded (105회에서)** | **QueryBudgetExceeded (105회에서)** |

경로: `_ensure_body`(`federated.py`) → `_sync_page_references`(`spring.py`, 라이브 전체를
다시 훑는다) → `build_edges`(`tools/references.py`) → 링크마다 `fs.get` → 다시
`_ensure_body`. **`read` 한 번이 링크 연결 성분 전체를 당긴다.**

### 고친 뒤 (2026-08-01, S15P11B106-151)

같은 명령·같은 코퍼스. 고침 두 가지 — 포트에 `resolve_address`(존재 확인 전용, 본문을
안 당긴다) 를 내고 `build_edges` 가 그것을 쓴다. 그리고 `_ensure_body` 의 재동기화를
스코프 전체에서 방금 받은 그 한 장으로 좁힌다.

| 항목 | 100장 | 150장 |
| --- | --- | --- |
| **`read` 1회의 조회 API 호출** | **1** (was 100) | **1** (was 150) |
| 같은 `read` 의 본문 적재 | 1 | 1 |
| read 1회까지의 누적 호출 | 4 | 4 |
| 예산 켠 시나리오(read 1 + 검색 5) | ok, 9회 사용 | ok, 9회 사용 |
| 같은 시나리오를 고정 예산 105 로 | ok, 9회 사용 | ok, 9회 사용 |

**장수에 비례하지 않는다** — 100장과 150장의 숫자가 같다. 링크 사슬이 그대로 있는
코퍼스에서 잰 값이다(`--link-density 1`).

`QUERY_CALLS_PER_PAGE = 2` 는 **안 바꿨다.** 이제 실측이 9회라 예산 305 든 105 든 남아
돌지만, 그 상수의 근거였던 관계 조회 API(`relations`) 몫은 fan-out 과 별개로 그대로 있고
줄여서 얻는 것이 없다. 줄이려면 관계 조회가 많은 시나리오를 따로 재야 한다.

| `MAX_WORK_SEARCH_ROWS` (`vaultfs/federated.py`) | 20 | 작업층 무제한 실측 최대 13행(3배 규모)의 1.5배이자 `MAX_SEARCH` 와 같은 값. **단, 아래 「걸릴 수 없다」 참고** |
| `QUERY_CALL_BUDGET_BASE` (`vaultfs/query_client.py`) | 105 | 링크 없는 시나리오 실측 23회. 그리고 `experiments/*/report.json` **8개 실험 문서 34건** 중 조회 API 를 건드리는 툴 호출(read·search·lint)이 가장 많았던 문서가 32회(`2026-07-27-opus46-12docs` 의 한 문서 — D9 로 인용되는 폭주 문서) + 하이드레이션 3 = ~35회. 그 35회의 3배 |
| `QUERY_CALLS_PER_PAGE` (`vaultfs/query_client.py`) | 2 | fan-out 실측이 장당 본문 1.0회(100장→100건, 150장→150건)이고 본문은 `wikiId` 캐시로 장수에 묶인다. 여기에 관계 조회 API(`get_backlinks` → `relations`) 한 바퀴를 장당 1회로 잡아 합쳐 2. **관계 조회는 캐시가 없어 장당이 아니라 호출당 1회다** — 상한이 아니라 "한 바퀴" 의 몫이고, 본문 항이 묶여 남는 여유(100장 108/305, 150장 158/405)가 그것을 받친다 |

**조회 예산은 고정값이 아니다.** `예산 = 105 + 2 × 카탈로그 페이지 수`. 하이드레이션이
페이지 수를 클라이언트에 넘긴다(`note_catalog_size`). 처음에는 `MAX_QUERY_CALLS = 105`
고정이었는데 **그것이 링크 있는 위키에서 정상 `read` 한 번을 죽였다** — 위 표의 마지막
줄이 그 회귀를 재현한 것이다. 소비량이 위키 장수에 비례하므로 고정 예산은 위키가 커지는
것만으로 정상 작업을 실패시킨다. 정상 작업을 죽이는 상한은 상한이 아니라 버그다.

예산의 목적은 시간이 아니다 — 조회 API 호출은 수백 밀리초라 시간 예산에 영향이 없다.
D9(`10-onboarding`: 724초에 툴 77회)처럼 맴도는 것을 끊고 조회 결과가 문맥에 쌓여 출력을
늘리는 것을 막는 장치다. 첫 판본의 `200` 은 근거 없는 안전판이었다.

#### `MAX_WORK_SEARCH_ROWS` 는 MCP 툴 경로에서 걸릴 수 없다

`tools/search.py` 가 `min(limit, MAX_SEARCH)` 로 먼저 자르고 `tools/helpers.MAX_SEARCH`
가 20 이므로 어댑터에 도달하는 `limit` 은 항상 20 이하다 — `min(limit, 20) == limit` 이다.
**측정이 보여준 것은 "자를 필요가 없었다"(13행 ≤ 20)이지 "잘라서 막았다"가 아니다.**
D8(출력 토큰 과다)을 실제로 막는 것은 이 상수가 아니라 `MAX_SEARCH` 와 툴의 240자
렌더링(`_CONTEXT_CHARS`)이다. 이 상수는 **어댑터를 툴 밖에서 직접 부르는 호출자에 대한
2차 방어선**으로만 남아 있다. 그 성질은 단위 테스트가 상한을 낮춰 고정한다
(`tests/mcp/test_federated_vaultfs.py::test_work_search_rows_are_capped`).

### 확인된 결함 — 본문 적재가 작업층 검색 결과를 밀어낸다

`FederatedVaultFS.search_chunks` 의 `min(limit, MAX_WORK_SEARCH_ROWS)` 는 부모의 `LIMIT`
에 걸리는데 **부모 SQL 은 층을 모른다** (`local.py` 의 `search_chunks`, WHERE 에 layer
조건이 없다). 라이브 본문이 색인되면 같은 `LIMIT` 을 라이브 청크가 채워 작업층 행이
사라진다.

**출처가 다른 두 관측이 있다. 둘 다 적는다.**

이 저장소의 하네스 (`measure_federated.py --phases d`, 작업층 초안 5장, `limit=5`,
질의 `연차`):

```
본문 적재 전                             내부 색인의 작업층 행 5행
본문 적재 후 (--link-density 0, 1건)     내부 색인의 작업층 행 3행
본문 적재 후 (--link-density 1, 100건)   내부 색인의 작업층 행 3행
```

별도 합성 코퍼스(리뷰어 관측)에서는 **5행 → 0행**이었다. **이 하네스로는 0행이 재현되지
않는다** — 인용할 때 출처를 갈라 써야 한다.

크기는 FTS 순위에 달렸고 **적재량에 단조 비례하지 않는다** — 본문 1건만 적재해도 2행이
밀리고 100건을 적재해도 3행에서 멈춘다. 기제는 두 관측이 같다: 부모 SQL 이 층을 모르고
`LIMIT` 을 걸어 라이브 청크가 순위대로 그 자리를 채운다.

#### 고친 뒤 (2026-08-01, S15P11B106-154)

포트에 층 인자를 다는 대신 **애초에 안 넣는 쪽**으로 고쳤다. 조회 API 경로의 라이브 검색은
조회 API 가 하므로 내부 색인의 라이브 위키 행은 중복이었다 (`_indexes_live_locally`).
원본문서·목차는 조회 API 가 검색해 주지 않아 그대로 넣는다.

```
본문 적재 전                             내부 색인의 작업층 행 5행
본문 적재 후 (--link-density 0, 1건)     내부 색인의 작업층 행 5행   (was 3)
```

같은 명령의 다른 수치도 줄었다: 조회 API 호출 23 → 22, 본문 적재 5 → 4.

### 후속 티켓 후보 — 지연 적재 fan-out 자체

**예산을 키운 것은 증상을 막은 것이고 근본 원인은 fan-out 이다.**
`_sync_page_references` 가 본문 하나를 당길 때마다 라이브 전체를 다시 훑고(O(n)) 그
과정에서 링크된 본문을 다 당긴다. 그래서 `read` 한 번의 비용이 위키 장수에 비례한다.
예산 상향은 정상 작업이 죽지 않게 한 것뿐이며, 조회량·시간 자체는 그대로다.

### 덤으로 확인된 것 — `_allocate` 의 `limit` 초과 분기

층별 몫 배분(`federated._allocate`)의 `len(work) + len(live) > limit` 분기가 단위
테스트뿐 아니라 **통합 경로에서도 실제로 탄다.** 위 실행에서 `_allocate` 호출 15회 중
5회가 그 분기였다 (`--drafts 40` 에서는 6회). 앞 태스크가 "통합 경로 도달 미검증" 으로
남긴 항목이 메워졌다. 다만 **몫 숫자 자체(work/live 각각 몇 행이 남는가)는 여전히 단위
테스트만 검증한다.**

### 이 수치를 인용할 때의 한계 — 전부 읽는다

1. **가짜 게이트웨이다.** 네트워크 지연이 없고, 라이브 스니펫 길이(120자)도 게이트웨이가
   정한 값이다. 실제 백엔드 조회 API 가 나오면 최소한 스니펫 길이와 목록 페이지네이션은
   다시 재야 한다.
2. **원본 코퍼스에 내부 위키 링크가 0건이다.** 링크 fan-out 은 `--link-density` 로 합성해
   따로 쟀다. 실제 위키의 링크 밀도·연결 성분 분포는 모른다.
3. **`nextCursor` 가 항상 `null`** 이라 목록 조회 API 가 여러 바퀴 도는 경우는 미측정이다.
   그만큼 예산 소비가 늘어난다.
4. **`MAX_WORK_SEARCH_ROWS` 는 툴 경로에서 걸릴 수 없다** (위 절).
5. **`min()` 적용 지점이 층을 모른다** (위 「확인된 결함」).
6. **한 요청이 문서 여럿을 실으면 예산이 좁을 수 있다.** `report.json` 재집계는 문서
   1건당 툴 호출이다. 한 클라이언트가 문서 여럿의 생애를 걸치는 계약이면 재검토가 필요하다.
7. **토큰은 재지 않았다 — 문자 수만 셌다.** 토크나이저를 붙이면 값이 모델 판본에 묶인다.
8. **작업층 초안 12장은 가정이다.** 원본문서 1건이 위키 1~2장을 낳는다는 기존 측정에서
   12문서 작업의 상한으로 잡았다. 문서 1건이 5장을 내는 작업이면 달라진다.
9. **`index.md` 없이 돌았다** — 목차 하이드레이션이 빈 채였다. 검색 응답 크기·호출 수에는
   영향이 없지만 목차를 읽는 흐름은 이 측정에 없다.
10. **에이전트 실제 실행이 아니다.** 질의 5개·상위 3건 읽기는 우리가 짠 시나리오다.
    실제 에이전트 실행 측정은 아래 「측정을 막고 있는 것」 때문에 아직 못 한다.

## 측정을 막고 있는 것 (2026-07-30)

`stream-json` 전환이 이것을 드러냈다. 첫 스모크 실행에서 에이전트가 MCP 툴을 **하나도**
부르지 못하고 `Bash`·`Edit` 로 19턴을 헤매다 제한 시간에 걸렸다. 총계만 보던 앞 판본에서는
「툴 호출 0」까지만 보였고 그 이유를 알 수 없었다.

원인이 둘이었고 **하나는 고쳤다.**

### 고쳤다 — `uv run --project` 가 MCP 스폰에 너무 느리다

```
system/init  mcp_servers: [{"name": "wiki", "status": "pending"}]
             mcp tools: []
result       "No MCP tools currently available (wiki server still connecting)."
```

매 스폰마다 프로젝트를 재해석해서 CLI 클라이언트가 핸드셰이크를 끝내기 전에 포기한다.
서버 자체는 정상이다 — 같은 명령을 직접 띄우면 즉시 기동한다. `MCP_TIMEOUT=60000` 은
효과 없었다.

`sys.executable -m wiki_mcp.local_server` 로 바꿨다 (`claude_code.py` 트랩 5,
`deep_agents.py` 도 같이). 해석 단계가 없고 `uv` 가 PATH 에 있을 필요도 없다. `env` 를
덮지 않는다 — 이 파일을 돌리는 인터프리터가 이미 의존성을 갖고 있고, 그것이 바로 `env`
override 가 파괴하는 성질이다 (`telemetry.py`).

확인: 툴 10개가 붙고 실제 호출이 서버측 집계까지 도달한다.

```
스트림측 tool_use   ['ToolSearch', 'mcp__wiki__guide', 'mcp__wiki__list_scopes']
서버측 집계         ['guide', 'list_scopes']
```

### 남았다 — 스폰된 CLI 에서 MCP 툴이 지연 로딩된다

위 확인은 프롬프트에 `mcp__wiki__guide` 라고 **정식 이름을 적었을 때**다. 지시문처럼
`` `guide` `` 로만 쓰면 에이전트가 찾지 못한다. `ToolSearch` 로 검색해야 하는 상태이고,
haiku 는 그 단계에서 헤매다 위키를 건드리지 않고 답한다.

```
프롬프트 "`guide` 를 부른 뒤 `search` 로 …"
스트림측 툴집계   {"Bash": 4, "ToolSearch": 2, "Monitor": 2, "Read": 1}
서버측 툴집계     {}
수집된 검색어      []
```

`--setting-sources ""` 를 추가해 운영자 설정 상속을 줄였다 (트랩 6). `CronCreate`·
`DesignSync`·`EnterWorktree`·`Skill` 같은 개발자 세션 툴은 사라졌지만 `ToolSearch`·
`Monitor` 는 남는다 — 지연 로딩이 사용자 설정이 아니라 CLI 자체 구성에서 온다.

`--bare` 는 쓸 수 없다. 로그인 세션을 안 읽어 구독 과금이 깨진다 (트랩 1).

**Task 6(`--effort` 대조)과 Task 7(`deepagents`)이 여기서 막힌다.** 2026-07-27 측정은
정상적으로 툴을 불렀으므로 그 사이 CLI 판본이 바뀌었다.

시도해 볼 것이 남아 있다 — 지시문에 툴 정식 이름(`mcp__wiki__guide`)을 쓰면 통한다.
다만 그것은 **프롬프트 변경이라 과거 측정과의 비교를 깨뜨린다.** 별도 판단이 필요하고
이 계획의 범위가 아니다.

**측정 결과가 측정한 사람의 환경에 의존한다.** `manifest.json` 에 CLI 판본과 설정 출처를
함께 적어야 한다.

## `orphan-page` 증가폭 — 목차 하이드레이션 제거의 영향 (2026-08-05)

목차(`index.md`)가 더 이상 에이전트 vault 로 하이드레이션되지 않으므로(Spring 이 DB 로
그린다), `orphan-page` 판정 근거였던 「목차에서 닿을 수 없다」가 항상 거짓이 됐고 판정
근거를 본문 링크(`get_backlinks`)만으로 바꿨다. **목차 링크로만 닿던 페이지가 새로
경고에 걸린다** — 그 증가폭을 실측했다.

`tests/conftest.py`의 `vault` 픽스처·`tests/mcp/test_lint.py`의 `_page(..., link_from_index=)`
헬퍼를 그대로 재사용해 페이지 2장(서로 링크 없음, 원본문서 인용은 있음)을 만들고
`LintHandler.run("*")` 의 `orphan-page` 건수를 셌다. (MCP 하네스가 아니라 in-process
호출이다 — 이 작업의 격리 워크트리에 등록된 `wiki-harness` MCP 서버가 다른 브랜치의
`ai/`를 가리켜 이 변경을 잴 수 없었다.)

| 조건 | orphan-page 건수 (2장 중) |
| --- | --- |
| 목차가 두 페이지를 링크 (변경 전 상황을 재현) | 0 |
