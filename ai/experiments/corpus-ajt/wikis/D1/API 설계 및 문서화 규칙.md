사내 서비스가 제공하는 HTTP API 의 설계와 문서화 규칙을 안내한다. 새 엔드포인트는 이 규칙을 따르고, 기존 엔드포인트는 **변경할 때 함께 맞춘다**[^1].

## 경로와 버전

모든 공개 API 는 `/api/v1` 로 시작하고, 서버 사이에서만 쓰는 내부 호출은 `/internal/v1` 로 구분한다[^2].

자원 이름은 **복수형 명사**로 적고 **동사를 경로에 넣지 않는다** — 「문서를 삭제한다」는 `DELETE /api/v1/documents/{id}` 로 표현한다[^3].

경로 변수는 **소문자와 하이픈**, 질의 문자열 이름은 **캐멀케이스**다[^4].

## 상태 코드

| 상황 | 코드 |
|------|------|
| 조회·수정 성공 | 200 |
| 생성 성공 | 201 |
| 본문 없는 성공 | 204 |
| 요청이 잘못됨 | 400 |
| 인증 없음·만료 | 401 |
| 권한 없음 | 403 |
| 자원 없음 | 404 |
| 서버 잘못 | 500 |

성공 코드는 위와 같고[^5], 실패 코드도 위와 같다[^6]. **처리하지 못한 예외를 200 으로 감싸 오류 필드에 담지 않는다**[^7].

## 오류 응답

오류 본문은 두 필드로 한다[^8].

- `code` — 대문자와 밑줄로 된 오류 이름
- `message` — 사용자에게 그대로 보여도 되는 한국어 문장

`code` 는 **이름만 읽고 무슨 일이 있었는지 알 수 있게** 짓는다. `ERROR_1` 처럼 번호를 쓰지 않는다[^9]. **같은 상황에 서로 다른 `code` 를 두지 않으며**, 새 이름을 추가할 때에는 기존 목록을 먼저 확인한다[^10].

## 페이지네이션

목록 응답은 `page` 와 `size` 를 질의 문자열로 받는다. `size` 기본값은 **20**, 최대값은 **100** 이다[^11].

응답에는 항목 배열과 함께 **전체 개수**를 담고, 결과가 잘렸으면 **잘렸다는 사실을 응답에 표시**한다[^12].

## 날짜와 시각

시각은 **ISO 8601** 문자열로 주고받는다. **저장과 전송은 UTC**, 표시 시점에 사용자 시간대로 바꾼다[^13]. 날짜만 필요한 값에는 시각을 붙이지 않는다[^14].

## 호환성

```mermaid
graph LR
    A["필드 제거 필요"] --> B["새 필드 추가"]
    B --> C["두 판 함께 제공"]
    C --> D["예고 기간 경과"] --> E["기존 필드 제거"]
```

**이미 배포된 필드의 이름과 뜻을 바꾸지 않는다**[^15].

**응답에 필드를 추가하는 것은 호환을 깨지 않는 변경**이고, **요청에 필수 필드를 추가하는 것은 호환을 깨는 변경**이다[^16].

## 문서화

모든 엔드포인트는 API 문서에 등록한다. **문서에 없는 엔드포인트는 외부에서 쓰지 않는 것으로 본다**[^17].

요청·응답 예시는 **실제로 동작하는 값**으로 적는다. 예시와 구현이 어긋나면 **구현이 아니라 문서를 정본으로 보고 논의**한다[^18].

엔드포인트를 바꾼 변경에는 문서 수정을 같은 변경에 포함한다 — **문서 갱신을 나중으로 미루지 않는다**[^19]. 변경을 리뷰하는 방법은 [코딩 컨벤션 및 코드 리뷰](pages/1c05c98df2eb.md), 배포 절차는 [배포 및 CI/CD 파이프라인](pages/94439bb14718.md)을 참고한다.
