사내 서비스가 제공하는 HTTP API 의 설계와 문서화 규칙을 정한다. 새로 만드는 엔드포인트는 이 규칙을 따르며, 기존 엔드포인트는 변경할 때 함께 맞춘다.

## 1. 경로와 버전

모든 API 경로는 `/api/v1` 로 시작한다. 서버 사이에서만 쓰는 내부 호출은 `/internal/v1` 로 구분한다.

자원 이름은 복수형 명사로 적는다. 동사를 경로에 넣지 아니한다. 「문서를 삭제한다」는 `DELETE /api/v1/documents/{id}` 로 표현한다.

경로 변수는 소문자와 하이픈으로 적는다. 질의 문자열의 이름은 캐멀케이스로 적는다.

## 2. 상태 코드

성공은 조회와 수정에 200, 생성에 201, 본문 없는 성공에 204 를 쓴다.

요청이 잘못된 경우에는 400, 인증이 없거나 만료된 경우에는 401, 권한이 없는 경우에는 403, 자원이 없는 경우에는 404 를 쓴다.

서버 잘못은 500 으로 낸다. 처리하지 못한 예외를 200 으로 감싸 오류 필드에 담지 아니한다.

## 3. 오류 응답

오류 응답의 본문은 다음 형식으로 한다.

- `code` — 대문자와 밑줄로 된 오류 이름
- `message` — 사용자에게 그대로 보여도 되는 한국어 문장

`code` 는 이름만 읽고 무슨 일이 있었는지 알 수 있게 짓는다. `ERROR_1` 처럼 번호를 쓰지 아니한다.

같은 상황에 서로 다른 `code` 를 두지 아니한다. 새 이름을 추가할 때에는 기존 목록을 먼저 확인한다.

## 4. 페이지네이션

목록 응답은 `page` 와 `size` 를 질의 문자열로 받는다. `size` 의 기본값은 20, 최대값은 100 으로 한다.

응답에는 항목 배열과 함께 전체 개수를 담는다. 결과가 잘린 경우에는 잘렸다는 사실을 응답에 표시한다.

## 5. 날짜와 시각

시각은 ISO 8601 형식의 문자열로 주고받는다. 저장과 전송은 UTC 를 기준으로 하고, 표시 시점에 사용자 시간대로 바꾼다.

날짜만 필요한 값에는 시각을 붙이지 아니한다.

## 6. 호환성

이미 배포된 필드의 이름과 뜻을 바꾸지 아니한다. 필드를 없애야 하는 경우에는 새 필드를 추가해 두 판을 함께 제공한 뒤 예고 기간이 지나면 제거한다.

응답에 필드를 추가하는 것은 호환을 깨지 않는 변경으로 본다. 요청에 필수 필드를 추가하는 것은 호환을 깨는 변경이다.

## 7. 문서화

모든 엔드포인트는 API 문서에 등록한다. 문서에 없는 엔드포인트는 외부에서 쓰지 않는 것으로 본다.

문서에는 요청·응답 예시를 실제로 동작하는 값으로 적는다. 예시와 구현이 어긋나면 구현이 아니라 문서를 정본으로 보고 논의한다.

엔드포인트를 바꾼 변경은 문서 수정을 같은 변경에 포함한다. 문서 갱신을 나중으로 미루지 아니한다.
