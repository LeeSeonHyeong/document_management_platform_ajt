# 한국어 검색 평가 코퍼스

`INDEX.md` 가 경고하던 "한국어 코퍼스 측정은 미실시" 를 메우는 자산이다. 두 곳에서 쓴다.

- AI 서버 SQLite FTS5 의 한국어 토큰화 회귀 테스트 (계획 Task 2)
- Spring `wiki_search_chunk` 의 MySQL `ngram` 구현 검증 (DR-029) — 같은 셋으로 대조하면
  두 검색이 같은 품질인지 말할 수 있다

## 이것이 무엇이 아닌가 — 먼저 읽는다

**합성 코퍼스다. 실제 사내 문서가 아니다.** 여기 수치로 "우리 위키에서 잘 찾는다" 를 말할
수 없다. 말할 수 있는 것은 "한국어에서 토큰화 방식이 이만큼 차이를 만든다" 뿐이다.

**영어 코퍼스(`../corpus/`) 수치와 직접 비교하지 않는다.** 난이도가 다르다 — 여기는 100장
중에서 고르고 거기는 12건 중에서 고른다. 같은 R@5 라도 뜻이 다르다.

## 구성

```
pages/          100장.  글자수 평균 7,946 · 중앙 7,931 · 최소 7,856 · 최대 8,155
  20장          주제 페이지.  질의의 정답이 되는 것들
  d001~d080     채움 페이지.  정답이 아닌 것을 100장 규모로 채운다
queries.json    질의 40개 = 정확어 20 + 자연어 20.  dev / test 로 반씩 나뉜다
```

페이지 크기를 8k자 근처로 맞춘 이유는 실측이다. `experiments/` 의 생성된 위키가 평균
9,734B(영어)이고 한국어 위키 실측이 평균 7,793자였다. 512토큰 청크 기준으로 페이지 하나가
청크 여러 개로 쪼개지는 규모여야 청킹이 검색에 미치는 영향이 드러난다.

질의가 쓰는 정답 페이지는 17개다. 주제 페이지 중 `communication`·`performance`·`travel`
셋은 어느 질의의 정답도 아니다 — 의도한 것이다. 정답이 아닌 주제 페이지가 있어야
"그럴듯한데 답은 아닌" 후보가 순위에 섞인다.

## dev / test

| 분할 | 크기 | 규칙 |
| --- | --- | --- |
| `dev` | 정확어 10 + 자연어 10 | 튜닝·반복 측정. 여러 번 봐도 된다 |
| `test` | 정확어 10 + 자연어 10 | **판정에만. 한 번만 본다** |

`test` 를 보고 나서 구현을 고쳤으면 그 질의들은 `dev` 로 강등한다. 안 그러면 튜닝 대상을
평가 기준으로 쓰는 것이고, 그 수치는 아무것도 뜻하지 않는다.

종류별로 번갈아 나눴다. 무작위로 나누면 어느 쪽에 어려운 질의가 쏠렸는지 알 수 없다.

## 질의 종류

**정확어(exact)** — 본문에 그 단어가 글자 그대로 있다. `연차`·`이월`·`베스팅`·`패스키`.
위키 변환 에이전트의 검색이 이 성격이라고 **가정**하고 있다 (설계 문서 §2.3). 그 가정은
아직 실측으로 확인되지 않았다 — 계획 Task 9 가 실제 질의를 수집해 재검증한다.

**자연어(para)** — 뜻만 같다. `쉬는 날 며칠 받나`·`주식 받은 거 언제 팔 수 있어`. 사원
챗봇 질문이 이 성격이다. BM25 계열이 근본적으로 약한 쪽이고, 여기서 의미 검색이 필요한지가
갈린다 (측정: 자연어 R@5 0.25 → 0.80).

## 측정

```bash
cd ai && uv run python experiments/corpus-ko/evaluate_sqlite.py            # dev
cd ai && uv run python experiments/corpus-ko/evaluate_sqlite.py --split all
```

`../INDEX.md` 가 수치의 정본이다. 요약하면 2글자 분해 + OR 이 최선이고(R@5 0.60 · 정확어
0.95 · 0건 7), 현행 공백 분리 AND 가 0.33 · 0.65 · 26 이다. MySQL 8.4.11
`ngram`(`ngram_token_size=2`) 실측에서도 정확어 0.95 / MRR 0.96 이 일치했다.

**수치를 적을 때 세 가지를 함께 적는다 — 색인 방식 · 질의 방식 · 어느 분할.** 하나라도
빠지면 비교가 조용히 깨진다. 실제로 깨졌다: 초기 표가 `unicode61` 은 OR 로, `trigram` 은
폐기한 48개 세트로, 2글자는 AND 계열로 재 한 표에 나란히 두고 있었다 (`../INDEX.md`
「정정」).

위 수치는 **분할 이전 40개 전체**다. dev/test 를 나눈 것은 이번 승격이다.

## 아직 안 된 것

**블라인드 재라벨이 남았다.** 코퍼스·질의·정답 라벨을 한 사람이 작성했다 — 나다. 질의를
만들면서 어느 페이지가 답인지 알고 있었으므로 라벨이 그 기억을 반영한다. 다른 사람이 코퍼스만
보고 다시 라벨을 붙여 일치율을 재는 것이 남았다.

그때까지 이 수치는 **방식 사이의 상대 비교**에만 쓴다. "2글자가 공백 분리보다 낫다" 는
말할 수 있고 "R@5 0.60 이면 충분하다" 는 말할 수 없다.

**hard negative 보강도 남았다.** 채움 페이지 80장은 주제가 다르기만 하다. 정답과 비슷하거나
겹치거나 상충하는 페이지(같은 제도를 다르게 설명하는 옛 문서 같은 것)가 있어야 순위 품질이
제대로 드러난다.
