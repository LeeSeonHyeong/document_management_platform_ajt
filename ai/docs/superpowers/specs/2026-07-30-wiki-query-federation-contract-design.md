# Wiki 조회 창구 계약 제안 — federation 선행 명세

- 티켓: S15P11B106-150
- 선행: S15P11B106-139 (FR-WIKI-002·FR-AI-003·NFR-PERF-002 개정, DR-029·DR-030 신설)
- 상위 설계: `2026-07-29-wiki-context-federation-design.md`
- 상태: **제안**. 계약 파일(`../docs/api/`)은 이 문서로 바뀌지 않는다
- 독자: 2~8절은 백엔드, 9절은 AI

## 1. 왜 이 문서가 필요한가

FR-WIKI-002 가 개정되어 목표가 확정됐다.

> 백엔드는 그 범위를 대상으로 검색·본문·관계 조회 수단을 제공하고, 에이전트가 필요한 Wiki 를 선택해 조회한다.

같은 항목의 「단계 도입」이 **조회 수단이 준비되기 전까지는** `wiki-context-selections` 로 고르고 백엔드가 본문을 요청에 실어 보내는 과도기를 지정했다. 지금은 그 과도기다. 과도기의 대가도 요구사항에 적혀 있다 — *"문맥 범위가 그 선택에 제한되며, 위키 규모가 커질수록 수정·병합 기회를 잃는다."*

막힌 지점은 구현 능력이 아니라 **계약의 부재**다. `2026-07-29-wiki-context-federation-design.md` §11 이 *"이 문서만으로는 구현할 수 없다"* 로 시작하고 그 첫 항목이 질의 API 계약이다. 계약이 없으면 백엔드는 무엇을 만들지 모르고, AI 는 무엇을 부를지 모른다.

계약 변경 절차(`../docs/api/README.md`) 1번이 *"변경 제안자가 영향받는 Request와 소비 담당자를 적는다"* 이고 이 창구의 유일한 소비자가 AI 서버다. 그래서 AI 가 초안을 낸다.

**이 문서는 제안이다.** 합의 뒤 계약 변경 절차를 따라 `../docs/api/` 에 반영되며, 그때부터 계약이 정본이다. AI 어댑터를 제품 코드로 넣는 것도 계약이 선 다음이다.

## 2. 공통 규칙

### 2.1 헤더

| 헤더 | 용도 |
| --- | --- |
| `X-Internal-Api-Key` | 기존. "AI 서버가 맞다" |
| `X-Wiki-Capability` | **신규.** "이 요청이 이 범위를 볼 수 있다" |
| `X-Request-Id` | 기존 규약(`rest-api-convention` 6.4). 관측·상관관계용 |

두 인증값은 역할이 다르다. 키는 호출자의 신원, capability 는 이 요청의 열람 범위다.

### 2.2 capability

```
발급   백엔드가 변환·수정 요청을 시작할 때 만든다
묶임   요청 1개 · scopeKey 1개 · scopeVersion 1개
전달   AI 가 창구 호출마다 X-Wiki-Capability 에 싣는다
확인   백엔드가 서버 측 permit 으로 검증한다
소멸   요청 종료·timeout·취소 시 만료된다
금지   로그에 남기지 않는다
```

**`requestId` 를 인가에 쓰지 않는다.** 상위 설계 §7.2 가 초기 판단을 정정했다 — `requestId` 는 correlation ID 로 로그에 남고 비밀값으로 취급되지 않는다. 그것으로 열람 범위를 인가하면 로그를 본 사람이 다른 부서 위키를 조회할 수 있다.

### 2.3 오류

허가 범위 밖은 **`404`** 다. `403` 이 아니다 — `403` 은 "있지만 권한 없음"이라 다른 부서 위키의 존재를 노출한다 (NFR-SEC-003 · FR-ACL-006).

```
400   요청값 오류
401   내부 API 키 오류
404   허가 범위 밖 · capability 만료 · 대상 없음
500   서버 오류
```

**이 창구는 Spring 엔드포인트이므로 `rest-api-convention` 의 오류 규약을 따른다.** FastAPI 내부 API 가 400·401·500 으로 좁혀진 것과 다르다 — 그 제약은 Spring 클라이언트의 분기가 `UNEXPECTED_STATUS` 로 뭉개지지 않게 하려는 것이고, 방향이 반대인 이 창구에는 적용되지 않는다. AI 클라이언트는 `404` 를 정상 분기로 처리한다.

오류 본문은 기존 Spring 형식을 그대로 쓴다 (`timestamp`·`status`·`error`·`code`·`message`·`path`·`fieldErrors`).

### 2.4 scopeVersion

**모든 창구 응답에 `scopeVersion` 을 싣는다.** 백엔드가 요청 시작에 발급한 값과 다르면 AI 는 그 자리에서 중단하고 `failureStage = scope_changed` 로 응답한다 (7절).

`wiki_scope.scope_version` 컬럼이 이미 ERD 에 있다 (S15P11B106-139).

확인이 두 곳에 있다.

```
AI 쪽    창구 응답을 볼 때마다        헛일을 줄이는 장치
백엔드   반영 직전 (DR-030 · CAS)     안전장치
```

AI 쪽 확인은 백엔드 확인을 대체하지 않는다. 지금은 전역 직렬 큐가 겹침을 *우연히* 막고 있고, FR-AI-003 이 개정한 `scope_key` 별 병렬은 DR-030 배포 뒤에 켠다. 즉 이 필드는 **락 범위를 좁히기 위한 선행 조건**이다.

### 2.5 범위 파라미터

모든 창구가 `scopeKey` 를 받는다. capability 에 묶인 값과 다르면 `404` 다. 백엔드가 "이 요청은 자기 `scopeKey` 만 읽을 수 있다"를 강제해야 한다 — 없으면 AI 서버가 임의 범위를 읽어 권한 우회가 된다.

## 3. 창구 6종 (엔드포인트 7개)

본문 창구만 호출이 둘이다(목록·단건). 그래서 창구는 6종, 엔드포인트는 7개다.

### 3.1 검색

```
GET /internal/v1/wiki-search?scopeKey=D1-D2&query=연차 이월&limit=10

→ { "scopeVersion": 47,
    "items": [
      { "wikiId": "101",
        "title": "휴가 규정",
        "breadcrumb": "휴가 규정 > 연차 > 이월",
        "snippet": "연차는 다음 해 3월까지 이월할 수 있다…",
        "chunkIndex": 3,
        "contentHash": "9f2a…" } ] }
```

`wiki_search_chunk` 를 읽는다. DR-029 가 *"반영이 완료된 Wiki 만 색인하고 작업 공간의 검증 전 내용은 색인하지 않는다"* 로 정했으므로 **이 창구는 라이브만 돌려준다.** 작업 중인 페이지는 AI 가 자기 안에서 찾아 합친다 (9.2).

**질의 방식은 `boolean phrase` 로 요청한다.** 실측 근거는 `experiments/INDEX.md` — MySQL 8.4.11 `ngram_token_size=2` 에서 정확어 R@5 0.95, `natural` 은 0.90 이다. `boolean +req`(모든 어절 AND)는 **쓰지 않는다** — 자연어 질의 R@5 가 0.00 으로 전멸한다. 사원 위키 검색은 `natural` 이 낫고 에이전트는 `boolean phrase` 가 낫다는 것이 같은 측정의 결론이다.

`limit` 기본값과 상한은 6절 결정 요청 항목이다.

### 3.2 본문 — 목록

```
GET /internal/v1/wiki-pages?scopeKey=D1-D2

→ { "scopeVersion": 47,
    "items": [
      { "wikiId": "101",
        "title": "휴가 규정",
        "summary": "연차와 반차 사용 기준",
        "wikiCategoryId": "9",
        "categoryName": "휴가 및 근태",
        "wikiPath": "wiki/D1-D2/pages/a3f2c1d4.md",     // 권장 — 4절 참고
        "contentHash": "9f2a…",
        "updatedAt": "2026-07-27T09:00:00Z" } ] }
```

**본문을 싣지 않는다.** 목록은 카탈로그다.

7/28 설계(`2026-07-28-ai-server-contract-design.md` §4.1)는 `includeContent=true` 가 반드시 필요하다고 적었다. 근거는 "`search` 가 AI 안의 청크 FTS 로 돌고 청크는 본문을 저장할 때 생기므로 지연 적재가 성립하지 않는다"였다. **federated 모드에서 그 논거는 무효다** — 검색이 백엔드 창구로 나가므로 AI 가 본문을 미리 다 받아 색인할 이유가 없다. 상위 설계 §3.3 이 라이브 층을 "카탈로그 + 본문 캐시"로 가른 것이 이 뜻이다.

`summary` 는 `wiki.summary` 에서 채운다. 이 컬럼은 S15P11B106-139 로 ERD 에 추가됐다 — `index.md` 마크다운에서 되읽던 우회(D10)를 대체한다.

### 3.3 본문 — 단건

```
GET /internal/v1/wikis/101/content?scopeKey=D1-D2

→ { "scopeVersion": 47,
    "wikiId": "101",
    "title": "휴가 규정",
    "wikiPath": "wiki/D1-D2/pages/a3f2c1d4.md",        // 권장 — 4절 참고
    "contentMarkdown": "---\ntitle: 휴가 규정\n…",
    "contentHash": "9f2a…" }
```

프론트매터를 포함한 원문이다. 백엔드가 `wiki.wiki_path` 로 파일을 읽어 싣는다.

**AI 는 파일에 직접 접근하지 않는다.** 이 원칙은 창구가 생겨도 바뀌지 않는다.

### 3.4 관계

```
GET /internal/v1/wikis/101/relations?scopeKey=D1-D2

→ { "scopeVersion": 47,
    "wikiId": "101",
    "wikiRefs": ["102", "115"],          // 이 위키가 참조하는 위키
    "documentRefs": ["15"],              // 근거 원본문서
    "backlinks": ["108"] }               // 이 위키를 참조하는 위키
```

`wiki.wiki_refs` · `document_refs` JSON 을 읽는다 (DR-002 — 별도 관계 테이블은 만들지 않는다).

**`backlinks` 는 저장돼 있지 않다.** 정방향 JSON 만 있으므로 역방향은 조회로 계산해야 한다. 비용과 방식(`JSON_CONTAINS` 스캔 · 생성 컬럼 · 별도 색인)은 6절 결정 요청 항목이다.

이 창구가 필요한 이유는 FR-WIKI-002 가 *"본문·관계를 근거로 변환"* 을 요구하기 때문이다. 병합할 때 역방향을 모르면 남의 링크를 끊는다.

### 3.5 목차

```
GET /internal/v1/wiki-spaces/D1-D2/index

→ { "scopeVersion": 47, "scopeKey": "D1-D2", "indexMarkdown": "# 목차\n…" }
```

### 3.6 카테고리

```
GET /internal/v1/wiki-spaces/D1-D2/categories

→ { "scopeVersion": 47,
    "items": [ { "wikiCategoryId": "9", "name": "휴가 및 근태", "wikiCount": 12 } ] }
```

FR-WIKI-014 가 에이전트의 카테고리 생성·수정·병합·삭제를 요구하므로 현재 구조를 알아야 한다. `wikiCount` 는 병합 판단에 쓴다.

### 3.7 원본문서 파싱본

```
GET /internal/v1/documents/15/parsed?scopeKey=D1-D2

→ { "documentId": "15", "originalFileName": "취업규칙.pdf", "parsedMarkdown": "# 취업 규칙\n…" }
```

`lint` 가 각주의 인용을 원문과 대조할 때 쓴다 (FR-WIKI-001 · NFR-AI-002).

## 4. `wikiPath` — 필수가 아니라 권장

응답에 `wikiPath` 를 넣어달라고 요청하지만 **필수는 아니다.** 근거를 분명히 적는다.

AI 는 `wikiId` 만으로 주소를 지을 수 있다. `vaultfs/spring.py:80` 이 그렇게 동작한다 — *"selectedWikis 에는 `wikiPath` 가 없다 — 새 코퍼스는 `wikiId` 로 주소를 짓는다(`pages/{wikiId}.md`, `wikiId` 가 이미 있어 유일함이 보장된다)."* 따라서 "없으면 중복 페이지가 생긴다"는 것은 사실이 아니다.

필요할 수 있는 이유는 **링크 해석**이다. 위키 본문의 내부 링크는 `](a3f2c1d4.md)` 처럼 파일명(pageKey) 기준이다 (`tools/references.py:80`). 라이브 페이지를 `pages/101.md` 로 넣으면 본문에 적힌 링크가 어느 페이지도 가리키지 못하고, `lint` 가 깨진 링크로 잡아 에이전트가 남의 링크를 고치려 들 수 있다.

`wikiPath` 를 받으면 접두사(`wiki/{scopeKey}/`)만 떼어 그대로 주소로 쓰므로 이 문제가 사라진다. 백엔드 비용은 이미 저장된 컬럼(DR-016)을 응답에 넣는 것뿐이다.

**대안은 AI 가 주소 체계를 `wikiId` 기준으로 바꾸는 것인데, 툴 10개·`lint`·각주·링크 파서가 모두 영향을 받는다.** 상위 설계 §3.4 가 *"쓰기는 손대지 않는다"* 로 정했으므로 이번 범위가 아니다.

**판정은 9.2 의 검증에서 한다.** 링크 해석이 실제로 깨지는지 확인한 뒤 "필수"로 올리거나 요청을 철회한다.

## 5. 백엔드가 읽을 곳과 구현 순서 제안

### 5.1 데이터 출처

| 창구 | 읽을 곳 | 비고 |
| --- | --- | --- |
| 검색 | `wiki_search_chunk` | `FULLTEXT … WITH PARSER ngram` 이 이미 있다 |
| 본문 목록 | `wiki` + `wiki_category` | 메타데이터만 |
| 본문 단건 | `wiki.wiki_path` → 파일 | |
| 관계 | `wiki.wiki_refs` · `document_refs` | 역방향은 계산 필요 |
| 목차 | `index.md` | |
| 카테고리 | `wiki_category` + `COUNT` | |
| 파싱본 | 문서 파싱 파일 | |

### 5.2 순서 제안

```
1  바로 되는 것       본문 목록 · 본문 단건 · 목차 · 카테고리 · 파싱본
                      있는 데이터를 꺼내는 것에 가깝다

2  선행 작업이 있는 것  검색
                      S15P11B106-146 (검색 청크 색인) 이 채워져야 동작한다

3  새로 만드는 것      관계 (역방향 계산) · capability (인증 신설)
```

### 5.3 재사용 제안

`WikiQueryService` 가 이미 위키 읽기와 범위 접근 검증을 갖고 있다 (`WikiQueryServiceScopeAccessTest`). 내부 창구는 **그 서비스를 재사용하고 인증만 교체**하면 1군(본문·목차·카테고리)의 구현 비용이 크게 줄어든다.

`-145` 가 만드는 `/api/v1/...` 는 프론트엔드용 공개 API 이고 이 창구는 `/internal/v1/...` 이므로 경로도 인증도 충돌하지 않는다.

## 6. 백엔드 결정 요청

AI 가 정하면 안 되는 것이다.

**6.1 capability** — 발급·보관·만료 방식. 형식(불투명 토큰 vs 서명값), 만료 시간, `scopeVersion` 을 토큰에 넣을지 서버 측 permit 에만 둘지.

**6.2 페이지네이션·상한** — 본문 목록과 검색의 결과 상한, 커서 방식, 배치 조회 여부. 위키 1,000장 규모에서 목록 한 번에 주기가 가능한지.

**6.3 역방향 관계** — `backlinks` 계산 방식과 비용. 매 호출 스캔이 부담이면 응답에서 빼고 AI 가 정방향만으로 처리하도록 조정할 수 있다.

**6.4 재진입** — Spring → AI 호출 중에 AI → Spring 콜백이 생긴다. 상위 설계 §11.6 이 지적한다 — S15P11B106-73(트랜잭션 경계)이 남아 있거나 scope lease 가 비재진입 락이면 **DB 커넥션 고갈 또는 교착**이 난다. lease 는 재진입 가능해야 하고 AI 호출은 트랜잭션 밖이어야 한다.

**6.5 장애 처리** — Spring 장애·응답 유실 시 상태 전이, permit·lease 가 AI timeout 과 프로세스 고아화 후에도 남는 실패 모드, 과거 `scopeVersion` 보존 여부(보존하지 않으면 "같은 버전 조회"를 제공할 수 없다).

**6.6 D1 과의 관계** — 백엔드 read-timeout 이 10분이고 실측 최장이 894.6초(14.9분)다. NFR-PERF-002 가 요구하는 것은 `백엔드 대기 > AI 절대 상한` 부등호다. AI 측은 처리 시간을 10분 안으로 줄이고 **절대 상한도 10분 밑으로 내리는 방향으로 정했다**(별건). 창구가 늘면 왕복이 늘어나므로 그 예산 안에 들어가는지 함께 봐야 한다.

## 7. AI 가 제안해 정한 것 — 협의 항목

### `failureStage` 에 `scope_changed` 신설

NFR-AI-003 이 정한 실패 단계는 다섯이다.

```
context_load   agent_timeout   agent_error   lint_failed   assemble
scope_changed  ← 신규 제안: 작업 중 같은 범위의 위키가 바뀜
```

기존 다섯 중 버전 불일치에 맞는 값이 없다. 탈락시킨 후보와 이유:

- `version_conflict` — 계약 버전과 혼동된다
- `scope_version_conflict` — 기존 다섯보다 눈에 띄게 길다
- `stale_context` — 원인이 아니라 증상이다

이 실패는 `FAILED` 로 기록되고, FR-DOC-012 가 `FAILED`·`CANCELLED` 만 재처리 가능하다고 정했으므로 별도 규칙 없이 재처리 대상이 된다.

**백엔드가 다른 이름을 원하면 바꾼다.** 계약에 없던 값을 AI 가 정한 것이므로 협의 항목으로 남긴다.

## 9. AI 쪽 작업

### 9.1 진행 방식

주문서를 백엔드에 먼저 넘기고 함께 맞춰간다. AI 는 기다리지 않고 `experiments/backend_sim.py` 를 창구 대역으로 세워 병행 검증한다. 백엔드 구현이 나오면 주소만 바꿔 끼운다.

**이 검증이 증명하는 것은 "우리 주문서에 앞뒤가 안 맞는 게 없다"까지다.** 가짜 서버는 우리가 상상한 대로 답한다. "백엔드가 실제로 이렇게 만들 수 있다"는 백엔드 검토에서만 확인된다.

데이터는 `experiments/corpus-ko/` 를 쓴다 — 한국어 위키 100장, 질의 40개.

### 9.2 검증 항목

| 확인 | 실패하면 |
| --- | --- |
| 기존 페이지를 고치는가 | 이름표가 안 맞는다 |
| 라이브 본문의 위키 링크가 해석되는가 | 4절 판정 — `wikiPath` 를 필수로 올린다 |
| 검색에 라이브와 작업층이 모두 나오는가 | 방금 쓴 페이지를 에이전트가 못 찾는다 |
| 버전을 바꿔 두면 `scope_changed` 로 멈추는가 | 헛일을 계속한다 |
| 허가 범위 밖이 `404` 인가 | 권한 우회 구멍 |
| 같은 본문을 두 번 받지 않는가 | `contentHash` 규칙이 헛돈다 |

검색은 **두 섹션으로 나눠** 에이전트에게 보여준다 (상위 설계 §7.1). 라이브(창구)와 작업층(AI 내부)을 섞으면 에이전트가 "내가 방금 쓴 것"과 "원래 있던 것"을 구분하지 못한다.

### 9.3 작업층 검색 결과 상한

상위 설계 §7.1 은 *"work 결과는 자르지 않는다"* 인데 D8(출력 토큰 과다)과 충돌하고, 문서 자신이 *"상한을 둔다"* 로 결론을 냈다. **상한을 둔다.** 자르지 않으면 검색 응답이 부풀고 그대로 출력 토큰이 되어 10분 목표를 깨뜨린다.

**숫자는 지금 정하지 않는다.** 100장 규모에서 실측해 정하고 `experiments/INDEX.md` 에 근거를 남긴다.

### 9.4 캐시 규칙

```
요청 시작   임시 루트를 연다 (지금과 같음)
작업 중     창구에서 받은 카탈로그·본문을 쌓는다
요청 끝     통째로 버린다
```

영속 색인은 만들지 않는다. 상위 설계 §6.4 가 기각했다 — 색인이 남으면 그것이 두 번째 정본이 되어 백엔드와 어긋난다.
