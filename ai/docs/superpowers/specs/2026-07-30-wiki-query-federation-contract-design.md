# Wiki 조회 창구 계약 제안 — federation 선행 명세

- 티켓: S15P11B106-150
- 선행: S15P11B106-139 (FR-WIKI-002·FR-AI-003·NFR-PERF-002 개정, DR-029·DR-030 신설)
- 상위 설계: `2026-07-29-wiki-context-federation-design.md`
- 상태: **제안**. 계약 파일(`../docs/api/`)은 이 문서로 바뀌지 않는다
- 독자: 2~8절은 백엔드, 9절은 AI

## 1. 왜 이 문서가 필요한가

FR-WIKI-002 가 개정되어 목표가 확정됐다.

> 백엔드는 그 범위를 대상으로 검색·본문·관계 조회 수단을 제공하고, 에이전트가 필요한 Wiki 를 선택해 조회한다.

같은 항목의 「단계 도입」이 **조회 수단이 준비되기 전까지는** `wiki-context-selections` 로 고르고 백엔드가 본문을 요청에 실어 보내는 과도기를 지정했다. 지금은 그 과도기다. 과도기의 대가도 요구사항에 적혀 있다 — *"문맥 범위가 그 선택에 제한되며, 위키 규모가 커질수록 수정·병합 기회를 잃는다."*

막힌 지점은 구현 능력이 아니라 **계약의 부재**다. `2026-07-29-wiki-context-federation-design.md` §11 이 *"이 문서만으로는 구현할 수 없다"* 로 시작하고 그 첫 항목이 질의 API 계약이다. 계약이 없으면 백엔드는 무엇을 만들지 모르고, AI 는 무엇을 부를지 모른다.

계약 변경 절차(`../docs/api/README.md`) 1번이 *"변경 제안자가 영향받는 Request와 소비 담당자를 적는다"* 이고 이 창구의 유일한 소비자가 AI 서버다. 그래서 AI 가 초안을 낸다.

**이 문서는 제안이다.** 합의 뒤 계약 변경 절차를 따라 `../docs/api/` 에 반영되며, 그때부터 계약이 정본이다. AI 어댑터를 제품 코드로 넣는 것도 계약이 선 다음이다.

## 2. 공통 규칙

### 2.1 헤더

| 헤더 | 용도 |
| --- | --- |
| `X-Internal-Api-Key` | 기존. "AI 서버가 맞다" |
| `X-Wiki-Capability` | **신규.** "이 요청이 이 범위를 볼 수 있다" |
| `X-Request-Id` | 기존 규약(`rest-api-convention` 6.4). 관측·상관관계용 |

두 인증값은 역할이 다르다. 키는 호출자의 신원, capability 는 이 요청의 열람 범위다.

### 2.2 capability

```
발급   백엔드가 변환·수정 요청을 시작할 때 만든다
묶임   요청 1개 · scopeKey 1개                     ← scopeVersion 은 묶지 않는다
전달   AI 가 창구 호출마다 X-Wiki-Capability 에 싣는다
확인   백엔드가 서버 측 permit 으로 검증한다
소멸   요청 종료·timeout·취소 시 만료된다
금지   로그에 남기지 않는다
```

**`scopeVersion` 을 capability 에 묶지 않는다 — 초기 판단을 정정한다.** 앞 판본은 요청 1개·`scopeKey` 1개·`scopeVersion` 1개에 묶는다고 적었는데, 그러면 2.4 의 버전 불일치 감지가 성립하지 않는다.

```
묶었을 때   버전이 바뀌면 capability 가 무효 → 404
            404 는 "허가 밖 · 만료 · 없음" 을 한 값으로 덮는다 (2.3)
            → AI 는 "버전이 바뀌었다" 와 "페이지가 없다" 를 구분할 수 없다
            → scope_changed 를 낼 근거가 사라진다
```

**capability 는 `scopeKey` 와 요청 생명주기만 인가하고, 읽기는 항상 현재 버전을 돌려준다.** 버전이 바뀌어도 창구는 `200` + 새 `scopeVersion` 을 주고, 판정은 AI 가 한다.

검토하고 채택하지 않은 대안: 스냅샷 읽기(항상 발급 시점 버전을 돌려준다). 일관성은 가장 높지만 백엔드가 과거 버전을 보존해야 하고, DR-030 이 *"버전 유지를 위해 DB 트랜잭션을 실행 시간 동안 열어 두지 않는다"* 로 정한 방향과 반대다. 과거 스냅샷 보존은 요구사항에 없다.

**`requestId` 를 인가에 쓰지 않는다.** 상위 설계 §7.2 가 초기 판단을 정정했다 — `requestId` 는 correlation ID 로 로그에 남고 비밀값으로 취급되지 않는다. 그것으로 열람 범위를 인가하면 로그를 본 사람이 다른 부서 위키를 조회할 수 있다.

### 2.3 오류

허가 범위 밖은 **`404`** 다. `403` 이 아니다 — `403` 은 "있지만 권한 없음"이라 다른 부서 위키의 존재를 노출한다 (NFR-SEC-003 · FR-ACL-006).

```
400   요청값 오류
401   내부 API 키 오류
404   허가 범위 밖 · capability 만료 · 대상 없음
500   서버 오류
```

**HTTP 상태는 같아도 `code` 로 구분한다.** 상태를 나누면 존재가 노출되지만, 오류 본문의 `code` 는 이미 허가를 통과한 호출자만 본다. AI 가 안전하게 멈추려면 "내 허가가 죽었다"와 "그 페이지가 없다"를 구분해야 한다.

| `code` | 뜻 | AI 의 처리 |
| --- | --- | --- |
| `WIKI_CAPABILITY_EXPIRED` | 허가 만료·철회 | 즉시 중단. `failureStage = scope_changed` |
| `WIKI_SCOPE_NOT_FOUND` | 허가 범위 밖 범위 | 즉시 중단. `failureStage = context_load` |
| `WIKI_NOT_FOUND` | 그 위키가 없음 | 카탈로그에 있었다면 중단(2.6), 없었다면 정상 분기 |
| `DOCUMENT_NOT_FOUND` | 그 원본문서가 없음 | 각주 검증 실패로 처리 |

`message` 는 네 경우 모두 같은 문장을 쓴다 — 메시지로 존재가 새지 않게 한다.

**이 창구는 Spring 엔드포인트이므로 `rest-api-convention` 의 오류 규약을 따른다.** FastAPI 내부 API 가 400·401·500 으로 좁혀진 것과 다르다 — 그 제약은 Spring 클라이언트의 분기가 `UNEXPECTED_STATUS` 로 뭉개지지 않게 하려는 것이고, 방향이 반대인 이 창구에는 적용되지 않는다. AI 클라이언트는 `404` 를 정상 분기로 처리한다.

오류 본문은 기존 Spring 형식을 그대로 쓴다 (`timestamp`·`status`·`error`·`code`·`message`·`path`·`fieldErrors`).

### 2.4 scopeVersion

**위키를 다루는 창구 6개 응답에 `scopeVersion` 을 싣는다.** 백엔드가 요청 시작에 발급한 값과 다르면 AI 는 그 자리에서 중단하고 `failureStage = scope_changed` 로 응답한다 (7절).

**원본문서 파싱본(3.7)은 예외다.** 원본문서는 위키 스냅샷의 일부가 아니다 — 파싱 결과는 위키가 몇 번 바뀌든 그대로다. 여기에 위키 버전을 실으면 무관한 이유로 작업이 중단된다.

`wiki_scope.scope_version` 컬럼이 이미 ERD 에 있다 (S15P11B106-139).

확인이 두 곳에 있다.

```
AI 쪽    창구 응답을 볼 때마다        헛일을 줄이는 장치
백엔드   반영 직전 (DR-030 · CAS)     안전장치
```

AI 쪽 확인은 백엔드 확인을 대체하지 않는다. 지금은 전역 직렬 큐가 겹침을 *우연히* 막고 있고, FR-AI-003 이 개정한 `scope_key` 별 병렬은 DR-030 배포 뒤에 켠다. 즉 이 필드는 **락 범위를 좁히기 위한 선행 조건**이다.

### 2.5 창구를 부를 수단은 변환·수정 요청이 준다

capability 와 시작 버전이 AI 에 들어올 경로가 필요하다. **창구만 만들고 열쇠를 전달하지 않으면 AI 는 창구를 부를 수 없다.**

`wiki-transformations`·`wiki-edits` 요청에 두 필드를 더한다.

```
wikiCapability   string   창구 호출에 실을 허가. 없으면 AI 는 창구를 부르지 않는다
scopeVersion     integer  요청 시작 시점의 범위 버전. 응답과 비교할 기준
```

**둘 다 선택 필드다.** 없으면 AI 는 지금처럼 `selectedWikis` 로 동작한다(과도기 push). 있으면 창구를 쓴다. 그래서 백엔드가 창구를 배포하기 전에도 계약이 깨지지 않고, 배포 후에는 요청에 두 값을 넣는 것만으로 전환된다.

**`wikiCapability` 는 마스킹 대상이다.** AI 서버는 이 값을 로그·예외 메시지·telemetry 에 남기지 않는다. 오류 본문에 실어 되돌리지도 않는다.

### 2.6 카탈로그에 있던 페이지가 사라지면 멈춘다

목록(3.2)에 있던 `wikiId` 의 본문 조회가 `WIKI_NOT_FOUND` 로 오면, 그 사이 지워진 것이다. **빈 본문으로 계속 진행하지 않는다** — 에이전트가 빈 페이지를 보고 "내용이 없다"고 판단해 덮어쓸 수 있다.

`failureStage = scope_changed` 로 중단한다. 2.2 를 고친 뒤에도 목록과 본문 조회 사이의 경합은 남으므로, 버전 비교만으로는 이 경우를 못 잡는다.

### 2.7 범위 파라미터

모든 창구가 `scopeKey` 를 받는다. capability 에 묶인 값과 다르면 `404` 다. 백엔드가 "이 요청은 자기 `scopeKey` 만 읽을 수 있다"를 강제해야 한다 — 없으면 AI 서버가 임의 범위를 읽어 권한 우회가 된다.

## 3. 창구 6종 (엔드포인트 7개)

본문 창구만 호출이 둘이다(목록·단건). 그래서 창구는 6종, 엔드포인트는 7개다.

### 3.1 검색

```
GET /internal/v1/wiki-search?scopeKey=D1-D2&query=연차 이월&limit=10

→ { "scopeVersion": 47,
    "items": [
      { "wikiId": "101",
        "title": "휴가 규정",
        "breadcrumb": "휴가 규정 > 연차 > 이월",
        "snippet": "연차는 다음 해 3월까지 이월할 수 있다…",
        "chunkIndex": 3,
        "contentHash": "9f2a…" } ] }
```

`wiki_search_chunk` 를 읽는다. DR-029 가 *"반영이 완료된 Wiki 만 색인하고 작업 공간의 검증 전 내용은 색인하지 않는다"* 로 정했으므로 **이 창구는 라이브만 돌려준다.** 작업 중인 페이지는 AI 가 자기 안에서 찾아 합친다 (9.2).

**질의 방식은 `boolean phrase` 로 요청한다.** 실측 근거는 `experiments/INDEX.md` — MySQL 8.4.11 `ngram_token_size=2` 에서 정확어 R@5 0.95, `natural` 은 0.90 이다. `boolean +req`(모든 어절 AND)는 **쓰지 않는다** — 자연어 질의 R@5 가 0.00 으로 전멸한다. 사원 위키 검색은 `natural` 이 낫고 에이전트는 `boolean phrase` 가 낫다는 것이 같은 측정의 결론이다.

**계약으로 확정한다** — 백엔드가 정하게 남기면 그 값이 검색 품질을 좌우한다.

| 항목 | 값 | 근거 |
| --- | --- | --- |
| `limit` 기본 | `10` | 에이전트가 한 번에 훑을 수 있는 양. 상위 설계의 R@5 측정도 K=5 기준이다 |
| `limit` 최대 | `50` | 넘으면 `400`. 검색 응답이 그대로 출력 토큰이 되므로(9.5) 상한이 필요하다 |
| 정렬 | 관련도 내림차순, 동률은 `wikiId` 오름차순 → `chunkIndex` 오름차순 | 동률 순서가 흔들리면 같은 질의가 다른 결과를 낸다 |
| 페이지네이션 | **없다** | `limit` 안에서 끝낸다. 에이전트가 검색 결과 2페이지를 넘기는 동작은 없다 |
| 질의 모드 | 서버가 항상 `boolean phrase` 로 수행한다 | 파라미터로 열지 않는다 — 에이전트가 `+req` 를 골라 자연어 질의를 전멸시킬 수 있다 |

`query` 가 빈 문자열이면 `400` 이다. FTS 빈 식은 문법 오류이고, 그 예외가 툴 응답에 「오류」로 나가면 에이전트가 검색 자체를 포기한다.

### 3.2 본문 — 목록

```
GET /internal/v1/wiki-pages?scopeKey=D1-D2&cursor=&limit=200

→ { "scopeVersion": 47,
    "nextCursor": "eyJ3aWtpSWQiOiIzMDEifQ",           // 더 없으면 null
    "items": [
      { "wikiId": "101",
        "title": "휴가 규정",
        "summary": "연차와 반차 사용 기준",
        "wikiCategoryId": "9",
        "categoryName": "휴가 및 근태",
        "wikiPath": "wiki/D1-D2/pages/a3f2c1d4.md",     // 필수 — 4절 참고
        "contentHash": "9f2a…",
        "updatedAt": "2026-07-27T09:00:00Z" } ] }
```

**본문을 싣지 않는다.** 목록은 카탈로그다.

**페이지네이션을 계약으로 확정한다.** 위키 1,000장이면 카탈로그만으로도 응답이 커진다.

| 항목 | 값 |
| --- | --- |
| `limit` 기본 / 최대 | `200` / `500` (넘으면 `400`) |
| 정렬 | `wikiId` 오름차순 — 안정 정렬이라 커서가 항목을 건너뛰거나 겹치지 않는다 |
| `cursor` | 불투명 문자열. 백엔드가 형식을 정한다. AI 는 받은 값을 그대로 되돌려준다 |
| `nextCursor` | 다음 페이지가 없으면 `null` |

AI 는 `nextCursor` 가 `null` 이 될 때까지 이어 받아 카탈로그를 완성한다. **`scopeVersion` 이 페이지 사이에 바뀌면 중단한다**(2.4) — 반쯤 낡은 카탈로그로 작업하면 안 된다.

7/28 설계(`2026-07-28-ai-server-contract-design.md` §4.1)는 `includeContent=true` 가 반드시 필요하다고 적었다. 근거는 "`search` 가 AI 안의 청크 FTS 로 돌고 청크는 본문을 저장할 때 생기므로 지연 적재가 성립하지 않는다"였다. **federated 모드에서 그 논거는 무효다** — 검색이 백엔드 창구로 나가므로 AI 가 본문을 미리 다 받아 색인할 이유가 없다. 상위 설계 §3.3 이 라이브 층을 "카탈로그 + 본문 캐시"로 가른 것이 이 뜻이다.

`summary` 는 `wiki.summary` 에서 채운다. 이 컬럼은 S15P11B106-139 로 ERD 에 추가됐다 — `index.md` 마크다운에서 되읽던 우회(D10)를 대체한다.

### 3.3 본문 — 단건

```
GET /internal/v1/wikis/101/content?scopeKey=D1-D2

→ { "scopeVersion": 47,
    "wikiId": "101",
    "title": "휴가 규정",
    "wikiPath": "wiki/D1-D2/pages/a3f2c1d4.md",        // 권장 — 4절 참고
    "contentMarkdown": "---\ntitle: 휴가 규정\n…",
    "contentHash": "9f2a…" }
```

프론트매터를 포함한 원문이다. 백엔드가 `wiki.wiki_path` 로 파일을 읽어 싣는다.

**AI 는 파일에 직접 접근하지 않는다.** 이 원칙은 창구가 생겨도 바뀌지 않는다.

### 3.4 관계

```
GET /internal/v1/wikis/101/relations?scopeKey=D1-D2

→ { "scopeVersion": 47,
    "wikiId": "101",
    "wikiRefs": ["102", "115"],          // 이 위키가 참조하는 위키
    "documentRefs": ["15"],              // 근거 원본문서
    "backlinks": ["108"] }               // 이 위키를 참조하는 위키
```

`wiki.wiki_refs` · `document_refs` JSON 을 읽는다 (DR-002 — 별도 관계 테이블은 만들지 않는다).

**`backlinks` 는 저장돼 있지 않다.** 정방향 JSON 만 있으므로 역방향은 조회로 계산해야 한다. 비용과 방식(`JSON_CONTAINS` 스캔 · 생성 컬럼 · 별도 색인)은 6절 결정 요청 항목이다.

이 창구가 필요한 이유는 FR-WIKI-002 가 *"본문·관계를 근거로 변환"* 을 요구하기 때문이다. 병합할 때 역방향을 모르면 남의 링크를 끊는다.

### 3.5 목차

```
GET /internal/v1/wiki-spaces/D1-D2/index

→ { "scopeVersion": 47, "scopeKey": "D1-D2", "indexMarkdown": "# 목차\n…" }
```

### 3.6 카테고리

```
GET /internal/v1/wiki-spaces/D1-D2/categories

→ { "scopeVersion": 47,
    "items": [ { "wikiCategoryId": "9", "name": "휴가 및 근태", "wikiCount": 12 } ] }
```

FR-WIKI-014 가 에이전트의 카테고리 생성·수정·병합·삭제를 요구하므로 현재 구조를 알아야 한다. `wikiCount` 는 병합 판단에 쓴다.

### 3.7 원본문서 파싱본

```
GET /internal/v1/documents/15/parsed?scopeKey=D1-D2

→ { "documentId": "15", "originalFileName": "취업규칙.pdf", "parsedMarkdown": "# 취업 규칙\n…" }
```

`lint` 가 각주의 인용을 원문과 대조할 때 쓴다 (FR-WIKI-001 · NFR-AI-002).

**이 창구만 `scopeVersion` 이 없다.** 2.4 의 예외다 — 원본문서 파싱 결과는 위키가 몇 번 바뀌든 그대로이므로, 위키 버전을 실으면 무관한 이유로 작업이 중단된다.

## 4. `wikiPath` — 필수다. 그리고 지금 push 경로가 이미 깨져 있다

**앞 판본은 "권장"이라고 적었다. 정정한다 — 필수다.** 그리고 이 필드의 부재는 창구의 문제가 아니라 **현재 돌고 있는 코드의 결함**이다.

### 4.1 왜 필수인가

AI 는 `wikiId` 만으로도 주소를 지을 수 있다. `vaultfs/spring.py:80` 이 그렇게 동작한다 — *"selectedWikis 에는 `wikiPath` 가 없다 — 새 코퍼스는 `wikiId` 로 주소를 짓는다(`pages/{wikiId}.md`)."* 그래서 **중복 페이지는 생기지 않는다.** 앞 판본이 그렇게 적은 것은 틀렸다.

문제는 **링크 해석**이다.

```
저장된 본문의 링크    ](a3f2c1d4.md)          파일명(pageKey) 기준   tools/references.py:76
하이드레이션 주소     pages/101.md            wikiId 기준            vaultfs/spring.py:80
                      → 링크가 어느 페이지도 가리키지 못한다
```

그러면 라이브 페이지 사이의 인용 그래프가 통째로 비고, `lint` 가 깨진 링크로 잡아 에이전트가 **남의 링크를 고치려 들 수 있다.** 병합·제거에서는 끊어야 할 링크와 그대로 둘 링크를 구분하지 못한다.

### 4.2 창구만의 문제가 아니다 — 지금 깨져 있다

계약의 `selectedWikis` 에 `wikiPath` 가 없다. 코드도 그것을 받거나 넘기지 않는다.

```
schemas.py:123        SelectedWiki 에 wikiPath 없음
routers/wiki.py:41    변환 요청에서 넘기지 않음
spring.py:80          그래서 pages/{wikiId}.md 로 적재
references.py:76      링크 파서는 pages/{pageKey}.md 를 해석
test_api_wiki.py:161  ID 기반 주소를 테스트가 고정하고 있음
```

**과도기 push 경로에서도 라이브 페이지의 내부 링크가 해석되지 않는다.** 창구를 만들지 않아도 고쳐야 하는 결함이다. `lint` 가 라이브 전용 페이지의 내용 검사를 하지 않으므로(`tools/lint.py:39`) AI 쪽에서는 조용히 지나간다.

### 4.2.1 S15P11B106-149 가 머지되면서 하드 실패로 승격됐다

`-149`(AI 발급 경로 반영)가 develop 에 들어왔다. **그 변경은 옳고, 이 결함과 만나서 문서 반영을 통째로 실패시킨다.**

`-149` 는 반영 전에 본문의 Wiki 링크를 실제 경로 목록과 대조하고, 없으면 예외를 던진다.

```java
// WikiMarkdownLinkValidator:22-23
if (!target.endsWith(".md") || target.contains("..")
        || !allowedAddresses.contains(target)) {
    throw new IllegalArgumentException("Wiki 페이지 링크를 찾을 수 없습니다: " + target);
}
```

백엔드 설계 문서도 못 박았다 — *"존재하지 않는 Wiki 페이지를 가리키면 전체 반영을 실패시킨다"* (`../docs/superpowers/specs/2026-07-30-wiki-agent-paths-design.md`).

그래서 실패 경로가 이렇게 닫힌다.

```
1  백엔드가 selectedWikis 에 wikiPath 를 보내지 않는다
2  AI 가 라이브 페이지를 pages/{wikiId}.md 로 적재한다
3  에이전트가 그 페이지를 링크한다 — 자기가 본 주소를 쓴다
4  Spring 이 실제 경로 목록(pages/{pageKey}.md)과 대조한다 → 없다
5  예외 → 그 문서의 반영이 전체 실패한다
```

**즉 에이전트가 기존 페이지를 링크하는 순간 변환이 실패한다.** 병합·"관련 문서" 링크는 정상 동작이므로 드문 경우가 아니다.

`wikiPath` 를 계약 1.6.0 에서 필수로 한 것이 이 실패의 정본 해결책이다. 백엔드가 그 값을 채우면 AI 의 주소가 실제 파일명과 같아지고 검증을 통과한다.

**확인 필요** — `-149` 가 `selectedWikis` 에 `wikiPath` 를 넣지 않은 것은 코드로 확인했다 (`backend/.../global/ai/` 안에서 `wikiPath` 는 `WikiTransformationResponse.java:25` 한 곳, 즉 AI→Spring 방향뿐이다). 실제로 반영 실패가 재현되는지는 실기동으로 확인해야 한다 — 지금 근거는 코드 판독이다.

### 4.3 조치

```
창구 응답 (3.2 · 3.3)          wikiPath 필수
selectedWikis (과도기 push)    기존 위키에 wikiPath 필수 추가 → 계약 1.6.0
신규 위키                       AI 가 발급한 경로를 응답에 실어 보낸다 (계약 v1.3.1 부터 있음)
```

백엔드 비용은 이미 저장된 컬럼(DR-016)을 응답과 요청에 넣는 것뿐이다.

**대안(AI 가 주소 체계를 `wikiId` 기준으로 바꾸는 것)은 채택하지 않는다.** 저장된 파일명과 본문에 적힌 링크를 전부 마이그레이션해야 한다. 상위 설계 §3.4 가 *"쓰기는 손대지 않는다"* 로 정한 것과도 반대다.

**별건으로 분리한다.** push 경로 수정은 창구와 독립이므로 이 티켓에 섞지 않는다 (10절).

## 6. 백엔드 결정 요청

AI 가 정하면 안 되는 것이다.

**6.1 capability 의 형식과 만료 시간** — 불투명 토큰인지 서명값인지, 만료를 몇 분으로 둘지, 서버 측 permit 을 어디에 보관할지.

**묶는 범위는 정해졌다** — 요청 1개와 `scopeKey` 1개다. `scopeVersion` 은 묶지 않는다. 2.2 가 이유를 적었다(묶으면 버전 불일치를 `404` 로 덮어 `scope_changed` 를 낼 수 없다).

**6.2 커서 형식** — 페이지네이션의 존재·기본값·상한·정렬은 3.1·3.2 에서 계약으로 확정했다. 남은 것은 `cursor` 문자열의 내부 형식뿐이고 그것은 백엔드 소관이다. AI 는 받은 값을 그대로 되돌려준다.

**6.3 역방향 관계** — `backlinks` 계산 방식과 비용. 매 호출 스캔이 부담이면 응답에서 빼고 AI 가 정방향만으로 처리하도록 조정할 수 있다.

**6.4 재진입** — Spring → AI 호출 중에 AI → Spring 콜백이 생긴다. 상위 설계 §11.6 이 지적한다 — S15P11B106-73(트랜잭션 경계)이 남아 있거나 scope lease 가 비재진입 락이면 **DB 커넥션 고갈 또는 교착**이 난다. lease 는 재진입 가능해야 하고 AI 호출은 트랜잭션 밖이어야 한다.

**6.5 장애 처리** — Spring 장애·응답 유실 시 상태 전이, permit·lease 가 AI timeout 과 프로세스 고아화 후에도 남는 실패 모드.

**과거 `scopeVersion` 보존은 필요 없다.** 2.2 에서 스냅샷 읽기를 채택하지 않았으므로 백엔드는 현재 버전만 알면 된다.

**6.6 백엔드 read-timeout** — 지금 10분이고 실측 최장이 894.6초(14.9분)다. NFR-PERF-002 가 요구하는 것은 `백엔드 대기 > AI 절대 상한` 부등호다. **AI 측이 10분 안에 끝내고 절대 상한도 10분 밑으로 내리는 방향으로 정했으므로 백엔드 값은 그대로 둔다**(별건). 이 창구 때문에 늘려달라는 요청이 아니다 — 근거는 9.5.

## 7. AI 가 제안해 정한 것 — 협의 항목

### `failureStage` 에 `scope_changed` 신설

NFR-AI-003 이 정한 실패 단계는 다섯이다.

```
context_load   agent_timeout   agent_error   lint_failed   assemble
scope_changed  ← 신규 제안: 작업 중 같은 범위의 위키가 바뀜
```

기존 다섯 중 버전 불일치에 맞는 값이 없다. 탈락시킨 후보와 이유:

- `version_conflict` — 계약 버전과 혼동된다
- `scope_version_conflict` — 기존 다섯보다 눈에 띄게 길다
- `stale_context` — 원인이 아니라 증상이다

이 실패는 `FAILED` 로 기록되고, FR-DOC-012 가 `FAILED`·`CANCELLED` 만 재처리 가능하다고 정했으므로 별도 규칙 없이 재처리 대상이 된다.

**백엔드가 다른 이름을 원하면 바꾼다.** 계약에 없던 값을 AI 가 정한 것이므로 협의 항목으로 남긴다.

**계약 버전을 1.4.0 이 아니라 1.5.0 으로 올린 이유.** 반영 전 `README` 는 `1.4.0`, 컬렉션은 `1.3.1` 로 갈라져 있었다 — `abbe101` 이 README 만 올리고 생성기를 안 올렸고, 한 시간 뒤 `fbb5492` 가 생성기를 `1.3.1` 로 올려 어긋났다. 내용은 양쪽에 다 있고 숫자만 안 맞았다. 어느 쪽 번호도 재사용하지 않고 둘을 `1.5.0` 으로 합쳤다.

## 9. AI 쪽 작업

### 9.1 진행 방식

주문서를 백엔드에 먼저 넘기고 함께 맞춰간다. AI 는 기다리지 않고 `experiments/backend_sim.py` 를 창구 대역으로 세워 병행 검증한다. 백엔드 구현이 나오면 주소만 바꿔 끼운다.

**이 검증이 증명하는 것은 "우리 주문서에 앞뒤가 안 맞는 게 없다"까지다.** 가짜 서버는 우리가 상상한 대로 답한다. "백엔드가 실제로 이렇게 만들 수 있다"는 백엔드 검토에서만 확인된다.

데이터는 `experiments/corpus-ko/` 를 쓴다 — 한국어 위키 100장, 질의 40개.

### 9.2 검증 항목

| 확인 | 실패하면 |
| --- | --- |
| 기존 페이지를 고치는가 | 이름표가 안 맞는다 |
| 라이브 본문의 위키 링크가 해석되는가 | 4절 판정 — `wikiPath` 를 필수로 올린다 |
| 검색에 라이브와 작업층이 모두 나오는가 | 방금 쓴 페이지를 에이전트가 못 찾는다 |
| 버전을 바꿔 두면 `scope_changed` 로 멈추는가 | 헛일을 계속한다 |
| 허가 범위 밖이 `404` 인가 | 권한 우회 구멍 |
| 같은 본문을 두 번 받지 않는가 | `contentHash` 규칙이 헛돈다 |

검색은 **두 섹션으로 나눠** 에이전트에게 보여준다 (상위 설계 §7.1). 라이브(창구)와 작업층(AI 내부)을 섞으면 에이전트가 "내가 방금 쓴 것"과 "원래 있던 것"을 구분하지 못한다.

### 9.3 작업층 검색 결과 상한

상위 설계 §7.1 은 *"work 결과는 자르지 않는다"* 인데 D8(출력 토큰 과다)과 충돌하고, 문서 자신이 *"상한을 둔다"* 로 결론을 냈다. **상한을 둔다.** 자르지 않으면 검색 응답이 부풀고 그대로 출력 토큰이 되어 10분 목표를 깨뜨린다.

**숫자는 지금 정하지 않는다.** 100장 규모에서 실측해 정하고 `experiments/INDEX.md` 에 근거를 남긴다.

### 9.4 캐시 규칙

```
요청 시작   임시 루트를 연다 (지금과 같음)
작업 중     창구에서 받은 카탈로그·본문을 쌓는다
요청 끝     통째로 버린다
```

영속 색인은 만들지 않는다. 상위 설계 §6.4 가 기각했다 — 색인이 남으면 그것이 두 번째 정본이 되어 백엔드와 어긋난다.

### 9.5 시간 예산 — 조회 왕복은 변수가 아니다

**10분 목표는 이 창구 때문에 흔들리지 않는다.** 창구가 늘면 왕복이 늘어 느려질 것 같지만 실측이 반대를 말한다.

```
하이드레이션 100장     712ms
FTS 검색               2.4ms
에이전트 루프 (문서 1건)  126 ~ 894초
```

문맥 준비가 실행 시간의 **0.1~0.7%** 다. 상위 설계 §2.2 의 결론이 *"문맥 범위를 넓히는 비용은 무의미하다 — 속도는 결정 변수가 아니다"* 인 이유다.

시간을 지배하는 것은 출력 토큰이다. D8 이 그것을 측정했다 — **시간 ≈ 출력토큰 ÷ 55** 로 거의 일정하다(12건 중 11건이 45~59 tok/s). 6.9KB 문서에 출력 30,224 토큰, 21.9KB 에 50,620 토큰이 나왔다. 위키 2~3장이면 5,000 토큰 수준이어야 하는데 그보다 한 자리 크다.

따라서 10분 안에 들어가려면 줄여야 하는 것은 **조회 횟수가 아니라 출력 토큰**이다. 창구 호출은 수백 밀리초 단위라 수십 번 늘어도 예산에 영향이 없다.

그래도 조회 횟수 상한은 **AI 쪽 손잡이로 남긴다** — 백엔드에 요청할 것이 아니라 우리가 거는 제한이다. 목적은 시간이 아니라 두 가지다.

- 에이전트가 같은 것을 반복 조회하며 맴도는 것을 끊는다 (D9 의 `10-onboarding` 이 그 사례 — 724초에 툴 77회, 출력 589 토큰)
- 조회 결과가 문맥에 쌓이면 그것이 다음 턴의 입력이 되어 간접적으로 출력을 늘린다

숫자는 9.3 의 상한과 함께 실측해 정한다. **상한을 선언만 하고 세지 않으면 아무 효과가 없다** — 창구 클라이언트의 호출 지점 한 곳에서 세고, 초과하면 `failureStage = agent_error` 로 중단한다. 검색·본문·관계·카테고리·파싱본 호출을 모두 센다.

### 9.6 창구 7개를 어디서 쓰나

창구를 만들고 부르지 않으면 계약만 늘어난다. 각 창구가 에이전트 동작의 어디에 붙는지 적는다.

| 창구 | 붙는 곳 |
| --- | --- |
| 목록 | 하이드레이션 — 카탈로그를 채운다 |
| 목차 | 하이드레이션 — `index.md` 를 채운다 |
| 본문 | `get()` 첫 접근에 지연 적재 |
| 검색 | `search_chunks` 의 라이브 절반 |
| **관계** | **`references` 툴과 제거·병합 전 영향 범위 확인** |
| **카테고리** | **하이드레이션 — 현재 카테고리 맵. FR-WIKI-014 의 생성·병합 판단 근거** |
| **원본문서 파싱본** | **`lint` 의 각주 인용 대조 (FR-WIKI-001 · NFR-AI-002)** |

굵게 표시한 셋이 앞 판본에서 빠져 있었다. 관계 창구는 3.4 가 *"역방향을 모르면 병합할 때 남의 링크를 끊는다"* 로 필요성을 논증했는데 정작 쓰는 곳을 적지 않았다.

**지연 적재와 관계 창구의 관계를 분명히 한다.** 본문을 당긴 페이지만 내부 인용 그래프에 들어간다. 즉 `get_backlinks` 는 "지금까지 읽은 범위 안의 역링크"만 안다. 제거·병합처럼 **범위 전체의 역링크가 필요한 판단에는 관계 창구를 쓴다** — 내부 그래프로 대신하면 안 읽은 페이지의 링크를 놓친다.
