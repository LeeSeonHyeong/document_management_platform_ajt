# 시연 데이터 준비 — 격리 환경 구축과 QA 잔재 정제

작성일 2026-08-08. 대상: **로컬 환경만**. prod·develop 서버와 코드는 건드리지 않는다.

발표 시연에 앞서 QA 흔적이 섞인 데이터를 정제하고, 위키 에이전트가 잘 동작하는
시연용 데이터셋을 만든다. 이 문서는 **1단계(환경 구축과 정제)**만 다룬다.
2단계(문서 코퍼스 확장)는 별도 설계로 넘긴다.

## 배경

지금 데이터에는 심사자 3명의 QA 흔적이 남아 있다. 시연에서 보여줄 화면에
`[샘플] 취업규칙 위키` 같은 껍데기와 테스트 계정이 그대로 노출된다.

시연의 논점은 **"단순 RAG와 LLM Wiki가 무엇이 다른가"**다. 따라서 데이터는
RAG가 못 하는 것을 드러내야 한다 — 흩어진 문서의 통합, 개정·모순의 정리,
각주로 남는 근거, 링크를 통한 개념 탐색.

## 목표와 비목표

**목표**
- 기존 데이터를 잃지 않으면서 시연 전용 환경을 만든다
- 확정된 QA 잔재를 제거한다
- 조직을 시연에 맞는 형태(3부서 × 4사원 + 관리자, 총관리자 1)로 맞춘다
- 정합성 점검을 스크립트로 만들어 2단계에서도 쓴다

**비목표**
- 코드 수정 — 링크 생성 로직·주소 체계는 이번에 손대지 않는다
- prod 반영 — 시연은 로컬에서 한다
- 문서 코퍼스 확장 — 2단계
- 원본 문서 출처 결정 (PostHog 한국어판 등) — 별도 논의

## 조사 결과

### 링크가 적은 이유는 데이터가 아니라 구조다

에이전트에게 주어진 위키 주소는 `pages/{키}.md` 형식이다(`tools/guide.py:34`).
**키는 페이지가 생겨야 존재하므로, 아직 만들지 않은 페이지는 가리킬 주소가 없다.**
정방향 참조는 쓸 수 없고, 이미 존재하는 페이지를 가리키는 역방향만 가능하다.

`build_edges`(`tools/references.py`)는 해석 못 한 링크를 버리고 나중에 복구하지
않는다. 이 동작은 prod 이미지(`bf84ece`)와 develop HEAD(`c3e90ee`) 사이에
`references.py`·`vaultfs/`·`changes.py` 변경이 하나도 없어 **동일하다.**
2026-08-03 forward-ref 설계 문서가 다루는 문제이며, 아직 미착수다.

따라서 링크 밀도는 **적재 순서**가 결정한다. 실측이 이를 뒷받침한다.

| | prod (`ajt_prod`) | 로컬 (`ajt`) |
| --- | --- | --- |
| 위키 | 8 | 18 |
| 위키 본문의 아웃링크 | 3 | 12 |
| `scope_version` (ALL) | 9 | 33 |

로컬은 여러 작업으로 나눠 적재해 뒤 페이지가 앞 페이지를 참조할 수 있었다.
prod은 몰아서 넣어 링크가 거의 붙지 않았다.

### 로컬 `ajt` 본문 품질은 시연에 쓸 만하다

실제 위키 16건이 1.5K~13K, 각주 2~34개를 갖는다. 예를 들어
「연차유급휴가 규정」은 규정 원문(`연차휴가 운영지침.md`)과 개정 공문
(`03-service-rules-amendment.md`) 두 문서를 통합해 연차 **15일 → 20일** 개정을
표로 대비하고, 경과규정(시행일 전 확정분은 종전 기준)까지 각주와 함께 정리한다.

**이 개정 사례가 RAG 대비를 보여주는 소재다.** RAG에 "연차가 며칠이냐"고 물으면
15일 조각과 20일 조각이 모순인 채 함께 나온다. 위키는 개정 결과와 시행일,
경과 조치를 근거 각주와 함께 하나의 답으로 제시한다.

### 확인된 QA 잔재

| 대상 | 근거 |
| --- | --- |
| 위키 14·15 `[샘플]` | 77~93바이트 껍데기. 경로가 `pages/14.md`로 해시가 아님 = 손으로 넣은 시드 |
| 파일 `pages/1·2·6·7.md` | DB에 대응 행이 없는 고아 파일 |
| 계정 신입일·신입이·거절일·거절이 | 가입 승인 흐름 테스트용 |
| 관리자 지시 문서 49·56·60·62 | 어느 위키 각주도 인용하지 않음 (무변경 응답 잔재로 추정) |

관리자 지시 45·57·63은 **남긴다.** 위키 10·20의 각주가 이들을 인용하고 있고,
지시 내용도 정상 업무 지시다. 문서 56은 파일명이 `w24`인데 참조가 `[20]`이라
과거 수동 교정(2026-08-07 재설계 문서 기록)의 흔적이다.

## 설계

### ① 격리 — 지우지 않고 새로 판다

| | 새로 만드는 것 | 손대지 않는 것 |
| --- | --- | --- |
| DB | `ajt_demo` | `ajt`(축적 18위키), `ajt_prod`(prod 사본) |
| 파일 | `build/ajt-demo-documents` | `build/ajt-documents`(18M) |

로컬 `ajt`와 `build/ajt-documents`를 각각 복제한 뒤, 복제본에서만 작업한다.
백엔드는 `SPRING_DATASOURCE_URL`·`DOCUMENT_STORAGE_ROOT` 두 환경변수로 이쪽을
가리키게 띄운다.

**원본에 대한 삭제 작업이 0건이다.** 되돌리기는 `DROP DATABASE ajt_demo`와
디렉터리 삭제뿐이며, 몇 번이든 처음부터 다시 할 수 있다.

### ② 잔재 제거

위 표의 네 항목을 `ajt_demo`와 그 파일 루트에서만 제거한다.
DB 행과 파일을 **항상 짝으로** 지운다. 관리자 지시 4건은 문서 행·파일과 함께
`wiki.document_refs`의 해당 항목도 제거해 양방향을 맞춘다.

### ③ 조직 재구성

목표는 **총관리자 1 + 3부서 × (관리자 1 + 사원 4) = 16명**이다.

부서는 **개발부(D1)·인사부(D4)·디자인부(D3)**를 쓰고 기획부(D2)는 제외한다.
D2 스코프는 `scope_version`이 0으로 한 번도 쓰인 적이 없어 빼도 남는 것이 없다.

가입 승인 흐름 테스트 계정(신입일·신입이·거절일·거절이)은 **제외한다.** 시연
시나리오에 가입 승인이 들어가면 그때 다시 넣는다 — 계정 4행을 추가하는 일이라
되돌리기 비용이 거의 없다.

부족한 사원은 SQL로 추가한다. `department`·`member`·`wiki_scope`·
`document_category`는 조직 데이터이므로 직접 입력을 허용한다.

최고관리자(9)는 지금 개발부 소속이라, 전용 부서(`department_id = 6`)로 옮긴다. 개발부
인원 집계에 총관리자가 섞이지 않게 하기 위해서다.

### ④ 링크 확보 — 순차 적재

2단계에서 문서를 추가할 때 **토대 문서를 먼저 올려 위키를 만들고, 그것을
참조할 문서를 나중에 올린다.** 한 작업에 몰아넣으면 뒤에 생길 페이지를 가리킬
주소가 없어 링크가 붙지 않는다.

### ⑤ 정합성 점검 스크립트

`check.sh`는 **검사 7종**(문제가 있으면 실패로 잡아 종료코드 1)과 **지표 6개**(정보로만
보여주고 실패로 잡지 않음)로 나뉜다. 모두 실제로 발견된 사례에서 나온 항목이다.

**검사 (실패 조건)**

| 검사 | 나온 사례 |
| --- | --- |
| `wiki.document_refs`가 가리키는 문서가 실재한다 | 위키가 지워진 문서를 계속 인용하는 사고 |
| 문서→위키 정참조 양방향 일치 (`document_wiki_refs`가 가리키는 위키도 그 문서를 되가리킨다) | prod 문서 18 (한쪽만 참조) |
| 문서→위키 역방향 dangling (문서가 가리키는 위키가 실재한다) | `cleanup.sh`가 위키를 지운 뒤 그 위키를 가리키던 문서 참조가 남는 사고. 검사 2는 `INNER JOIN`이라 위키가 이미 삭제되면 행 자체가 사라져 못 잡는다 — `LEFT JOIN`으로 봐야 한다 |
| 중복 업로드 (같은 스코프·파일명·`file_size`가 둘 이상) | prod 문서 34·35. `file_size`까지 묶는 이유는 같은 파일명이라도 크기가 다르면(예: `03-service-rules-amendment.md`의 간이판·상세판) 서로 다른 근거이기 때문 |
| `document_refs`가 빈 위키 (근거 없는 위키) | prod 위키 13이 될 뻔한 사례 |
| DB에 행이 없는 고아 페이지 파일 | 로컬 `pages/1·2·6·7.md`, prod `D8` 잔해 |
| 각주가 인용하는 문서가 실재한다 (파일명 기준) | 중복 사본을 지울 때 남은 문서에 그 파일명이 하나도 안 남아 각주 근거가 끊기는 사고 |

**지표 (정보성 — 실패로 잡지 않음)**

| 지표 | 비고 |
| --- | --- |
| 위키 수 | |
| 문서 수 | |
| 계정 수 | |
| 위키 본문의 아웃링크 수 | 2단계 목표 지표 |
| 고아 문서 수 (`document_wiki_refs`가 빈 문서) | 검사가 아니라 지표다 — 문서를 올리고 아직 변환 전이면 정상적으로 고아이기 때문 |
| 끊긴 `ai_job` 참조 (`ai_job.document_ids`가 이미 삭제된 문서를 가리키는 건수) | 과거 작업 이력이라 결함인지 판단이 애매해 지표로만 둔다 |

## 작업 규칙

1. **DB와 파일은 항상 같이 간다.** 한쪽만 손대지 않는다
2. **위키는 손으로 만들지 않는다.** 반드시 에이전트를 통해 만든다 — 직접 넣으면
   `content_hash`·`wiki_search_chunk`·참조 그래프가 어긋나고, 시연 중 에이전트가
   그 위키를 건드리는 순간 드러난다
3. **SQL 직접 입력은 조직 데이터에 한한다** (`department`·`member`·`wiki_scope`·
   `document_category`)

## 되돌리기

```sql
DROP DATABASE ajt_demo;
```
```bash
rm -rf backend/build/ajt-demo-documents
```

원본 `ajt`·`ajt_prod`·`build/ajt-documents`는 어느 단계에서도 수정하지 않는다.

## 무엇을 쓰고 무엇을 안 쓰나

**베이스는 로컬 `ajt` 하나다.** 시연 데이터의 위키·문서는 전부 여기서 온다.

**prod QA 데이터(`ajt_prod`)는 시연 데이터에 넣지 않는다.** 조사에만 썼다 —
거기서 나온 사고 유형(카테고리 오분류, 양방향 참조 불일치, 중복 업로드, 고아
페이지 파일)이 그대로 ⑤의 점검 항목이 됐다. 사본은 대조군으로 보관한다.

두 데이터를 합치지 않는다. 합치면 문서 ID가 충돌하고 각주가 가리키는 파일명이
어긋난다.
