# GMS 요청 크기벽 대응 — 문맥 압축 (요약 미들웨어 재설정)

- 상태: 구현 완료 (단위 테스트 `tests/runtime/test_compaction.py`. 실기동 검증은 아직)
- 날짜: 2026-08-02
- 범위: `ai/` (agent_runtime — deepagents 위키 에이전트)

## 문제

긴 병합 잡이 GMS 게이트웨이의 **요청 크기 한도(~42K 토큰)** 를 넘겨 죽는다.

- 실측(job 7, 01.docx 병합): 문맥이 턴마다 누적 `5.3K → … → 42.3K` 로 자라다가, 다음 콜에서
  GMS가 **400 `[GMS 에러] Model not found in request for domain api.anthropic.com`** 반환 → 변환 500 실패.
- 한국어 ~1자=1토큰(count_tokens 실측 0.85~1.02). 42K 토큰 ≈ 한국어 ~4.4만자.
- 원인: **새 문서 크기가 아니라 병합 중 누적되는 대화 이력·도구결과**가 지배. 작은 문서(679자)도
  기존 위키 여러 개와 병합하면 20턴 만에 벽에 닿는다.
- `max_retries=0` + GMS 400은 재시도 대상이 아니므로, 한 번 벽에 닿으면 잡 전체가 죽고
  그때까지 쓴 크레딧이 전액 낭비된다(이번에 2,404 크레딧 손실).

## 왜 지금까지 방치됐나

`create_deep_agent` 은 **기본으로 요약 미들웨어를 이미 넣는다**(`create_summarization_middleware`).
그러나 기본 트리거가 **`("fraction", 0.85)` 또는 `("tokens", 170000)`** — GMS 42K 벽보다 4~10배
높아 **우리가 벽에서 죽을 때까지 한 번도 안 터진다.** 내장 오버플로 폴백도 `ContextOverflowError`
(Anthropic 창 초과)만 잡고, 우리의 GMS `BadRequestError`(400)는 못 잡는다.

## 설계

내장 요약 미들웨어를 **낮은 트리거로 재설정**해, 문맥이 42K 벽에 닿기 전에 압축한다.

### 동작 (문서 `wrap_model_call` 기준)
매 모델 콜 직전에 누적 문맥(시스템+도구+이력) 토큰을 세고, 트리거 이상이면 오래된 메시지를
요약(LLM 1콜)해 몇 줄로 줄이고 최근 메시지는 보존 → 총량이 뚝 떨어진 채로 콜을 보낸다.

### 설정값 (근거)
| 파라미터 | 값 | 근거 |
| --- | --- | --- |
| `trigger` | `("tokens", 34000)` | 42K 벽까지 **최대 1턴 증가폭(실측 ~4.6K)** 여유. 34+4.6=38.6<42. 너무 낮으면(28K) 1~2턴마다 압축 → 요약 콜 남발 |
| `keep` | `("messages", 6)` | deepagents 기본과 동일. 최근 작업맥락(편집 중 위키·직전 도구결과) 보존 |
| 요약 모델 | **haiku** (`anthropic:claude-haiku-4-5-20251001`) | 요약 콜 자체를 싸게. 요약할 양 ~22K 토큰이라 haiku로 충분 |
| `summary_prompt` | 커스텀 | 병합 핵심 보존 지시 — **모순 수치(예: 연차 15↔20)·편집한 페이지 주소·미해결 항목** |
| `backend` | 에이전트의 파일시스템 backend | 원본 이력 오프로드 (deepagents 규약) |

### 제약 (검증 대상)
- **요약 콜도 GMS를 타므로 42K 미만이어야 한다.** 요약할 양 ≈ (트리거 − keep) ≈ ~22K < 42K → 충족.
- 본체 콜 최대 ≈ 트리거 + 1턴증가폭 = 38.6K < 42K → 충족.

### 배선 (문서 `_apply_custom_middleware` 기준)
`middleware=[...]` 로 넘긴 커스텀 미들웨어는 **이름 기준 병합** — 같은 `.name` 이면 기본을 교체,
아니면 append. append 되더라도 커스텀(34K)이 기본(170K)보다 먼저 터지므로 기능상 안전.
`arun` 의 `create_deep_agent` 에 커스텀 `SummarizationMiddleware` 를 추가한다.

### floor 와 병행
시간 floor(600초, 별도 커밋 완료)와 함께여야 긴 병합이 실제로 완주한다 — floor는 타임아웃,
압축은 크기벽. 서로 다른 벽이다.

   구성되는지 단위 테스트. 토큰 카운트로 "34K에서 압축 발동" 로직 확인.

## 추가 결정 (2026-08-05) — 트리거를 프로바이더별로 가른다

직접 Anthropic 키가 들어와 위 "범위 밖"의 캐싱 항목이 해소됐다. 표준 스토해드 호출로
프롬프트 캐싱이 실제로 붙는 것을 확인했다 — 1회차 생성 5402 토큰, 2회차 읽기 5402 토큰.

그러면 34K 고정이 **직접 API 에서는 손해**가 된다. 이유가 둘이다.

1. 벽이 없다. 직접 API 는 컨텍스트 1M 이라 34K 는 필요보다 30배 가까이 좁다 — 압축이 불필요하게
   자주 터지고, 매번 요약 LLM 콜이 하나 더 붙는다.
2. **압축과 캐싱이 서로 싸운다.** 압축은 이력을 다시 쓴다 → 프롬프트 접두사가 바뀐다 →
   캐시가 통째로 무효화된다(캐싱은 접두사 일치). 캐시 읽기 단가는 입력의 0.1배이므로,
   벽이 없다면 이력을 길게 들고 가는 편이 싸다.

### 결정: `base_url` 로 자동 분기 (환경변수 아님)

`compaction_trigger_for(base_url)` 가 정한다 (`agent_runtime/deep_agents.py`).

| base_url | 트리거 | 근거 |
| --- | --- | --- |
| 빈 값 (SDK 기본 엔드포인트) | 170K | 게이트웨이는 `base_url` 을 반드시 주므로 빈 값 = 직접 API |
| 호스트가 `UNCAPPED_API_HOSTS` 에 있음 | 170K | 벽이 없다고 **아는** 곳 |
| 그 밖 전부 | 34K | 모르면 벽이 있다고 본다 |

**기본값이 안전한 쪽이다.** 잘못 좁히면 요약 콜을 몇 번 더 도는 낭비로 끝나지만, 잘못 넓히면
벽에서 잡이 죽고 그때까지 쓴 비용을 전액 잃는다(job 7 에서 2,404 크레딧). 지금 직접 키는
일시적이라 게이트웨이로 되돌아갈 수 있는데, 자동 분기는 **사람이 설정을 되돌리는 것을 잊어도**
안전하다 — 환경변수 방식을 택하지 않은 이유가 이것이다.

접미사 일치로 넓혀지지 않도록 호스트를 파싱해 정확히 비교한다
(`api.anthropic.com.evil.example` 는 34K). 판단 결과는 `logger.info` 로 남긴다.

### 남은 것

- **캐시 TTL(5분 vs 1시간)은 손대지 않았다.** 1시간은 쓰기 단가가 2배라 같은 접두사를 3회
  이상 읽어야 이득이고, 잡 하나 안에서 그게 성립하는지 재지 않았다. 기본(5분)을 유지한다.
- 직접 API 에서 170K 트리거로 긴 병합을 완주시킨 실측이 없다. 게이트웨이 34K 경로만 실측됐다.
