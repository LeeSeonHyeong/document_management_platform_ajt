# 2단계 엔드포인트를 에이전트 하나로 합친다 — 설계

작성 2026-07-31. 백엔드 제의로 시작한 설계다. **같은 날 저녁 개정** — §6.4·§6.6 이 확정
요구사항 두 개와 어긋난 것을 고쳤다 (§6.4.1·§6.6). 계약 버전은 1.7.0 이 아니라 **1.8.0** 이다
(§12).

## 1. 무엇을 바꾸나

지금 위키 변환과 챗봇은 **각각 두 번 호출**된다. 첫 호출에서 무엇을 볼지 고르고, 백엔드가
그 결과의 본문을 읽어 두 번째 호출에 실어 보낸다.

첫 호출도 결국 LLM이 고르는 것이므로 나눌 이유가 없다. **한 번 호출로 합치고, 무엇을 볼지는
에이전트가 도구를 써서 직접 정한다.**

| 지금 | 바뀐 뒤 |
| --- | --- |
| `wiki-context-selections` + `wiki-transformations` | `wiki-transformations` |
| `answer-context-selections` + `answers` | `answers` |
| `wiki-edits` | 그대로 (조회 방식만 통일) |
| `source-parses` | 손대지 않는다 |

AI가 제공하는 엔드포인트가 5개에서 3개로 줄어든다.

**기능별로 하나다.** 위키와 챗봇을 한 주소에 합치지는 않는다. 둘은 입력·출력·걸리는 시간이
다르고 하나는 쓰기, 하나는 읽기다. 한 주소에 넣으면 요청 안에서 다시 갈라야 한다.

**없어지는 엔드포인트는 바로 지운다.** 남겨두지 않는다. 백엔드가 새 형태로 부르는 것과 같은
시점에 배포해야 한다.

### 1.1 두 번에 나눠 한다

| 단계 | 무엇 | 선행 |
| --- | --- | --- |
| **이 문서가 다루는 것** | 챗봇 (`answer-context-selections` + `answers` → `answers`) | 없음 |
| 다음 | 위키 변환·관리자 수정 | S15P11B106-151 · 152 · 154 |

챗봇은 선행 작업이 없다 — 위키 편집용 저장 계층을 쓰지 않기 때문이다 (§2.1, §6.1). 위키
변환은 그 계층을 쓰므로 세 티켓을 기다린다.

**§4.1·§4.3·§5 의 위키 부분은 다음 단계의 밑그림이다.** 이번에 구현하지 않는다.

## 2. 백엔드 쪽은 이미 다 있다

**조회 API 8개가 이미 만들어져 있다.** S15P11B106-150 에서 만들었고 권한 검사까지 붙어 있다
(`InternalWikiQueryController`).

```
GET /internal/v1/wiki-search                      본문 검색
GET /internal/v1/wiki-pages                       목록
GET /internal/v1/wikis/{wikiId}/content           본문
GET /internal/v1/wikis/{wikiId}/relations         참조 관계
GET /internal/v1/wiki-spaces/{scopeKey}/index      목차
GET /internal/v1/wiki-spaces/{scopeKey}/categories 카테고리
GET /internal/v1/wiki-spaces/{scopeKey}/relations  범위 전체 참조 관계
GET /internal/v1/documents/{documentId}/parsed     원본문서 파싱본
```

못 쓰고 있던 이유는 백엔드가 아니라 **우리 쪽 배선이 없어서**다. MCP 서버가 별도 프로세스로
뜨는데 그 프로세스에 Spring 주소와 권한값을 넘기는 경로가 없다 (S15P11B106-152).

### 2.1 선행 작업 — 챗봇은 없고, 위키 변환에만 있다

처음에는 둘 다 S15P11B106-151·152 를 기다려야 한다고 보았다. **챗봇은 아니다.** 그 두 티켓은
**위키 편집용 저장 계층**(`FederatedVaultFS` · MCP 서버 프로세스)의 문제이고, 챗봇은 그 계층을
쓸 이유가 없다 — 쓰지 않으니 작업 공간도, 참조 그래프 동기화도, 스코프 격리도 필요 없다.

챗봇에 필요한 것은 **읽기 도구 몇 개**뿐이다. 그것을 런타임에 직접 붙이면(§6.1) 두 티켓이
선행이 아니게 된다.

| 무엇 | 151 (fan-out) | 152 (MCP 배선) | 154 (작업층 검색) |
| --- | --- | --- | --- |
| 챗봇 합치기 | 무관 | 무관 | 무관 |
| 위키 변환 합치기 | 필요 | 필요 | 필요 |

**그래서 챗봇을 먼저 한다.** 선행 작업이 없고, 쓰기가 없어 실패해도 위키가 망가지지 않는다.
위키 변환은 세 티켓이 끝난 뒤 별도로 한다.

## 3. 권한 — 이미 있는 것을 그대로 쓴다

백엔드는 요청마다 무작위 문자열(32바이트)을 발급하고, 거기에 **범위 · 범위 버전 · 만료
시각**을 묶어 메모리에 저장한다. AI가 조회할 때 그 문자열을 `X-Wiki-Capability` 헤더에
실으면, 백엔드가 저장해둔 것과 맞춰보고 범위가 다르거나 만료됐으면 거절한다
(`WikiCapabilityService`).

문자열 자체에는 아무 정보도 없다. AI 입장에서는 **뜻을 모르는 값**이고, 받아서 그대로
되돌려주기만 한다. 판단은 백엔드가 한다.

**위키 변환·수정은 이미 이렇게 돈다.** 범위가 하나이므로 그대로 쓴다.

**챗봇은 범위가 여러 개다.** 사용자가 전사 위키와 소속 부서 위키를 함께 볼 수 있다. 그래서
챗봇 요청에는 **범위마다 하나씩** 담는다. 백엔드는 이미 있는 발급 함수를 범위 수만큼 부르면
된다. 새 엔드포인트도, 새 개념도 없다.

### 3.1 이 방식이 안고 있는 문제 (이번 범위 밖)

- **서버를 재시작하면 발급한 값이 다 사라진다.** 진행 중인 작업의 조회가 전부 거절된다
- **서버를 여러 대로 늘리면 안 맞는다.** 발급한 서버와 조회를 받는 서버가 다르면 못 찾는다
- **큐 대기와 겹친다.** 쓰기를 큐로 직렬화하기로 백엔드와 합의했는데, 큐에서 대기하는 동안
  만료될 수 있다. 앞에 긴 작업이 밀려 있으면 자기 차례에 이미 만료다

작업 번호(`jobId`·`questionId`)로 판정하면 세 문제가 다 없어진다 — DB에 있으니 재시작에
안 죽고, 서버가 여러 대여도 맞고, 얼마를 기다려도 살아 있다. **다만 이번에는 하지 않는다.**
지금 방식이 돌아가고 검사도 붙어 있어서, 갈아치우면 백엔드 작업이 커진다. 별건으로 남긴다.

## 4. 요청·응답 계약

### 4.1 위키 변환

```
POST /internal/v1/wiki-transformations

남는 것   jobId · documentId · scopeKey · changeType · parsedMarkdown
          removedParsedMarkdown(제거·교체일 때)
          wikiCapability · scopeVersion  ← 선택 필드에서 필수로
빠지는 것 currentIndex · currentCategories · selectedWikis
```

`wikiCapability`·`scopeVersion` 은 계약 1.6.0 에 이미 선택 필드로 있다. 필수화만 하면 된다.

**응답은 그대로 둔다** — `summary` · `wikiChanges` · `categoryChanges` · `relationChanges` ·
`indexEntries`. 백엔드가 이미 받아 반영하는 모양이라 바꿀 이유가 없다.

### 4.2 챗봇

```
POST /internal/v1/answers

남는 것   questionId · conversationId · question · conversationMessages
바뀌는 것 wikiIndexes[] 각 행에 wikiCapability 를 더한다 (필수)
          (지금은 scopeKey + 목차 마크다운뿐. scopeVersion 은 넣지 않는다 — §7.1)
빠지는 것 questionType · selectedWikis · selectedSchedules
          scheduleSummaries — 일정은 도구로 조회한다 (§6.3)
```

**요청이 네 덩이로 끝난다** — 번호 둘, 질문, 이전 대화, 그리고 범위별 목차. 나머지는 전부
에이전트가 도구로 가져온다.

**허가값을 별도 배열로 두지 않고 `wikiIndexes` 행에 넣는다.** 두 배열로 나누면 한쪽에만 있는
범위가 생길 수 있고, 그 경우 에이전트가 목차는 읽었는데 본문은 못 읽는 상태가 된다. 한 행에
두면 그 어긋남이 애초에 불가능하다.

**허가값이 없으면 그 범위는 답변 근거가 되지 못한다.** 그래서 선택 필드로 두지 않는다 — 빠지면
위키 조회가 전부 실패하고 §6.4.1 의 「근거 없음」으로 나와 원인을 짐작하기 어렵다. 이 변경은
이미 엔드포인트를 삭제하는 비호환 변경이므로 「배포 전 호환」 논거도 성립하지 않는다.

**응답에 `questionType` 이 더해진다** — `answer` · `sources[]` · `questionType`.

지금 `questionType` 은 1단계 응답으로 나와 2단계 요청으로 되돌아가는 값이다. 합치면 요청에서
사라지고 **응답으로 자리를 옮긴다.** 백엔드가 `question` 테이블에 저장하는 값이라 없애지
않는다. 어떻게 정하는지는 §6.4 에 있다.

**`sources[]` 에 `title` 을 담는다.** 백엔드가 `answer_source.source_title`(`NOT NULL`)에 저장
한다. 장부가 제목을 갖고 있으므로 새로 조회할 것은 없다.

### 4.2.1 이전 대화에 상한을 건다

지금은 실려 온 이전 대화를 **통째로** 모델에 넘긴다. 상한이 없다. 설계 문서에는 12개·4천 자로
적혀 있는데 구현되지 않았다.

에이전트로 바꾸면 여기에 도구 결과까지 쌓인다. **이번에 상한을 실제로 넣는다** — 최근 12개
(6턴), 4천 자. 넘으면 오래된 것부터 버린다.

**요청을 거절하지 않는다.** 상한을 넘겨 보내는 것은 백엔드 잘못이 아니다 — 대화가 길어지면
당연히 넘는다. 우리가 조용히 자르고 최근 것으로 답한다.

### 4.3 위키 관리자 수정

엔드포인트 수는 그대로다(이미 하나다). 조회 방식만 통일한다 — `evidenceDocuments` 를 실어
보내는 대신 에이전트가 파싱본 조회 API로 직접 읽는다. `wikiCapability`·`scopeVersion` 필수화는
변환과 같다.

> **가정.** 「다 합치기」에 관리자 수정이 포함된다고 보았다. 아니면 이 절을 빼면 된다 —
> 다른 절에 영향이 없다.

## 5. 에이전트가 하는 일

**위키 변환**: 목차·카테고리를 조회해 현재 상태를 파악하고, 검색으로 관련 페이지를 찾아
필요한 것만 읽고, 작업 공간에 쓰고, `lint` 를 통과시킨다. 지금과 같다 — 앞에 붙어 있던
힌트가 없어지는 것뿐이다.

**챗봇**: 질문 맥락을 보고 유형을 판단한다. 위키 질문이면 실려 온 목차에서 관련 페이지를 골라
본문을 조회해 읽고, 목차에 없으면 검색한다. 일정 질문이면 기간을 정해 목록을 조회하고 필요한
것의 내용을 읽는다. 그다음 답변과 「쓴 자료」 신고를 낸다.

## 6. 챗봇 에이전트 설계

### 6.1 MCP 를 쓰지 않는다 — 도구를 런타임에 직접 붙인다

**이것이 이 설계의 핵심 결정이다.** 세 가지가 여기서 한꺼번에 풀린다.

지금 위키 에이전트는 MCP 서버를 별도 프로세스로 띄우고 그 안의 도구를 쓴다. 그 구조가
필요한 이유는 **쓰기** 때문이다 — 작업 공간, 참조 그래프, 청크 색인, 스코프 격리(프로세스
1개 = 스코프 1개). 챗봇은 그중 아무것도 필요 없다.

배포 런타임은 도구를 목록으로 받는다 (`create_deep_agent(model=..., tools=...)`). 지금 그
목록을 MCP 로 얻고 있을 뿐이다. **챗봇에서는 파이썬 함수 몇 개를 그 자리에 그대로 넣는다.**

무엇이 풀리나 — **두 가지다.**

| 문제 | 어떻게 풀리나 |
| --- | --- |
| S15P11B106-152 (별도 프로세스에 권한값 전달) | **선행이 아니게 된다.** 배포 런타임도 MCP 서버를 별도 프로세스로 띄운다(`sys.executable -m wiki_mcp.local_server`). 도구를 직접 붙이면 그 경계가 없으니 넘길 것이 없다 |
| S15P11B106-151 (본문 하나 읽으면 링크 전체를 당긴다) · 154 | **일어나지 않는다.** 둘 다 편집용 저장 계층(`FederatedVaultFS`)의 동작이다. 챗봇 도구는 조회 한 번으로 끝난다 |

> **도구 지연 로딩은 여기 근거가 아니다.** 그것은 `claude-code` 명령줄 도구만의 문제이고,
> 배포 런타임은 도구 목록을 미리 받아 통째로 넘긴다. **이 설계는 배포 런타임을 기준으로 한다**
> — 명령줄 도구는 모델 키가 없어 임시로 쓰는 시험용이다.

**대가**: 명령줄 도구는 도구를 MCP 로만 받으므로 챗봇을 그쪽에서 돌릴 수 없다. 기준 런타임이
아니므로 설계상 문제는 아니지만, **로컬 확인 수단이 없어진다** (§10).

### 6.1.1 어느 런타임·어느 모델로 도는가

**배포는 `deepagents` 런타임이다.** 모델 제공자는 셋 중 하나를 쓴다 — GMS 게이트웨이,
OpenAI, Anthropic. 제공자는 모델 문자열의 접두사로 고르고 자격증명도 그 접두사로 갈린다
(`settings.credentials_for`).

**지금 실제로 쓸 수 있는 것은 OpenAI 뿐이다.**

| 제공자 | 지금 상태 |
| --- | --- |
| OpenAI | **쓸 수 있다.** 의존성도 이미 들어가 있다 (`langchain-openai`) |
| GMS 게이트웨이 | 토큰이 부족하다 |
| Anthropic 직결 | 키가 없고 결제도 안 되어 있다 |

`claude-code` 명령줄 도구는 **로컬 시험용이다.** 지침과 도구 사용이 어느 정도 먹는지 보려고
임시로 쓰는 것이고 배포에는 쓰지 않는다. 그래서 그쪽의 특성(도구 지연 로딩 등)을 설계 근거로
삼지 않는다.

**확인했다 (2026-07-31).** `deepagents` + `openai:gpt-4o-mini` 로 단발 호출이 돈다 — 1.8초,
입력 18 · 출력 2 토큰.

**그 확인에서 막을 결함이 하나 나왔다. 이 작업에 포함한다.**

단발 호출용 모델 기본값이 Anthropic 으로 박혀 있다 (`DEFAULT_TIER_MODELS`). 에이전트 모델을
`openai:...` 로 지정해도 그 호출은 Anthropic 으로 가고, 키가 없으니 실패한다. 오류는
「인증 방법을 못 찾았다」로 나와 원인을 짐작하기 어렵다.

세 곳(`AI_MODEL`·`AI_MODEL_FAST`·`AI_MODEL_QUALITY`)을 다 지정하면 지나간다. 그러나 **하나만
지정하고 배포하면 첫 요청에서 실패한다.** 기본값을 에이전트 모델과 같은 제공자로 맞추거나,
어긋나면 기동 시점에 막는다. 기동 시점에 막는 선례가 이미 있다 (`serve.py` 의 명령줄 도구
부재 검사).

**딸려오는 것 두 개.**

- **지침을 OpenAI 기준으로 조율해야 한다.** 위키 지침은 Claude 계열로 맞춰 온 것이다. 같은
  문장이 다른 모델에서 같게 먹지 않는다. §6.5 의 챗봇 지침은 처음부터 OpenAI 로 조율한다
- **기존 측정과 비교할 수 없다.** 지금까지의 챗봇·위키 측정은 Claude 계열 값이다. 새 측정은
  따로 세운다

### 6.2 도구 목록

다섯 개다. 모두 Spring 을 한 번 부르고 끝난다 — 캐시도, 색인도, 작업 공간도 없다.

| 도구 | 부르는 곳 | 상한 |
| --- | --- | --- |
| 위키 검색 | `GET /internal/v1/wiki-search` | 한 번에 20건 |
| 위키 본문 | `GET /internal/v1/wikis/{wikiId}/content` | 한 번에 1장 |
| 위키 목차 | `GET /internal/v1/wiki-spaces/{scopeKey}/index` | 범위 1개 |
| 일정 목록 | **신설 필요** (기간으로 조회) | 한 번에 50건 |
| 일정 상세 | **신설 필요** (`scheduleId` 로 조회) | 한 번에 1건 |

**상한을 넘으면 자르고, 잘랐다는 사실을 응답에 적는다.** 모르면 에이전트가 「이게 전부다」로
단정한다. 위키 검색에는 이미 같은 상한이 있다 (`tools/helpers.MAX_SEARCH`).

**위키 검색을 도구로 두는 이유**: 목차를 요청에 실어 보내지만, 목차에 잘 안 적힌 페이지는
검색으로 찾을 수 있다. §8-1 의 「목차가 천장이다」를 이것으로 완화한다.

### 6.3 일정은 도구로만 본다 — 요청에 싣지 않는다

일정 목록도 도구로 조회하므로 **요청에서 `scheduleSummaries` 가 사라진다.** 기간 문제도
같이 사라진다 — 에이전트가 필요한 기간을 정해서 물어보면 된다.

목록 도구는 제목·시각·대상만 돌려준다. 본문은 상세 도구로 따로 읽는다. 위키에서 목차를 보고
본문을 읽는 것과 같은 모양이다.

### 6.4 응답 세 조각을 어떻게 만드나 — 모델 말을 검사한다

응답은 `answer` · `sources` · `questionType` 이다. **모델에게 셋 다 받되, 출처는 우리가 가진
사실로 검사한다.**

| 조각 | 어디서 오나 |
| --- | --- |
| `answer` | 에이전트의 답변 글 |
| `sources` | 모델이 「이걸 썼다」고 신고한 것 **∩ 도구가 실제로 읽은 것** |
| `questionType` | **모델이 질문 맥락을 보고 판단한 것** (FR-QNA-002) |

**출처를 지어낼 수 없다.** 모델이 「취업 규칙에 따르면」이라고 써도 그 페이지를 읽지 않았으면
장부에 없으므로 교집합에서 빠진다. 읽은 기록이 화이트리스트다.

**읽었지만 안 쓴 것도 안 섞인다.** 위키 3장을 읽고 1장으로 답했으면 출처는 1장이다. 이것이
「읽은 것 전부」와 다른 점이다.

`title` 은 장부가 가진 것을 쓴다. 백엔드가 `answer_source.source_title`(`NOT NULL`)에 저장하므로
빠뜨리면 반영이 깨진다.

**신고가 없으면 읽은 것 전부로 떨어진다.** 모델이 신고를 빼먹었을 때 출처를 0개로 만드는 것보다
과다 포함이 낫다.

#### 6.4.1 근거를 못 찾았을 때 — 실패가 아니다

처음에는 「아무것도 읽지 않았으면 실패」로 정했다. **그것은 FR-QNA-007 위반이다** — 「접근 가능한
근거를 찾지 못하면 정보가 부족함을 안내해야 한다. 추측으로 답변을 생성하지 않는다.」 실패로
내면 사용자에게 「처리 중 문제가 생겼습니다」가 나가고, 지침의 「모르면 모른다고 한다」와도
정면으로 부딪친다.

**둘을 가른다.** 판단 근거는 이미 손에 있다 — `RunResult.tool_calls`.

| 상황 | 무엇을 내나 |
| --- | --- |
| 검색·목록을 불렀는데 읽을 것이 없었다 | **200.** `sources` 빈 배열, `answer` 는 정보 부족 안내 |
| 도구를 아예 부르지 않았다 | **500 `NO_WIKI_OR_SCHEDULE_WAS_READ`.** 찾아보지도 않은 것은 고장이다 |

앞쪽에서도 `questionType` 은 나온다 — 모델이 판단하므로 읽은 것과 무관하다.

> `questionType` 을 「읽은 자료의 종류」로 정하던 첫 설계는 **FR-QNA-002 위반**이었다 — 그 조항은
> 「질문 맥락을 보고 판단」을 요구한다. 결과로 정하면 일정 질문을 위키 공지로 답했을 때 유형이
> `wiki` 로 뒤집히고, 2026-07-29 측정의 분류 정확도 8/8 과도 비교가 끊긴다.

### 6.5 챗봇 지침을 새로 쓴다

**지금 챗봇에는 지침이 없다.** 단발 호출 두 번이라 프롬프트뿐이다. 에이전트로 바꾸면 위키
에이전트의 `guide` 에 해당하는 문서가 필요하다.

들어가야 하는 것:

- **먼저 목차를 본다.** 요청에 실려 있다. 위키 질문인지 일정 질문인지 둘 다인지 판단한다
- **목차에서 못 찾으면 검색한다.** 목차는 요약이라 빠진 것이 있을 수 있다
- **읽은 것에만 근거해 답한다.** 목차의 제목만 보고 내용을 추측하지 않는다
- **모르면 모른다고 한다.** 위키에 없는 것을 일반 지식으로 답하지 않는다 (§6.4.1 — 이것이
  정상 응답이다)
- **일정은 기간을 정해 조회한다.** 「다음」은 오늘 이후, 「지난」은 오늘 이전으로 잡는다
- **답변에 쓴 자료를 신고한다.** 읽은 것 중 실제로 근거가 된 것만 (§6.4)

**오늘 날짜를 지시문에 싣는다.** 모델은 오늘이 언제인지 모른다 — 훈련 시점 날짜로 조회한다.
`list_schedules` 가 기간을 필수로 받으므로 이것이 빠지면 일정 질문이 조용히 다 틀린다. 사용자
감각과 맞춰야 하므로 KST 기준으로 준다.

위치는 위키 지침과 나란히 둔다 — 두 런타임이 같은 사본을 읽어야 프롬프트 차이가 하네스
차이로 오해되지 않는다. 위키 지침이 그 이유로 도구가 되었다.

**분량이 이 작업에서 가장 큰 몫일 수 있다.** 위키 지침이 그랬다.

### 6.6 상한은 턴 수로 건다 — 사용자가 기다리는 시간이 천장이다

**주 장치는 턴 수다.** 몇 번 도는지를 묶으면 시간과 비용이 같이 묶이고, 시계로 재는 것보다
결과가 일정하다.

챗봇이 필요한 것은 이 정도다 — 목차 한 번, 검색 한두 번, 본문 두세 장, 답변. **턴 상한 4~5,
시간 상한 25초로 시작한다.** 위키 변환은 같은 장치를 훨씬 큰 값으로 쓴다.

**처음에 8턴·60초로 잡았다가 내렸다.** 지금 챗봇이 두 호출 합쳐 10초쯤인데, 구현대로면
`asyncio.wait_for(timeout+5)` 가 전체를 65초에서 자른다. 채팅에서 65초 침묵은 사용자가 창을
닫는다. 그리고 그 구조에서는 **시간이 주 장치가 되어** 턴 상한이 무의미해진다 — 8턴이면 정상
실행이 시간 상한에 먼저 닿기 때문이다. 25초·4~5턴은 둘이 대략 같이 걸리는 값이다.

상한에 걸리면 **그때까지 읽은 것으로 답하지 않는다.** 실패로 처리한다 — 반쯤 읽고 만든 답변은
근거가 빠져 있다.

**턴 상한 도달은 이름으로 구분되어야 한다.** `recursion_limit` 으로만 걸면 `GraphRecursionError`
가 나고 그것이 일반 예외로 잡혀 `MODEL_CALL_FAILED` 로 나간다 — `AGENT_TURN_LIMIT_REACHED` 를
계약에 올려놓고 한 번도 내지 않게 된다. 설치된 langchain 에 `ModelCallLimitMiddleware` 가
있으므로 그것으로 건다.

**두 겹으로 건다.** 호출자 쪽 `asyncio.wait_for` 와 런타임 자체 상한을 함께 쓴다 — 스레드는
취소할 수 없어서 앞의 것만으로는 실행이 계속 살아 크레딧을 쓴다 (`completion.py` 와 같은
이유).

#### 실측 (2026-07-31, openai:gpt-4o-mini, 질문 1건)

| 무엇 | 값 |
| --- | --- |
| 응답 시간 | **10.7초** (요청 → 200, 클라이언트 기준) |
| 도구 호출 | **4번** — `search_wiki` 1, `list_schedules` 1, `read_schedule` 1, `read_wiki` 1 |
| 모델 턴 | 5 (도구 4 + 구조화 응답 1) |
| 출처 | 위키 1 · 일정 1, 둘 다 `title` 채워짐 |

질문은 「다음 전사 일정과 연차 규정을 알려줘」(mixed)였고 `questionType` 이 `mixed` 로 왔다.
일정 기간이 `from=2026-08-01`(그날 다음날)로 잡혀 **지침의 오늘 날짜가 실제로 먹는다**는 것을
확인했다. 하네스는 `experiments/chat_agent_sim.py`, 창구는 `experiments/query_gateway.py` 다.

**상한을 그대로 둔다.** 10.7초는 25초의 절반이 안 되고, 4번은 5턴 안이다. 값이 시작점이라고
적어 둔 것은 그대로다 — 질문 하나로 잰 값이라 분포가 아니다.

**한 번 걸려 봤다 — 그리고 그게 지침을 고치게 했다.** 첫 시도에서 모델이 목차 링크의 파일
이름(`pages/eddb3cec8f14.md`)을 `wikiId` 로 넣어 `read_wiki` 를 다섯 번 헛불렀고 턴 상한에
걸렸다(6.7초). 계약의 목차는 `pages/{pageKey}.md` 로 링크하므로 **목차만 보고는 `wikiId` 를
알 수 없다.** 두 곳을 고쳤다: 지침이 「검색으로 wikiId 를 얻어서 읽어라」로 못박고, 읽기 실패
문장이 그 원인을 알려 준다. 고친 뒤 같은 질문이 4번 만에 답했다.

### 6.7 오류 이름

두 엔드포인트가 하나로 합쳐지므로 이름도 정리된다. **처음 보는 사람이 이름만 읽고 무슨 일이
있었는지 알 수 있게** 짓는다. 계약이 허용한 상태는 400·401·500 셋뿐이므로, 이름이 상태를
대신 설명해야 한다.

| 상태 | 이름 | 무슨 일인가 |
| --- | --- | --- |
| 400 | `INVALID_ANSWER_REQUEST` | 요청 형식이 잘못됐다 |
| 500 | `NO_WIKI_OR_SCHEDULE_WAS_READ` | 아무것도 조회하지 않아 근거가 없다 (§6.4) |
| 500 | `WIKI_QUERY_FAILED` | 위키 조회가 실패했다 |
| 500 | `SCHEDULE_QUERY_FAILED` | 일정 조회가 실패했다 |
| 500 | `AGENT_TURN_LIMIT_REACHED` | 턴 상한 안에 답을 못 만들었다 (§6.6) |
| 500 | `AGENT_TIMED_OUT` | 시간 상한에 걸렸다 (§6.6) |
| 500 | `MODEL_CALL_FAILED` | 모델 호출 자체가 실패했다 |
| 500 | `ANSWER_WAS_EMPTY` | 모델이 빈 답을 냈다 |

**사라지는 이름 두 개**: `ANSWER_CONTEXT_SELECTION_FAILED`(1단계 전용),
`INVALID_ANSWER_CONTEXT_REQUEST`. 그리고 `ANSWER_GENERATION_FAILED` 는 위 여섯 개로 쪼개진다
— 지금은 원인이 뭐든 이 하나로 나가서 무슨 일인지 알 수 없다.

> **계약에 없는 이름은 임의로 정하지 않는다** (`ai/CLAUDE.md`). 위 표는 **제안**이고, 계약 변경
> 절차(§12)에서 백엔드와 확정한다. 확정 전에는 MR 본문에 협의 항목으로 적는다.

### 6.8 실패했을 때

**백엔드와 합의한 것**: 한 번 실패하면 **한 번 더 시도**하고, 그래도 안 되면 사용자에게
「처리 중 문제가 생겼습니다」를 돌려준다. 재시도는 백엔드가 한다.

**다시 해도 같은 실패는 재시도하지 않는다.** `INVALID_ANSWER_REQUEST` 나
`NO_WIKI_OR_SCHEDULE_WAS_READ` 는 같은 요청에 같은 결과다. 재시도 대상은 시간 초과·모델 실패·
조회 실패·빈 답변뿐이다. 챗봇은 사용자가 기다리는 중이라 25초가 50초가 되는 것이 그대로 체감
된다 (아래 주의).

**재시도가 안전한 근거**: AI 는 작업 공간에만 쓰고 반영은 백엔드가 한다. 실패한 실행은
라이브 위키에 아무 흔적을 남기지 않는다. 같은 문서를 다시 넣어도 중복이 생기지 않는 것은
측정으로 확인했다 (`2026-07-27-reingest`, 재투입에서 create 0).

**주의**: 재시도는 시간과 비용을 두 배로 만든다. 위키 변환은 원래 분 단위라 문제가 없지만,
챗봇은 사용자가 기다리는 중이므로 첫 시도가 25초였으면 50초가 된다. §8-4 의 응답 시간
측정에 재시도까지 포함해서 봐야 한다.

**재시도가 안 듣는 실패도 있다.** 백엔드 조회가 계속 안 되거나 설정이 틀린 경우다. 다시 해도
같으므로 두 번 실패하고 사용자에게 메시지가 간다 — 맞는 동작이지만 시간은 두 배로 쓴다.

## 7. 백엔드에 부탁하는 것

**세 개다. 앞의 둘이 새 입구이고 마지막이 필드 하나다.**

**1. 일정 목록 조회 (내부용).** 기간을 받아 그 사람이 볼 수 있는 일정의 제목·시각·대상을
돌려준다. 공개 API 에 이미 같은 일을 하는 것이 있다(`GET /api/v1/schedules`, 로그인 사용자
기준으로 걸러 준다). **서비스 로직은 그것을 재사용하면 되고 입구만 새로 만든다.**

**2. 일정 상세 조회 (내부용).** `scheduleId` 로 본문까지 돌려준다.

**모양 제안** (백엔드가 고쳐도 된다. 우리가 필요한 것은 이 정보다):

```
GET /internal/v1/schedules?questionId=&from=&to=&keyword=&limit=
  → items[] : scheduleId · title · startAt · endAt · targetText · location
    truncated : 상한에 걸려 잘렸는지 (참/거짓)

GET /internal/v1/schedules/{scheduleId}?questionId=
  → scheduleId · title · content · startAt · endAt · targetText · location
```

- `keyword` 는 **제목에 그 글자가 들어있는지**로 본다. 한국어는 조사가 붙어(「연차를」) 단어
  단위 색인이 어긋나므로 부분 일치가 더 정확하다 — 위키 검색에서 실측한 성질이다
- 색인은 새로 만들 것이 없다. ERD 의 일정 표에 시작·종료·상태 색인이 이미 있고, 기간으로
  줄인 뒤 제목을 훑으면 된다
- `truncated` 가 필요한 이유: 잘린 줄 모르면 에이전트가 「이게 전부다」로 단정한다

두 입구의 권한은 **질문 번호(`questionId`)로 판정한다.** AI 가 조회할 때 번호를 함께 보내고,
백엔드가 그 번호로 질문한 사람을 찾아 그 사람 기준으로 거른다. 요청에 실린 값을 믿지 않는다.

> 위키는 허가값(§3)으로 판정하고 일정은 질문 번호로 판정한다. **판정 방식이 둘로 갈린다.**
> 위키 쪽에 이미 돌아가는 것이 있어서 그대로 쓰고, 일정은 새로 만드는 것이라 더 나은 쪽을
> 쓴다. 나중에 위키도 번호 기준으로 옮기면 하나가 된다 (§3.1).

**3. 챗봇 요청의 `wikiIndexes` 각 행에 그 범위의 허가값을 담는다.** 이미 있는 발급 함수를
범위 수만큼 부르면 된다.

### 7.1 정한 것

**`questionType` 은 응답에 남긴다.** 에이전트가 어차피 판단하므로 돌려주는 비용이 0이다.
백엔드가 `question` 테이블에 저장하는 값이라 빼면 그쪽이 바뀐다. 측정 지표로도 써 왔다 —
2026-07-29 챗봇 측정의 분류 정확도 8/8 이 이 값이다. **백엔드 확인 대상은 이 항목뿐이다**
(저장 형태가 바뀌지 않는지).

**`scopeVersion` 은 챗봇 요청에 넣지 않는다.** 범위 버전은 「작업 중에 위키가 바뀌었는지」를
보는 값이고, 챗봇은 읽기만 하므로 도중에 바뀌어도 해가 없다. 넣으면 버전 불일치로 정상
질문이 실패할 여지만 생긴다.

> 챗봇 도구는 위키 편집용 조회 클라이언트(`query_client.py`)를 쓰지 않으므로(§6.1) 버전
> 대조를 끄는 작업도 필요 없다. 백엔드는 허가값을 발급할 때 현재 버전을 그대로 넣으면 되고
> 우리는 보지 않는다.

**일정 기간은 정하지 않는다.** 에이전트가 질문에 맞춰 정한다 (§6.3). 백엔드가 미리 창을 고를
필요가 없어졌다.

## 8. 안고 가는 한계

**1. 목차 품질이 여전히 첫 관문이다.** 목차에 잘 적히지 않은 페이지는 에이전트가 못 고를 수
있다. 검색 도구(§6.2)가 있어 완전한 천장은 아니지만, 검색을 부를 생각을 하려면 목차에서
「없다」를 먼저 알아야 한다. 설계 문서에 이미 적힌 문제다 — 「`index.md` 품질을 측정 지표로
삼은 적이 없다」.

**2. 목차는 매 질문마다 다시 실린다.** 일정은 도구로 옮겨서 빠졌지만 목차는 남는다.

| 규모 | 추정 |
| --- | --- |
| 20페이지 | 약 3.4k 토큰 (실측 6,869바이트) |
| 100페이지 | 약 17k 토큰 (선형 추정) |

100페이지쯤 되면 목차도 도구로 옮기는 것을 다시 봐야 한다 (§9).

**캐싱으로 줄어드는지는 제공자에 달렸고, 다시 재야 한다.** 2026-07-29 측정에서 GMS 게이트웨이는
캐싱을 지원하지 않았다 — 표시를 정확히 붙여 같은 목차를 두 번 보내도 캐시 생성·읽기가 모두
0이었다. **그 값은 Claude 계열 + 게이트웨이 조건이다.** OpenAI 는 표시를 붙이는 방식이 아니라
같은 앞부분을 알아서 재사용하는 방식이므로, 실제로 걸리는지는 그 경로에서 재봐야 한다
(§6.1.1).

**3. 응답 시간은 재 봤다 — 늘어나지 않았다.** 2단계 시절이 두 호출 합쳐 약 10초였고,
에이전트 하나로 도구를 네 번 부른 실측이 **10.7초**다 (§6.6 실측표, gpt-4o-mini, 질문 1건).
조회가 여러 번 붙는 만큼 호출이 한 번으로 줄어 상쇄됐다. 위키 변환의 2분 반은 쓰기와 검사가
포함된 값이라 챗봇에 그대로 적용하면 과대추정이라고 적어 둔 그대로다.

**동기 방식을 유지한다.** 동시 접속 10명 규모로 보고 결정했고, 실측이 상한의 절반이 안 되므로
바꿀 근거가 없다. 실제로 느려지면 그때 비동기(번호를 주고 나중에 조회)로 바꾼다 — 그 전환은
AI·백엔드·프론트 세 곳을 다 건드린다. **분포는 여전히 모른다** — 질문 하나로 잰 값이다.

**4. OpenAI 키는 들어왔고 값도 재 봤다** (2026-07-31). 상한 두 개와 동기·비동기 결정의 근거가
§6.6 실측표·§8-3 에 있다. 남은 미측정은 **분포와 정확도**다 — 질문 하나로는 알 수 없고 예산이
3달러다 (§10.1).

## 10. 검증

- `uv run pytest -m "not ocr"` 기존 실패 0
- **도구를 가짜 백엔드로 돌려본다** — `experiments/query_gateway.py` 를 늘려 일정 두 입구를
  흉내내고, 다섯 도구가 상한·권한값을 제대로 쓰는지 본다. 모델 호출 없이 된다
- **출처 교집합** — 안 읽은 것을 신고한 응답을 만들어 걸러지는지 확인한다 (§6.4).
  에이전트 없이 단위 테스트로 고정한다
- **가짜 모델로 루프를 돌린다** — `GenericFakeChatModel`(langchain-core 에 이미 있다)에 도구 호출
  대사를 넣어 `create_deep_agent` 에 끼운다. 모델 판단만 가짜고 **루프·도구·HTTP·장부·응답 조립은
  전부 진짜다.** 도구를 직접 부르는 단위 테스트로는 안 잡히는 것을 여기서 잡는다 — 턴 상한이
  `AGENT_TURN_LIMIT_REACHED` 로 나오는지, 시간 상한, §6.4.1 의 200/500 갈림, 조회 실패가 어느
  이름으로 나가는지. **0원이다**
- **실기동 스모크** — 서버를 띄우고 세 엔드포인트를 실제 HTTP로 호출해 200과 응답 형태 확인
- **에이전트 한 번 돌려보기** — 진짜 모델로 질문 하나. 여기서 보는 것은 **「지침을 따르나」뿐이다**
  — 목차에서 맞는 페이지를 고르는지, 안 읽고 답하지 않는지. **여기까지가 이번에 확인할 전부다**
- **백엔드 실연동 — 했다 (2026-07-31).** Spring(169 브랜치, H2 `local` 프로파일) + AI 서버 +
  실제 OpenAI 로 `POST /api/v1/questions` 를 돌렸다. 일정 질문이 끝까지 갔다: 답변·출처
  (`scheduleId` 1, `title` 「[샘플] 전사 워크샵」)·`questionType=schedule` 이 DB 에 저장되고
  사용자 응답으로 돌아왔다.

  **단위 테스트가 못 잡은 결함 셋을 여기서 잡았다.** 157 의 교훈이 그대로 반복됐다:

  | 무엇 | 왜 단위로 못 잡나 |
  | --- | --- |
  | **두 번째 요청부터 전부 실패** — 요청마다 `asyncio.run` 이 루프를 새로 만들고 닫아 모델 클라이언트 연결 풀이 죽은 루프에 묶였다 (`Event loop is closed` → `APIConnectionError`) | 가짜 모델은 HTTP 를 쓰지 않아 루프에 묶일 것이 없다. **실기동 스모크도 못 잡는다** — 한 번만 보내면 통과한다 |
  | **턴 상한 이름이 고장을 덮었다** — 모델 호출이 매번 실패해도 호출 수는 올라가 `AGENT_TURN_LIMIT_REACHED` 가 먼저 나왔고, 그 이름 때문에 루프 결함을 네트워크 문제로 오진했다 | 이름 분기 테스트는 「상한이면 상한 이름」만 봤다. 「도구를 한 번도 못 불렀는데 상한」이라는 조합을 아무도 안 봤다 |
  | **도구 조회 실패가 사람 쪽에 안 남았다** — 모델에게 문장으로만 알려주니 로그가 비었고, 「상한에 걸렸다」만 보였다 | 도구 단위 테스트는 반환 문장을 보므로 로그가 없어도 통과한다 |

  고친 것: 챗봇 실행을 **서버 루프에서 그대로 await** 한다(`arun_with_tools` 가 정본,
  `run_with_tools` 는 스크립트용 껍데기), 도구 호출 수를 **우리가 세서** 상한 예외에도 남기고
  0 번이면 상한이 아니라 모델 실패로 낸다, 조회 실패·상한 도달을 로그로 남긴다(허가값은 찍지
  않는다).

  **백엔드에 넘긴 것 둘** (우리가 고치지 않는다):

  * `QuestionAskService.authorizedSources` → `ScheduleVisibilityPolicy.isReadableBy` →
    `Schedule.departmentIds()` 가 세션 밖에서 lazy 컬렉션을 건드려
    `LazyInitializationException` 이 난다. **답변 출처에 부서 공개 일정이 끼면 챗봇 요청이
    500** 이다 (재현: 개발부 사원으로 부서 일정을 묻는다).
  * `wiki-search` 가 로컬 `local` 프로파일에서 500 이다 — H2 에 MySQL 전문검색
    (`MATCH … AGAINST`)이 없다. **결함이 아니라 로컬 한계**이고, 그래서 **위키 검색 경로는
    이번 실연동에서 확인하지 못했다.** MySQL 로 띄워야 본다

### 10.1 예산이 3달러다 — 성능은 재지 않는다

**동작 확인까지만 한다.** 질문 하나가 끝까지 도는지 보고 멈춘다. 여러 질문으로 정확도를 재거나
턴 수를 조율하거나 응답 시간 분포를 잡는 것은 **예산이 생긴 뒤로 미룬다.**

질문 하나는 돌려 봤다 (§6.6 실측표) — 10.7초·도구 4번·출처 2건이고, 그것으로 상한 두 개와
동기 유지를 그대로 두기로 했다. **하지만 그것은 한 점이지 분포가 아니다.** 여러 질문으로 정확도를
재거나 턴 수를 조율하는 것은 예산이 생긴 뒤다.

측정할 때 값이 싼 모델을 쓴다. 위키 변환은 한 번에 분 단위로 돌아 비싸므로 **이번 예산으로는
챗봇만 본다** — 위키는 어차피 다음 단계다 (§1.1).

> **준비물**: 위 뒤 두 항목은 OpenAI 키가 `src/.env` 에 있어야 한다 (§6.1.1). 앞 세 항목은 키
> 없이 된다. 명령줄 도구로는 챗봇 에이전트를 돌릴 수 없으므로(§6.1) 대체 수단이 아니다.

## 12. 계약 변경 절차

요청 필드가 사라지고 새 필드가 생기므로 **호환되지 않는 변경**이다. 계약 문서를 직접 고치지
않고 `../docs/api/README.md` 의 계약 변경 절차를 따르며, 생성기
(`generate-postman-collections.mjs`)를 고쳐 재생성한다. JSON 을 직접 고치면 재생성 때
날아간다. `contractVersion` 을 올린다.

**버전은 1.8.0 이다.** 처음 1.7.0 으로 올렸는데, 이 작업이 develop 에서 갈라진 뒤
S15P11B106-101(AI 작업 수동 시작 API, `5e2ad9a`)이 먼저 머지되면서 1.7.0 을 가져갔다. 같은
번호가 두 뜻을 가지면 「1.7.0 기준으로 구현했다」가 어느 쪽인지 알 수 없어진다. 요구사항정의서도
2.18 로 올렸다 — FR-QNA-012 를 고치면서 변경 요약·문서 버전을 올리지 않은 것을 함께 정정했다.

프론트엔드 영향은 없다 — 내부 API 만 바뀐다.
