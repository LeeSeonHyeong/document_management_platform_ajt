# 한국어 데모 코퍼스 설계 — RAG로는 못 하는 것을 위키가 하는 장면을 심는다

- 작성일: 2026-08-01
- 대상: `experiments/corpus-ko-wiki/` 신설 (히어로 문서 세트 + 빌드 스크립트 + 온톨로지), `tests/parsing/` 견고성 픽스처 보강
- 배경: 시연이 일주일 안. 지금까지 위키 변환 측정은 PostHog 영어 12개(`experiments/corpus/`)로 했는데 (1) 해외 자료라 한국 사내 상황과 안 맞고, (2) 문서 간 주제 겹침이 거의 없어(Jaccard 0.09~0.21) 위키의 강점(병합·모순 해소·교차참조)을 **못 보여준다** (`experiments/INDEX.md` §코퍼스 관련 한계). 기존 `corpus-ko`는 검색 품질 측정 전용이고 위키 내부 링크가 0이라 교차참조를 못 보여줘 이 목적에 못 쓴다.
- 목표: **한국어**로, **RAG 대비 위키 우위를 의도적으로 자극**하고, **원본문서 형식의 여러 경우의 수**를 커버하는 데모·테스트 코퍼스.
- 상태: 설계 확정(사용자 승인 2026-08-01). 구현 계획 작성 대기.

## 1. 배경과 결정

### 1.1 "RAG와의 차이"는 이 코드베이스에서 무슨 뜻인가

이 코드베이스에서 "RAG"는 **챗봇 질의응답** 경로의 이름이다(`docs/superpowers/specs/2026-07-28-chatbot-answer-api-design.md`, Jira `S15P11B106-80`). **위키 생성** 경로는 그 반대편 — 편집 에이전트가 검색·조회·병합으로 원본문서를 하나의 정합된 위키로 만든다(`src/wiki_mcp/tools/guide.py`의 `GUIDE_TEXT`).

위키 생성이 naive 청크-검색 RAG 대비 이기는 지점(가이드·계약 설계 문서 근거):

- **병합(merge)**: 여러 문서에 흩어진 같은 주제를 한 페이지로. RAG는 조각을 개별 반환한다.
- **모순 해소**: 같은 항목의 서로 다른 값(구/신)을 업로드 시점에 현재값 + 이력으로 정리. RAG는 유사도 높은 조각을 그대로 던져 어느 게 현재값인지 모른다.
- **교차참조 링크**: 관련 페이지를 본문에서 링크. "링크가 관계 데이터의 유일한 입력원"(guide.py). RAG엔 '관계' 개념이 없다.
- **멱등 재업로드**: 같은 문서를 다시 올려도 중복 페이지가 안 생긴다(FR-DOC-012).

### 1.2 규모가 커질수록 차이가 커진다 (설계 함의)

소량에선 RAG top-k도 그럭저럭 맞힌다. 문서가 많아질수록: 중복 청크가 컨텍스트 창을 잠식, 검색 recall 저하(정답 청크가 top-k 탈락), 구버전 누적으로 현재값 판별 불가, 교차 합성 붕괴. 즉 **작은 큐레이션 세트는 메커니즘이 "존재함"을, 대량 세트는 그게 "중요함"을 증명한다.**

그래서 설계를 **2계층 + 확장 가능(scale-ready)** 으로 잡되, 마감(시연 일주일 안) 때문에 **이번엔 1계층(히어로)만 구현**하고 2계층(벌크 생성기)은 온톨로지·이음새만 남긴다.

### 1.3 확정된 결정

- 도메인: **사내 인사·복무 규정** (가상 회사 「(주)아지트」). PostHog 주제 구조(휴가·급여·복지·온보딩·보안·출장)를 한국화한 골격 위에 시나리오를 새로 엮는다.
- 보여줄 위키 강점: **모순 해소 + 병합 + 교차참조 그래프 + 멱등** 전부. 추가로 **회의록**으로 시간축·결정 흐름을 얹는다.
- 형식 커버리지: **DOCX·PDF·MD·TXT** 정상 경로 + **복잡한 표 DOCX** + **깨진/부분실패 파일**. **OCR(스캔본 이미지 PDF)은 제외** — 로컬 Tesseract 의존이라 시연에서 불안정하고 이번 핵심과 거리가 있음.
- 이번 범위: **히어로 세트만.** 벌크 생성기는 나중.

## 2. 비범위 (out of scope)

- **벌크(대량) 생성기 구현.** 온톨로지·이음새만 설계로 남긴다.
- **naive RAG 베이스라인 하니스.** 이 코퍼스는 차이를 *보여줄 수 있게* 만들지만, RAG 스트로맨을 나란히 돌리는 하니스는 별건. 이번엔 위키 결과(깨끗한 병합 페이지·그래프) 자체로 시연하는 것을 전제.
- **HWP(한글) 지원.** 파서가 `{.txt, .md, .pdf, .docx}`만 지원(`src/document_parser/parser.py:11`). 한국 사내에 흔하지만 이번 코퍼스엔 안 넣는다. "지원 형식은 이 4개"라는 시연 멘트/별도 티켓 여부는 추후 결정.
- **파이프라인 코드 변경.** 위키 생성·파싱 파이프라인은 이미 있다. 이 작업 산출물은 코퍼스(입력)뿐.

## 3. 산출물 구조

위치: `experiments/corpus-ko-wiki/` (기존 `corpus-ko`, `corpus-schedule` 컨벤션과 나란히).

**SSOT는 마크다운 원문**, 빌드 스크립트가 DOCX·PDF로 렌더한다. **렌더된 바이너리도 커밋**해 시연 당일 빌드가 필요 없게(turnkey) 한다. 원문이 있어 리뷰·수정이 쉽고, 형식은 재현 가능.

```
experiments/corpus-ko-wiki/
  README.md          # 도메인·문서별 의도 → 기대 위키 결과 → RAG라면 무엇이 무너지나 매핑 + 벌크 seam
  ontology.md        # 주제 목록 + 문서×주제 매트릭스 (히어로↔벌크 공유)
  sources/           # 각 문서 원문 .md (SSOT, 사람이 읽고 수정)
  build.py           # python-docx/pymupdf로 sources → documents/ 렌더 (tests/parsing 기법 재사용)
  documents/         # 렌더된 배포 파일 (.docx/.pdf/.md/.txt) — 커밋
```

## 4. 히어로 문서 세트 (8~9개)

각 문서의 역할이 곧 시연 포인트다. 수치·회사명은 제안값이며 자유롭게 조정 가능.

| # | 문서 (형식) | 심어둔 장치 → 보여줄 장면 |
|---|---|---|
| 1 | 복무규정 v1.0 (**DOCX**, 표) | 연차 **15일**, 교통비만 규정 → **모순의 구값** + 표 DOCX |
| 2 | 인사위원회 회의록 2024-03 (**PDF**) | "연차 15→**20일** 상향 의결", "출장 **식비** 신설" → **회의록 시간축** + 모순의 신결정 + 출장비 조각 |
| 3 | 복무규정 개정 공지 (**MD**) | 연차 20일 확정, 반차는 v1.0 "참조"만 → **모순 해소** + 교차참조 |
| 4 | 출장 관리 지침 (**DOCX**) | 출장 절차 + **숙박비** 정산 → 출장비 조각3 |
| 5 | 출장비 정산 FAQ (**TXT**) | "여비" 등 다른 어휘로 한도·영수증 → **병합(merge) 자극** (조각 1·2·4·5 → 한 페이지) |
| 6 | 팀리더 정기회의록 2024-06 (**PDF**) | 재택 주2일 시범, 대체휴일 승인 절차 → 회의록2 + **교차링크**(재택↔근태, 대체휴일↔연차) |
| 7 | 신입 온보딩 가이드 (**DOCX**, 긴 문서+표) | 연차·재택·보안을 각각 요약하며 링크 → **교차참조 허브** + 긴 문서 |
| 8 | 정보보안 지침 (**MD**) | 겹침 적은 독립 주제 → **대조군**(다 겹치진 않는 현실성) |
| 9 | (재업로드) 문서 3의 동일 사본 | → **멱등** 검증 (별도 파일 아님, 시나리오 표기) |

네 장면(모순 해소 / 병합 / 교차참조 / 멱등)이 전부 자연스럽게 발화되고, 회의록 2건이 시간축·결정 흐름을 얹는다.

### 4.1 주제 온톨로지 (히어로↔벌크 공유)

연차·반차·대체휴일/보상휴가·출장 및 출장비·급여/성과급·재택근무·경조사 지원·온보딩·정보보안. `ontology.md`에 문서×주제 매트릭스로 표기 → 나중에 벌크 생성기가 이 매트릭스만 읽고 주변을 채우면 되도록(seam).

## 5. 형식 커버리지와 견고성 픽스처

- 정상 경로: DOCX(표·병합셀·한글 제목 스타일 `제목 N`) · PDF(네이티브 텍스트) · MD · TXT 전부 커버. OCR 제외.
- 깨진/부분실패는 **시연 코퍼스와 분리**해 `tests/parsing/` 픽스처로: corrupt DOCX(malformed XML) · corrupt PDF(손상 바이트) · 빈 문서(empty) · partial_failure PDF(일부 페이지만 추출 실패). 파서가 안 죽고 오류코드(`corrupt_document`·`native_extraction_empty`·`partial_failure`)로 떨어지는지 확인. 기존 테스트 레시피(`tests/parsing/`의 `_write_pdf`·`_write_policy`·malformed-XML docx) 재사용.

## 6. README 의도 매핑 (RAG 차이를 "읽히게")

README에 문서별로 **의도 → 기대 위키 결과 → RAG라면 무엇이 무너지나**를 표로 적는다. 시연 진행자의 대본이자 회귀 기준이 된다. 예: 문서 1·2·3 → "위키: 연차 페이지 한 개, 현재값 20일, 근거 회의록 링크 / RAG: 15일·20일 청크를 다 반환해 현재값 불명."

## 7. 재사용하는 기존 자산

- **주제 골격**: PostHog 영어 12개(`experiments/corpus/`)의 인사·복무 주제 구조를 한국화.
- **파일 생성 기법**: `tests/parsing/`의 DOCX·PDF·깨진 파일 생성 레시피(python-docx / pymupdf).
- **생성 필러 방식**: `corpus-ko`의 절차적 생성 방식(향후 벌크에서 참고).

진짜 신규 저작은 "8~9개 한국어 문서 본문 + 의도적으로 심는 모순·흩어짐·교차링크·회의록 시간축"뿐 — 기존 코퍼스에 없어서 이 작업을 하는 부분이다.
