# 챗봇이 도구를 건너뛰고 500 을 낸다 (2026-08-10, 실기동)

시연 리허설 중 prod 에서 사원 챗봇이 간헐적으로 실패했다. 화면에는
`AI_SERVER_UNAVAILABLE` 이 떠서 AI 서버가 죽은 것처럼 보였으나 **AI 서버는 정상이었다.**

## 무엇이 일어났나

`answer.py` 의 가드가 걸린 것이다.

```python
if not run.tool_calls:
    raise InternalError(NO_SOURCE_CODE, "위키도 일정도 조회하지 않아 근거가 없습니다.", status=500)
```

모델이 첫 응답에서 도구를 한 번도 부르지 않으면 그 자리에서 500 이다. 근거 없는 답을
사용자에게 내보내지 않으려는 의도된 차단이며(S15P11B106-170), 버그가 아니다.

AI 컨테이너 로그의 차이는 검색 호출 한 줄뿐이다.

```

```

## 관찰

- **37 과 38 은 사실상 같은 질문인데 결과가 갈렸다. 비결정적이다.**
  "이력이 있을 때만 생긴다" 는 설명은 37 이 반증한다 (1턴이라 이력이 없다).
- **이력이 있으면 확률이 크게 오른다.** 42 는 같은 대화의 38 이 이미 답을 냈고,
  `answer_guide.chat_guide` 가 그 답변 **전문**을 시스템 지침의 `## 이전 대화` 로 넣는다.
  모델 입장에서 답이 이미 지침 안에 있으니 검색할 이유가 없다.
- 39·40·41 은 잡담이라 도구를 부를 이유가 없다. 이 실패는 자연스럽다.
- 39·40 처럼 대화 키가 매번 새로 생긴 것으로 보아 화면에서 대화가 나뉜 경우도 섞여 있다.

## 가설 (미검증)

`chat_guide` 는 볼 수 있는 **위키 목차 전문**도 지침에 넣는다. 목차에는 제목과 한 줄 요약이
있어, 재택근무처럼 흔한 주제는 목차만으로도 그럴듯한 답이 써진다. 시연 데이터가 커지며
위키가 16 → 35 로 늘어 목차 정보량이 크게 늘었고, 그만큼 모델이 검색을 생략할 여지가
커졌다는 설명이 가능하다. **확정하려면 실패 시 모델이 무엇을 근거로 삼았는지 봐야 하는데,
그 진단 로그는 MR !330 에 있고 prod 에는 아직 없다.**

## 코드 차이는 아니다

prod(`9cdbc5cf3c02`) 와 develop(`2cccf73f2a51`) 의 `ai/src/wiki_api/answer.py` 는 동일하다.
"어제까지 잘 됐다" 는 체감은 코드 변경이 아니라 입력(대화 이어짐·목차 크기) 쪽 변화로 보인다.
대화 이력 복원은 `d2e24ee` 에서 고쳤고, 그 전에는 새로고침마다 1턴이라 42 형태가 나올 수 없었다.

## 사용자에게 보이는 문구

`QuestionAskService` 는 챗봇 실패를 원인과 무관하게 전부 `ErrorCode.AI_SERVER_UNAVAILABLE`
로 낸다. 원인은 코드 이름이 아니라 `AiClientErrorMapper` 의 문구에 담긴다. AI 서버가 멀쩡한데도
"AI 서버를 사용할 수 없습니다" 로 읽히는 것은 이 때문이다.

`NO_WIKI_OR_SCHEDULE_WAS_READ` 는 재시도 대상에서 의도적으로 빠져 있다 — 같은 요청에 같은
결과라 대기 시간만 두 배가 된다(설계 §6.8).

## 선택지

1. **지침 강화** — "이전 대화나 목차에 답이 보여도 반드시 `wiki_search` 를 먼저 부른다" 를
   명시한다. 변경이 가장 작고 구조를 안 건드린다. 모델 준수에 의존한다
2. **이력에 답변 전문을 넣지 않는다** — 질문만, 또는 요약만 넣는다. 42 형태를 구조적으로 막는다
3. **목차에서 요약 제거** — 검색 없이는 답을 쓸 수 없게 된다. 가장 확실하지만 정상 동작에도 영향
4. **가드 완화** — 도구 0 회를 허용하고 출처를 비운다. 환각 차단을 포기하는 것이라 마지막 수단

1 + 2 를 함께 하는 것을 권한다. 어느 쪽이든 **먼저 `tests/runtime/fake_models.py` 하네스로
재현**해야 한다 — 비결정적이라 한 번 통과했다고 고쳐진 것이 아니다.
