## ① 검색은 옳았다 — 실제 질의를 실제 색인에 돌려 확인했다

### 방법

실패 트레이스(`019fd496-55b4-7e01-90b1-6930349a2f9c`, job 36)에서 에이전트가 실제로 던진
`search` 질의 33개를 LangSmith API 로 뽑아, **실제 위키 색인(MySQL `wiki_search_chunk`)에
그대로** 돌렸다. `InternalWikiQueryService.search` 와 같은 SQL·같은 `booleanTerms` 를
재현했다.

### 결과

| 질의 계열 | 건수 | 색인이 돌려준 것 |
| --- | --- | --- |
| 조직개편·조직도 | 7 | **전부 0건** |
| 출장·식비 | 15 | **전부 `출장비(여비) 정산 안내`(wiki 4)를 1위** |
| 경조사 | 6 | 전부 `연차유급휴가 규정`(wiki 5)을 1위 |

조직개편은 위키에 **실제로 없었다**(그래서 새로 만들어야 했다). 식비 조항은
`출장비(여비) 정산 안내` 에 **추가돼야 할 내용**이었고 색인은 그 페이지를 15번 다 1위로
줬다. **검색이 틀린 적이 한 번도 없다.**

그리고 질의 33개가 서로 다른 결과집합을 **14개**만 냈다. 절반 이상이 같은 답의 재수신이다.

### 그럼 왜 루프에 빠졌나

응답이 사실을 전달하지 못했다.

- 라이브 헤더가 **「이미 서비스 중이다」**라고 단정 → 「찾는 내용이 여기 있다」로 읽힌다.
  식비 조항이 없는 페이지를 15번 받고 「있다는데 없네」를 반복하며 13번 재질의했다
- **0건이 결론임을 말하지 않았다** → 조직개편을 5번 0건으로 확인하고도 `create` 로 안 갔다
- `guide` 가 **「키워드를 바꿔 여러 번 부른다」**고 시키면서 종료 조건이 없었다. bigram OR
  색인이라 표현을 바꿔도 결과가 거의 같으므로 **재질의는 구조적으로 새 정보를 못 준다.**
  에이전트는 지침을 지킨 것이다

### 여기서 뒤집힌 판단

조사 도중 **엔진(MySQL 검색)을 고치는 쪽으로 두 번 갔다가 되돌아왔다.** 근거는 골드셋
평균(`R@5 0.60`·`P@5 0.12`)이었는데, 그 값은 자연어 질의가 끌어내린 것이고 **위키 편집
에이전트가 쓰는 정확어 질의는 이미 `R@5 1.00`** 이다 (`experiments/INDEX.md`).

`INDEX.md` 는 수치의 정본이라고 루트 `CLAUDE.md` 에 적혀 있다. **먼저 읽었으면 그 두 턴이
없었다.** 검색·랭킹 판단 전에는 `INDEX.md` 를 먼저 본다.

## ② 골드셋이 에이전트 질의를 대표하지 않는다 — 미해결

`INDEX.md` 는 「랭킹·리랭커·BM25 로 얻을 수 있는 최대는 `dev` +0.05, `test` +0.15」라고
적고 있다. 그 결론은 **`corpus-ko` 코퍼스 위에서만 참**이다. 그 코퍼스가 재지 않는 것:

| # | 한계 | 근거 |
| --- | --- | --- |
| 1 | **정확어 질의가 전부 1~2어절** (`연차`·`이월`·`베스팅`). 에이전트 실제 질의는 3~6어절이 33개 중 24개 | `queries.json` vs 위 트레이스 |
| 2 | **「정답 없음」 질의가 0개.** 40개 전부 정답이 있다 | 8/6 실패는 정답이 없는 질의였다 |
| 3 | **정답이 질의당 1장.** 에이전트 과업은 중복 탐지라 0장이거나 여러 장일 수 있다 | — |
| 4 | **n=10** (종류별). `정확어 R@5 1.00` 의 95% 하한이 약 0.72 | — |
| 5 | **코퍼스가 균질하다** (전부 7,856~8,155자). 그런데 같은 `INDEX.md` 가 「MySQL 은 길이 정규화가 없어 긴 절이 빈도만으로 앞선다」고 지적한다 — **자기가 찾은 결함을 자기 코퍼스로는 못 잰다** | `INDEX.md` |
| 6 | **주제가 서로 안 겹친다.** 실제 위키는 「출장비」↔「교통비 지급 기준」처럼 인접 주제가 겹치고, 트레이스에서 매번 걸린 것이 그 케이스다 | — |

`corpus-ko/README.md` 자신이 1번을 예고하고 있었다 — *"위키 변환 에이전트의 검색이 이
성격이라고 **가정**하고 있다. 그 가정은 아직 실측으로 확인되지 않았다 — 계획 Task 9 가

반증한다.**

**따라서 「리랭커 천장 +0.05」를 일반 결론으로 인용하지 않는다.** 리랭커가 필요한지는
지금 판단할 수 없다 — 판단하려면 골드셋을 실제 질의 분포로 다시 만들어야 한다.

## ③ 삭제 재조정이 스스로 모순을 만든다 — **확인됨**

8/6 findings(`2026-08-06-duplicate-uploads-and-deletion-deadlock.md`)는 문서 25 삭제가
교착된 이유를 **「파일명이 같은 문서 23 이 살아 있어 각주가 그쪽으로 해석된다」**고 적었다.
**그 설명은 틀렸을 가능성이 크다.**

- 하이드레이션은 **위키 페이지만** 올린다 (`FederatedVaultFS._hydrate_catalog` 는
  `list_pages()` 만 부른다). **문서 23 은 애초에 vault 에 없다.**
- 삭제 재조정은 **지울 문서의 옛 본문을 스스로 스테이징한다**
  (`routers/wiki.py` 의 `load_source(payload.documentId, removed, ...)`). 뭘 지울지
  보여야 하니 필요한 동작이다.
- 스테이징본은 `visible_documents` 에 들어간다 (`shared/schema.sql` 확인).

즉 `find_source("01-service-rules-v1.docx")` 가 찾는 것은 **방금 우리가 올린 그 문서**다.
에이전트가 겪는 모순 —「지우라는 문서를 `read` 하면 나온다」— 은 **중복이 하나도 없어도
똑같이 생긴다.**

### 검증 결과 — 중복이 0 인 범위에서 재현됐다

`tests/mcp/test_removal_self_contradiction.py` 가 프로덕션 경로
(`SpringVaultFS.stage_source`)를 그대로 태운다.

| | 스테이징 전 | 스테이징 후 |
| --- | --- | --- |
| `find_source("복무규정.docx")` | `None` | **문서를 찾는다** |
| `lint` | `unresolved-citation` **잡음** | **안 잡음** |

에이전트가 겪은 상태:

- 지시: 「`sources/25/...` 가 **삭제**됐다. 걷어내라」
- `read`: **문서가 멀쩡히 나온다**
- `lint`: 그 각주를 **문제 삼지 않는다**
- 종료 조건은 「`error` 가 0 이 될 때까지」인데 **이미 0 이다**

끝낼 조건이 성립하지 않으니 무엇이 잘못됐는지 찾으려 검색을 반복하다 죽었다.

### 따라오는 것

**8/6 findings 의 ②·③ 설명을 정정해야 한다** (그 문서는 아직 커밋 전이다):

- ② 「문서 23 으로 해석된다」 → 문서 23 은 애초에 vault 에 없다. 원인은 삭제 경로 자신이다
- ③ 「삭제는 안전하다 — `unresolved-citation`(error)이 잡는다」 → **안 잡는다**

**파일명 유일성으로는 이 교착이 안 죽는다.** 중복이 0 인 범위에서 재현되기 때문이다.
중복 업로드는 그래프 오독(①) 문제로 남지만 삭제 교착의 원인은 아니다.

주소로 지목하는 것도 답이 아니었다 — 지시문은 **이미** `sources/{id}/parsed/content.md` 를
주소로 지목하고 있고, 그 주소가 읽히는 것이 문제이기 때문이다.

### 고친 방법 (MR !266)

`document_replaced` 분기는 **이미 이 문제를 알고 고쳐놨다.** 주석까지 있다 — *"그 사실을
적지 않으면 에이전트가 옛 내용만 있다고 보고 문단을 지우는 쪽으로 간다"*. 같은 교훈이
삭제 분기에만 반영되지 않았다. 그래서 삭제 분기에도 넣었다:

1. 그 주소가 **참고용 사본**이며 문서가 아직 있다는 뜻이 아님을 명시
2. **`lint` 로 완료를 판단하지 말 것** — 걷어낼 각주가 미해결로 안 잡히므로 `error 0` 은
   완료의 근거가 아니다
3. **고칠 곳 목록이 전부**임을 명시 — 참조 그래프가 각주 단위로 이미 안다

## ④ 삭제 시 각주 재귀속 — 배관은 이미 있다

같은 내용이 다른 살아 있는 원본문서에도 있는 문단은, 지금 지시문이 뺄셈만 하므로 **함께
지워진다.** 지운 뒤 `lint` 가 조용해서(각주가 없으니 `unresolved-citation` 도 없다) 아무도
모른다.

조사 중 **「다른 원본문서는 작업 공간에 없어 재귀속이 구조적으로 불가능하다」고 판단했는데
틀렸다.** `wiki_api/session.py::stage_evidence_documents(wiki_id)` 가 「이 위키가 근거로
쓴 원본문서 전부를 조회 API 로 읽어 올리는」 일을 이미 한다. 관리자 채팅(`wiki-edits`)
경로에만 연결돼 있고 삭제·교체 재조정에는 안 걸려 있을 뿐이다.

그리고 **유사도 판정이 필요하지 않다.** 각주의 인용문이 다른 원본문서에 **글자 그대로**
있는지만 보면 되고, 그것은 `lint` 의 `_lint_citations` 가 이미 하는 일이다. 없는 근거를
붙일 위험이 없다.

**남은 비용은 조회 예산과 컨텍스트다.** job 35 는 affected 가 14건이었다 — 페이지마다 근거
문서를 받으면 HTTP 호출이 수십 건이고, 원본문서를 여러 개 올리면 검색 표면이 커져 ①의 루프를
악화시킬 수 있다. 그래서 ①을 먼저 고친 뒤에 손대는 것이 맞다.

## ⑤ 하네스는 이 실패를 재현하지 못한다

`tools/harness/` 에 실제 위키 10페이지(MySQL 에서 복사)와 문서 46 을 심고 develop 코드와
수정 코드를 각각 돌렸다.

| | develop | 수정 |
| --- | --- | --- |
| 턴 | 22 | 17 |
| `search` | 8 | 5 |
| 입력 토큰 | 618,771 | 433,959 |
| 결과 | **성공** | 성공 |

**대조군도 성공했다** — 프로덕션에서 40턴에 죽은 작업이 하네스에서는 develop 로도 끝난다.
원인은 검색 경로가 다르기 때문이다: 하네스는 AI 내부 SQLite FTS5 를 쓰고 프로덕션 라이브
검색은 Spring MySQL `ngram` 이다. 같은 질의 `조직개편 플랫폼팀 신설` 이 **SQLite 3건 /
MySQL 0건**이다.

**따라서 하네스로는 검색 관련 회귀를 판정할 수 없다.** 방향(턴·토큰 감소)은 보이지만
실패/성공은 못 가른다. 검색이 얽힌 변경은 실기동으로 확인한다.

## 부수적으로 찾은 것

**작업 요약이 무엇을 고쳤는지 말하지 않았다.** `ingest_instruction` 은 5열 표를 요구하는데
`AgentReport.summary` 필드 설명이 「2~3문장 보고」였다. 마지막 답변은
`ToolStrategy(AgentReport)` 로 그 필드에 담기므로 **필드 설명이 프롬프트를 이겨 표가
구조적으로 나올 수 없었다.** 같은 티켓(S15P11B106-251) 안에서 스키마(`349f9f9`, 08-04)가
먼저 있었고 표 양식(`f713883`, 08-05)이 나중에 들어오며 앞의 것을 안 고친 누락이다.
S15P11B106-289 에서 고쳤다.

**부서관리자에게 ALL 범위 문서의 재시도 버튼이 보이는데 누르면 404 다.**
`DocumentManagementService.requireDocumentScope` 가 권한 밖이면 `NOT_FOUND` 를 던진다
(존재를 숨기려는 의도된 설계). 프론트가 버튼을 감추거나 안내를 줘야 한다. `ai/` 밖이라
담당자에게 알렸다.
