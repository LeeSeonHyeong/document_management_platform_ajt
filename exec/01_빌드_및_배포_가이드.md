### 1.6 개발 도구 (IDE)

IDE는 실행·배포의 필수 조건이 아니다. 아래는 개발에 실제로 사용한 도구다.

| 분야 | IDE/도구 | 버전 |
| --- | --- | --- |
| 백엔드 (Java) | IntelliJ IDEA Ultimate | **2026.1.3** |
| 프론트엔드 (React) | Visual Studio Code | **1.132.0** |
| AI (Python) | Visual Studio Code | **1.132.0** |
| DB 도구 | TablePlus | **26.6.0** |
| API 테스트 | Postman (웹) | 컬렉션 스키마 **v2.1.0** (`docs/api/`) |

- 백엔드가 IntelliJ 인 것은 `.gitignore` 가 `.idea/` 와 `*.iml` 을 무시하는 것과 맞는다.
  에디션은 설치본의 `product-info.json` 이 `productCode: IU`(Ultimate)로 확인된다.
- 프론트와 AI 는 같은 VS Code 를 쓴다. 설치된 확장이 그 둘을 가른다 —
  `ms-python.python`·`vscode-pylance`(AI), `dbaeumer.vscode-eslint`(프론트).
  Java 확장은 없다.
- Postman 은 데스크톱 앱을 설치하지 않고 웹으로 쓴다. 그래서 제품 버전 대신
  저장소에 커밋된 컬렉션의 스키마 버전을 적는다.

> 팀원마다 로컬 도구가 다를 수 있다. 위 값은 개발·배포를 수행한 환경(macOS)에서 확인한 것이다.

## 2. 주요 설정값

### 2.1 백엔드 (`backend/src/main/resources/application.yml`)

| 설정 | 값 | 이유 |
| --- | --- | --- |
| `spring.application.name` | `ajt-backend` | |
| `spring.profiles.active` | 기본 `local`, 운영은 환경변수로 `prod` | |
| `spring.jpa.properties.hibernate.jdbc.time_zone` | `UTC` | 컨테이너에 TZ 설정이 없어 UTC로 도는 것에 맞춤. 서버 시간대에 따라 같은 시각이 다르게 저장되는 문제 방지 |
| `spring.servlet.multipart.max-file-size` | **20MB** | 파일당 업로드 상한 |
| `spring.servlet.multipart.max-request-size` | **100MB** | 요청 전체 상한 |
| `server.tomcat.max-swallow-size` | **128MB** | 413 초과 시 Tomcat이 미판독 본문을 삼켜 공통 JSON 오류를 반환하게 함 (기본 2MB면 HTML 오류가 나감) |
| `management.endpoints.web.exposure.include` | `health,info` | Actuator 최소 노출 |
| `management.endpoint.health.probes.enabled` | `true` | |
| `spring.mail.host / port` | `smtp.naver.com` / `465` | SSL, 비밀번호 재설정 인증번호 발송 |
| `ajt.auth.access-token-expiration` | `1h` | |
| `ajt.auth.password-reset-expiration` | `30m` | |
| `ajt.ai.connect-timeout` | `5s` | |
| `ajt.ai.read-timeout` | `10m` | 위키 변환은 장시간 작업 |
| `ajt.ai.schedule-extraction-read-timeout` | `180s` | 계약상 일정 추출 상한 |

> `ajt.ai.internal-api-key`는 **기본값을 두지 않는다.** 비어 있으면 기동에 실패시켜
> 알려진 키로 내부 API가 열리는 것을 막는다.

### 2.2 nginx (`frontend/nginx.conf`)

| 설정 | 값 | 이유 |
| --- | --- | --- |
| `listen` | `443 ssl` | HTTPS 전용 |
| `ssl_certificate` | `/etc/letsencrypt/live/i15b106.p.ssafy.io/fullchain.pem` | **도메인 변경 시 반드시 수정** |
| `ssl_certificate_key` | `/etc/letsencrypt/live/i15b106.p.ssafy.io/privkey.pem` | 동일 |
| `location /assets/` | `Cache-Control: public, max-age=31536000, immutable` | 해시 파일명이라 장기 캐시 안전 |
| `location /` | `try_files $uri $uri/ /index.html`, `Cache-Control: no-cache` | SPA 라우팅 + 재배포 즉시 반영 |
| `location /api/` | `proxy_pass http://backend:8080` | Compose 서비스명 DNS |
| `client_max_body_size` | **100M** (`location /api/` 안에만 지정) | 기본 1MB면 대용량 업로드가 413으로 차단됨. 업로드는 모두 `/api/` 를 지나므로 이 위치면 충분하다 |

## 4. 수동 빌드 절차

### 4.1 사전 요구사항

```bash
docker --version          # 24.x 이상, Compose V2 포함
git --version
openssl version           # bootstrap-admin.sh 에 필요
htpasswd -h               # apache2-utils — bootstrap-admin.sh 에 필요
```

### 4.2 클론 및 환경변수 준비

```bash
git clone https://lab.ssafy.com/s15-webmobile2-sub1/S15P11B106.git
cd S15P11B106
git switch master

cp .env.example .env
# .env 를 열어 🔴 표시 항목을 모두 채운다 (3.2절 참고)
# 🟡 항목도 확인한다 — 특히 SUPER_ADMIN_EMAIL 과 MAIL_* 는
#    비워도 기동이 되므로 빠뜨려도 바로 드러나지 않는다
```

### 4.3 이미지 빌드

세 이미지 모두 **동일한 Git commit SHA**를 태그로 사용한다.

```bash
export IMAGE_TAG=$(git rev-parse --short=12 HEAD)

docker build --tag "ajt-backend:${IMAGE_TAG}"  backend
docker build --tag "ajt-frontend:${IMAGE_TAG}" frontend
docker build --target runtime --tag "ajt-ai:${IMAGE_TAG}" ai
```

각 Dockerfile은 **멀티스테이지**로 구성되어 빌드 도구가 런타임 이미지에 남지 않는다.

| 이미지 | build 단계 | runtime 단계 |
| --- | --- | --- |
| backend | `eclipse-temurin:21-jdk` → `./gradlew clean bootJar --no-daemon` | `eclipse-temurin:21-jre` + jar + curl(헬스체크용) |
| frontend | `node:22-alpine` → `npm ci && npm run build` | `nginx:alpine` + `/app/dist` + `nginx.conf` |
| ai | `python:3.12-slim` + uv → `uv sync --frozen --no-dev --extra deepagents` | `python:3.12-slim` + `.venv` + `src` (비특권 사용자) |

### 4.4 로컬 테스트 실행 (선택)

```bash
# 백엔드
cd backend && ./gradlew clean test --no-daemon && cd ..

# 프론트엔드
cd frontend && npm ci && npm run lint && npm run test && npm run build && cd ..

# AI
docker build --target test --tag "ajt-ai-test:${IMAGE_TAG}" ai
docker run --rm --volume "$PWD/docs:/docs:ro" "ajt-ai-test:${IMAGE_TAG}"
```

### 4.5 기동

```bash
docker compose \
  --project-name ajt-prod \
  --env-file .env \
  --file docker-compose.yml \
  up -d --no-build --remove-orphans
```

기동 순서는 `depends_on` + `healthcheck`로 강제된다.

| 서비스 | 무엇을 기다리나 |
| --- | --- |
| `mysql` | 없음 — 즉시 기동 |
| `ai` | 없음 — **`mysql` 과 병렬로 기동한다** (`depends_on` 없음. AI 서버는 DB 에 붙지 않는다) |
| `backend` | `mysql` **과** `ai` 가 **둘 다** healthy |
| `frontend` | `backend` 가 healthy |

즉 보장되는 것은 "backend 는 mysql·ai 가 모두 준비된 뒤에 뜬다"이지, mysql → ai 순서가 아니다.

### 4.6 상태 확인

```bash
docker compose --project-name ajt-prod ps
curl -k https://127.0.0.1/api/v1/health      # 프론트 경유 백엔드 헬스
docker compose --project-name ajt-prod logs -f backend
```

## 5. CI/CD 자동 배포 (Jenkins)

`Jenkinsfile` 기준. 브랜치에 따라 배포 대상이 자동 결정된다.

### 5.1 파이프라인 단계

```
Checkout           → IMAGE_TAG = git rev-parse --short=12 HEAD
                     scripts/resolve-deploy-target.sh 로 배포 대상 결정
   ↓
Backend Test       → ./gradlew clean test --no-daemon
   ↓
Frontend Check     → docker run node:22-alpine: npm ci && lint && test && build
   ↓
AI Test            → docker build --target test  →  pytest -m "not ocr and not llm"
   ↓
Docker Build       → backend / frontend / ai 3개 이미지 태깅
   ↓
Deployment Approval → master 브랜치일 때만 (최대 24시간 대기)
   ↓
Deploy             → scripts/deploy.sh "$IMAGE_TAG"
```

- 타임아웃: Build·Test 60분 / Deploy 10분
- `disableConcurrentBuilds()` — 동시 빌드 차단
- 빌드 이력 20개 보관

### 5.2 브랜치별 배포 대상 (`scripts/resolve-deploy-target.sh`)

| 브랜치 | Compose 프로젝트 | 포트 | 시크릿 파일 | 승인 |
| --- | --- | --- | --- | --- |
| `develop` | `ajt-develop` | **8090** | `/var/lib/jenkins/ajt-secrets/develop.env` | 불필요 |
| `master` | `ajt-prod` | **443** | `/var/lib/jenkins/ajt-secrets/prod.env` | **필요** |

그 외 브랜치는 `exit 2`로 배포가 거부된다.

### 5.3 배포 스크립트 동작 (`scripts/deploy.sh`)

1. **입력 검증** — `IMAGE_TAG`가 7~40자 소문자 hex(Git SHA)인지 확인. 아니면 중단
2. **배타 락** — `flock`으로 `/var/lib/jenkins/ajt-deploy/deploy.lock` 획득 (동시 배포 방지)
3. **이미지 존재 확인** — backend/frontend/ai 3개 모두 `docker image inspect` 통과해야 진행
4. **배포** — `docker compose up -d --no-build --remove-orphans`
5. **헬스체크** — `DEPLOY_HEALTHCHECK_URL`을 **5초 간격 최대 30회(약 150초)** 폴링
6. **성공 시** — `current-image-tag` 상태 파일 갱신 (원자적 `mv`)
7. **실패 시 자동 롤백** — 직전 태그로 재기동 후 다시 헬스체크
   - 직전 태그가 없으면(최초 배포) 실패한 스택을 `down`
   - 롤백 이미지가 없으면 오류 종료

> 롤백이 성공해도 스크립트는 **exit 1**로 끝난다 — 배포 자체는 실패로 기록된다.

## 6. 배포 시 특이사항 ⚠️

실제 포팅 시 반드시 확인해야 하는 항목이다.

### 6.1 도메인·인증서 (필수 수정)

`frontend/nginx.conf`에 도메인이 **하드코딩**되어 있다.

```nginx
ssl_certificate     /etc/letsencrypt/live/i15b106.p.ssafy.io/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/i15b106.p.ssafy.io/privkey.pem;
```

- 다른 도메인으로 포팅할 경우 **이 두 줄을 수정한 뒤 프론트 이미지를 재빌드**해야 한다.
- 호스트에 Let's Encrypt 인증서가 미리 발급돼 있어야 한다 (`/etc/letsencrypt` 를 read-only 바인드 마운트).
- 인증서가 없으면 nginx가 기동에 실패한다.

```bash
# 인증서 최초 발급 예시
sudo certbot certonly --standalone -d <도메인>
```

### 6.2 최초 배포 시 DB 초기화

`docker-compose.yml`이 `docs/db/erd.sql`을 MySQL 초기화 스크립트로 마운트한다.

```yaml
volumes:
  - ./docs/db/erd.sql:/docker-entrypoint-initdb.d/01-schema.sql:ro
```

- **이 스크립트는 데이터 볼륨이 비어 있을 때 최초 1회만 실행된다.**
- 이미 데이터가 있는 볼륨에 재기동하면 스키마 변경이 반영되지 않는다.
- 스키마를 갈아엎으려면 볼륨을 삭제해야 한다(**데이터 전손**):
  ```bash
  docker compose --project-name ajt-prod down
  docker volume rm ajt-prod-mysql-data
  ```

### 6.3 최고관리자 계정 부트스트랩 (최초 1회 필수)

가입 승인을 처리할 최초 관리자가 없으면 서비스를 쓸 수 없다.

```bash
bash scripts/bootstrap-admin.sh
# 또는 이메일 명시 (배포된 SUPER_ADMIN_EMAIL 과 일치해야 함)
bash scripts/bootstrap-admin.sh admin@example.com
```

스크립트가 하는 일:
- 배포된 backend 컨테이너의 `SUPER_ADMIN_EMAIL`을 읽어 **일치 여부를 검증**
- 이미 같은 이메일의 member가 있으면 `exit 3` (중복 생성 방지)
- `openssl rand -base64 32`에서 영숫자만 남겨 **15자** 임시 비밀번호 생성, `htpasswd -bnBC 12`로 BCrypt 해시
- `department('최고관리자')`, `member(ADMIN/APPROVED/ACTIVE)`, `wiki_scope('ALL')`, `document_category('일반')`를 한 트랜잭션으로 INSERT

> 🔴 출력된 **초기 비밀번호는 다시 확인할 수 없다.** 즉시 안전한 곳에 저장하고 로그인 후 변경한다.
> 호스트에 `openssl`과 `htpasswd`(apache2-utils)가 설치돼 있어야 한다.

### 6.4 이미지 태그 정책

- 운영에서 **`latest` 태그를 사용하지 않는다.** `IMAGE_TAG`는 반드시 Git commit SHA.
- Jenkins `Deploy` 단계는 빌드 시점 SHA와 배포 시점 SHA를 비교해 **다르면 배포를 중단**한다.
- 롤백이 가능하려면 **직전 커밋의 이미지 3종이 서버에 남아 있어야 한다.** `docker image prune` 시 주의.

### 6.5 타임존

- 컨테이너에 `TZ` 설정이 없어 **UTC**로 동작한다.
- `hibernate.jdbc.time_zone: UTC`로 못박아 저장 시각을 고정했다.
- 이미 저장된 값도 UTC 기준이므로, **TZ를 KST로 바꾸면 기존 데이터 해석이 어긋난다.** 변경하지 말 것.

### 6.6 GPU / 모델 제약

- 배포 서버에 GPU가 없어 **Ollama를 사용하지 않는다.** 모든 LLM 호출은 SSAFY GMS(Anthropic)로 고정.
- GMS 게이트웨이는 요청 본문을 약 100KB로 제한한다. 스캔 PDF OCR은 이 제한에 걸리므로
  **Google Gemini**를 별도로 사용한다 (`VISION_OCR_PROVIDER=gemini`).
- `GEMINI_API_KEY`가 비면 로컬 Tesseract로 폴백하나, **한글 언어팩이 없으면 실패**한다.

### 6.7 업로드 용량

파일당 20MB / 요청 100MB. 세 곳이 함께 맞아야 한다.

| 위치 | 설정 |
| --- | --- |
| nginx | `client_max_body_size 100M` |
| Spring multipart | `max-file-size 20MB`, `max-request-size 100MB` |
| Tomcat | `max-swallow-size 128MB` |

### 6.8 환경 분리

같은 서버에서 `develop`(8090)과 `master`(443) 스택이 함께 돌 수 있다.
**볼륨 이름(`MYSQL_VOLUME_NAME`, `AJT_FILES_VOLUME_NAME`)과 `COMPOSE_PROJECT_NAME`을 반드시 다르게** 지정해야 데이터가 섞이지 않는다.
