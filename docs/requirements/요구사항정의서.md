# 요구사항정의서_v2.20

# 사내 LLM Wiki 및 일정 관리 시스템 요구사항정의서

- 문서 버전: 2.20
- 작성일: 2026-07-23 (개정: 2026-07-31)
- 상태: 인터뷰 확정본
- 작성 기준: 기존 요구사항 명세서와 요구사항 인터뷰 확정 사항
- 2.20 변경 요약(위키 변환 자료 자율 조회): 위키 변환이 AI 를 두 번 부르던 것을 한 번으로 합친다. 백엔드는 목차·카테고리·선택 Wiki 본문을 전달하지 않고 조회 허가값만 전달하며, 에이전트가 필요한 것을 Wiki 조회 API 로 직접 읽는다(FR-WIKI-002 과도기 조항 해소). 챗봇(2.19)과 같은 방식이고, 조회 수단이 준비되면 `wiki-context-selections` 를 제거한다는 FR-WIKI-002 의 예고를 이행하는 것이다. 내부 계약은 1.9.0 이며 내부 API 가 6개에서 5개로 줄어든다. 공개 API·DB 테이블은 변경하지 않는다.
- 2.19 변경 요약(챗봇 답변 자료 자율 조회): 챗봇이 AI 를 두 번 부르던 것을 한 번으로 합친다. 백엔드는 권한 내 `index.md`와 범위별 조회 허가값만 전달하고, 에이전트가 필요한 Wiki 본문과 일정을 내부 조회 API 로 직접 읽는다(FR-QNA-012 신설·개정, 3절 질의응답 흐름 개정). 출처는 에이전트가 읽은 자료 중 답변에 사용한 것으로 하고, 읽은 기록과 대조해 사용하지 않았거나 읽지 않은 자료를 걸러낸다(FR-QNA-006 유지). 근거를 찾아봤지만 없으면 빈 출처로 정보 부족을 안내하고(FR-QNA-007 유지), 조회를 아예 시도하지 않은 실행만 실패로 처리한다. 질문 유형은 에이전트가 질문 맥락을 보고 판단한다(FR-QNA-002 유지). 일정 조회 권한은 질문 ID 로 백엔드가 판정하며 이를 위한 내부 일정 조회 API 두 개를 신설한다. 내부 계약은 1.8.0 이고, 공개 API·DB 테이블은 변경하지 않는다.
- 2.18 변경 요약(일정 수정 동시성 충돌 방지): 같은 일정을 동시에 수정할 때 나중 요청이 먼저 저장된 변경을 덮어쓰던 문제를 막는다(FR-SCH-005 보강). 일정 조회 응답에 동시성 토큰 `updatedAt`을 포함하고, 수정 요청은 마지막으로 조회한 `updatedAt`을 `expectedUpdatedAt`으로 실어 보낸다. 저장 직전 값이 현재와 다르면(=사이에 누군가 저장) 409로 거절한다. 수정 화면 진입부터 락을 잡지 않는 낙관적 방식이며, DB 스키마는 변경하지 않고 기존 `updated_at` 컬럼을 토큰으로 사용한다(저장 직전 짧은 행 락으로 직렬화). API 주소·요청/응답 성공 구조의 기존 필드는 유지하고 필드·에러만 보강한다.
- 2.17 변경 요약(부서관리자 역할·상태 변경 인가 갭 차단): 부서관리자(`role=ADMIN`이면서 부서장 지정된 사용자)는 사원 계정의 이름·부서만 수정할 수 있고, 역할(role)·계정 상태(accountStatus) 변경은 최고관리자만 가능함을 명시한다(FR-USR-007 보강). 프론트는 이미 화면에서 막고 있으나 Postman·개발자도구 등 직접 API 호출을 백엔드에서도 막는다. `PATCH /api/v1/users/{userId}`에서 최고관리자가 아닌 사용자가 요청한 role/accountStatus가 대상의 현재 값과 실제로 달라지면 403으로 거절하며, 기존 값을 그대로 재전송하는 것은 허용한다. ERD·API 주소·요청/응답 성공 구조는 변경하지 않고 권한 검증만 보강한다.
- 2.16 변경 요약(부서관리자 사용자 관리 접근 정합화): 가입 승인/거절 권한과 사용자 관리 권한을 분리한다. 사용자 목록/상세 조회와 사원 정보 수정은 최고관리자뿐 아니라 부서관리자(`role=ADMIN`)도 할 수 있게 완화한다(FR-USR-007 개정). 단 부서관리자는 사원 계정만 관리할 수 있고 다른 관리자 계정(다른 부서관리자·최고관리자)은 수정할 수 없으며, 어떤 관리자도 자기 자신을 강등/비활성화할 수 없다. 가입 신청 조회/승인/거부는 최고관리자만 가능하도록 유지한다(FR-USR-009). `role=admin`은 관리자 페이지 접근 가능 여부, `isSuperAdmin`은 가입 승인/거절 등 최고관리자 전용 작업 가능 여부로 구분한다. ERD·API 주소·요청/응답 성공 구조는 변경하지 않고 권한 게이트와 에러 케이스만 조정한다.
- 2.15 변경 요약(문의 답변 동시 등록 충돌 처리): 문의당 답변은 한 건(`inquiry_reply.inquiry_id` UNIQUE)인데 두 담당자가 거의 동시에 같은 문의에 답변을 등록하면 나중 요청이 DB UNIQUE 제약에 걸린다. 이를 서버 오류(500)가 아니라 "이미 답변이 등록됨" 업무 충돌(409)로 처리한다고 명시한다(FR-INQ-004 보강). 먼저 저장한 요청만 성공하고 나중 요청은 409로 거부한다. ERD·API 주소·요청/응답 성공 구조는 변경하지 않고 에러 케이스만 보강한다.
- 2.14 변경 요약(로그인 상태 비밀번호 변경 정식화): 로그인한 사용자가 현재 비밀번호를 확인한 뒤 본인 비밀번호를 변경하는 기능을 정식 기능으로 추가한다(FR-USR-013 신설). 프론트에는 이미 구현돼 있으나 명세·백엔드에 누락돼 있던 것을 프론트 구현(`PATCH /api/v1/me/password`, 본문 `currentPassword`·`newPassword`) 기준으로 반영한다. 본인 계정만 변경 가능하고, 새 비밀번호는 회원가입·재설정과 동일한 정책(8~100자)을 적용하며 현재 비밀번호와 같으면 거절한다. 이에 따라 "직접 비밀번호 변경 미제공"이던 4.2 범위 제외·FR-USR-011·사원 계정 화면 서술을 개정한다. 이메일 인증번호 재설정(FR-USR-004)은 그대로 유지하며, 관리자가 타인 비밀번호를 변경하는 기능은 계속 제공하지 않는다. ERD는 변경하지 않는다(`member.password_hash` 재사용).
- 2.13 변경 요약(최고관리자 정의·권한 명시 및 `isSuperAdmin` 응답 필드): 관리자를 부서장 지정 여부로 구분되는 두 성격 — **최고관리자**(`role=ADMIN`이면서 어떤 부서의 manager로도 지정되지 않은 사용자)와 **부서관리자**(`role=ADMIN`이면서 하나 이상의 부서 manager로 지정된 사용자) — 으로 명시한다. 별도 role/플래그를 추가하지 않고 부서장 지정 여부에서 파생하는 개념이다(FR-USR-006 개정). 사용자 관리 및 가입 승인/거절은 최고관리자만 수행할 수 있고, 부서관리자는 `role=ADMIN`이지만 이 권한이 없다(FR-USR-007·009 개정). 최고관리자는 자기 자신을 비활성화하거나 사원으로 강등할 수 없다(FR-USR-007 개정). 프론트가 관리자 유형을 구분할 수 있도록 로그인·내 정보 응답에 최고관리자 여부 `isSuperAdmin`(boolean)을 추가하며, 프론트는 `role=admin`이 아니라 이 값으로 사용자 관리 권한을 판단한다(FR-USR-001·011 개정). ERD·API 주소·요청 형식은 변경하지 않고 응답에 boolean 필드만 추가한다.
- 2.12 변경 요약(부서장 지정 자동 해제): 부서 관리자로 지정된 회원이 사용자 관리에서 사원으로 강등되거나 비활성화되어 지정 자격(`APPROVED`·`ACTIVE`·`ADMIN`)을 잃으면 해당 부서장 지정을 자동으로 해제한다(FR-USR-008 개정). 부서장 미지정(공석)은 기존에도 허용되므로 데이터 정합성에 문제가 없으며, ERD·공개 API는 변경하지 않는다.
- 2.11 변경 요약(변환 스냅샷 불일치 실패 단계): 작업 중 같은 `scope_key`의 Wiki가 바뀌어 반영할 수 없게 된 경우의 실패 단계 `scope_changed`를 신설한다(`NFR-AI-003` 개정). `DR-030`의 버전 확인이 감지하는 상태에 대응하는 값이 없어 기존 다섯 단계로는 기록할 수 없었다. 내부 API 계약은 같은 값을 `failureStage`에 추가한다. DB·공개 API는 변경하지 않는다.
- 2.10 변경 요약(근거 배열 저장 범위 명시): `DR-025`의 근거 배열 중 각주·위치·인용은 반영 전 기계 검증에만 쓰고 저장하지 않으며 저장 대상은 원본문서 ID뿐임을 명시한다. `DR-025`는 반환 계약이고 저장은 `DR-002`·`FR-WIKI-009`가 정하는데, `DR-025`만 떼어 읽으면 네 필드가 모두 저장되는 것으로 읽혀 실제로 오해가 발생했다. 계약·DB·공개 API는 변경하지 않는다.
- 2.9 변경 요약(Wiki 변환 문맥 범위): Wiki 변환 문맥을 사전 선택 5개에서 범위 전체로 넓히고, 백엔드가 검색·본문·관계 조회 수단과 요청 단위 열람 허가를 제공한다. 조회 수단 준비 전까지는 백엔드가 선택한 본문을 전달하는 과도기를 두되 개수 상한은 두지 않는다(FR-WIKI-002 개정). Wiki 본문 전문 검색 색인과 변환 스냅샷 버전 고정을 신설한다(DR-029·DR-030 신설). 변환 직렬화 단위를 전역에서 `scope_key`로 좁히고 범위별 병렬은 버전 확인 배포 후 활성화한다(FR-AI-003, 8절 개정). AI 작업 제한 시간을 문서 크기 비례와 절대 상한으로 고치고 백엔드 대기 시간이 그보다 길어야 함을 명시한다(NFR-PERF-002 개정). `wiki`에 요약·본문 해시·색인 해시 컬럼과 `wiki_search_chunk` 테이블을 추가한다. 공개 API 형식은 변경하지 않는다.
- 2.8 변경 요약(HttpOnly 쿠키 인증): 공개 API 인증은 Bearer 헤더 대신 `AJT_ACCESS_TOKEN` HttpOnly 쿠키를 사용한다. 상태 변경 요청은 CSRF 토큰을 요구하며, CSRF 토큰 발급과 서버 쿠키 만료 로그아웃 API를 추가한다. DB 테이블은 변경하지 않는다.
- 2.7 변경 요약(Wiki 추가·삭제·교체 변환): Wiki 변환은 `document_added`·`document_removed`·`document_replaced` 변경 유형과 삭제·교체 전 파싱 Markdown을 선택·변환 단계 모두에 전달한다. 변환 응답의 Wiki 변경안은 선택 근거를 포함할 수 있고 FastAPI 오류는 실패 단계를 제공한다. 내부 API 소비자는 정의되지 않은 응답 필드를 무시한다. 공개 API·DB 테이블은 변경하지 않는다.
- 2.6 변경 요약(Wiki 변환 문맥 선택): 새 원본문서의 파싱 Markdown과 `index.md`만으로 에이전트가 필요한 Wiki를 먼저 최대 5개 선택하고, 백엔드는 선택 Wiki의 본문과 관계 JSON만 재검증해 변환 단계에 전달한다. FastAPI는 파일 경로·DB에 직접 접근하지 않으며 공개 API·DB 테이블은 변경하지 않는다.
- 2.5 변경 요약(사원 와이어프레임 정합성): 아이디 찾기·사원 검색·본인 정보 수정·직접 비밀번호 변경을 제공하지 않고 내 정보는 조회 전용으로 확정한다. 가입 화면에서는 사번을 받지 않으며 가입 승인 시 시스템이 사번을 생성하고, 비로그인 가입용 부서 목록을 제공한다. 질문은 `conversationId` 기반 멀티턴으로 변경한다. 문의 담당자 후보는 모든 승인·활성 관리자로 확대하고 이름과 소속 부서를 표시한다. 일정의 별도 첨부파일을 제거하고 일정 원본문서는 관리자에게만 제공한다.
- 2.4 변경 요약(가입 승인·관리자·문의 정합성): 회원가입은 승인 대기 상태로 접수하고 관리자가 승인 또는 거부하며 거부 계정은 보존한다. 거부 이메일로 다시 가입하면 기존 계정을 승인 대기로 갱신한다. 최초 전체 관리자와 이후 부서 관리자는 동일한 관리자 역할을 사용하며 부서 관리자는 부서 관리 화면에서만 지정한다. 문의 등록자가 담당자를 직접 선택하는 구조를 도입했으며 후보 범위는 2.5에서 모든 승인·활성 관리자로 확대했다.
- 2.3 변경 요약(개발 착수 전 최종 정합성): MySQL 8.4 LTS와 권장 컬럼 타입을 확정하고, 파일 배열 업로드를 파일당 20MB·최대 20개·총 100MB로 제한한다. 질문은 AI가 Wiki·일정·혼합으로 자동 분류하며 `index.md`·일정 요약을 이용한 자료 선택과 선택 본문을 이용한 답변 생성의 2단계로 처리한다. Wiki 링크·관계 정합성은 백엔드가 반영 전에 검증한다. 문서 취소 상태, 일정 동기 추출, 필수 문의 우선순위와 다운로드 권한 정책을 API·ERD와 일치시킨다.
- 2.2 변경 요약(MVP 구조 단순화): 개발 기간 1주일 기준으로 부서 조합을 숫자형 Wiki 공간 ID 대신 정렬된 `scope_key`로 관리하고, 파일 경로는 업무 테이블에 직접 저장한다. 원본문서 카테고리는 관리자가, Wiki 카테고리는 AI 에이전트가 관리한다. 에이전트 채팅은 작업 화면이 아닌 Wiki 상세 화면에서 제공한다. 일정 거부 초안은 보존하지 않고 삭제하며, 질문 답변 출처는 Wiki 또는 일정 FK로 저장한다. Wiki 질문은 Wiki만 검색하고 연결 원본문서는 Wiki의 근거 자료로 표시한다. AI 작업의 문서 순서·결과는 `ai_job` JSON 컬럼에 저장하고, 문의 이미지 메타데이터는 문의 테이블 JSON 컬럼에 저장한다.

## 1. 문서 목적

본 문서는 사내에 흩어진 공지, 규정, 인수인계 문서와 교육 자료를 LLM Wiki로 재구성하고, 전체·부서·개인 일정을 관리하며, 권한에 맞는 지식과 일정에 대해 챗봇으로 질의응답하는 서비스의 초기 요구사항을 정의한다.

## 2. 프로젝트 개요

관리자는 위키 원본 문서와 일정 문서를 분리하여 업로드한다. 위키 원본문서는 관리자가 카테고리와 전체 또는 하나 이상의 부서를 선택하며, 시스템은 선택 부서 ID를 정렬한 `scope_key`에 해당하는 독립 Wiki 공간에 문서를 저장한다. 위키 편집자 에이전트(이하 에이전트)는 같은 `scope_key`의 현재 Wiki와 문서를 1건씩 순서대로 분석하여 생성·수정·병합·제거를 수행하고 결과를 즉시 반영하며 Wiki 카테고리도 관리한다. 관리자는 문서별 작업 요약을 확인하고 보완이 필요한 Wiki 상세 화면에서 에이전트에게 수정 요청한다. 일정 문서는 일정 초안 생성에만 사용되며 관리자가 승인한 일정만 사용자에게 공개된다. 사원은 권한 내 문서·Wiki·일정만 조회하고 챗봇 답변의 근거를 확인한다.

| FR-USR-004 | 이메일 비밀번호 재설정 | 사용자는 계정에 등록된 이메일로 받은 6자리 인증번호로 비밀번호를 재설정할 수 있어야 한다. | 이메일 등록 여부와 관계없이 동일한 응답을 반환한다. 인증번호는 5분간 유효하고 틀린 시도 5회 초과 시 폐기하며, 변경 완료 후 자동 로그인하지 않는다. 인증번호는 DB에 저장하지 않고 서버 메모리에 보관하며 저장용 테이블·컬럼을 추가하지 않는다. | 필수 |
| FR-USR-005 | 세션 만료 | 시스템은 일정 시간 활동이 없는 사용자의 세션을 만료해야 한다. | 만료 시간은 상세설계에서 설정한다. | 권장 |
| FR-USR-006 | 역할 관리 | 시스템은 사용자 역할을 관리자와 사원으로 구분하고, 관리자는 부서장 지정 여부로 최고관리자와 부서관리자를 구분해야 한다. | 역할 값은 관리자, 사원 두 가지이다. 시스템 개발자가 제공하는 최초 전체 관리자와 이후 지정되는 부서 관리자는 모두 같은 `ADMIN` 역할이며 별도 전체 관리자 역할·플래그를 두지 않는다. `ADMIN` 안에서 **최고관리자**는 어떤 부서의 manager로도 지정되지 않은 사용자이고, **부서관리자**는 하나 이상의 부서 manager로 지정된 사용자이다. 이 구분은 role이 아니라 부서장 지정 여부에서 파생하며, 별도 role·컬럼·플래그를 추가하지 않는다. | 필수 |
| FR-USR-007 | 사용자 관리 | **관리자(최고관리자·부서관리자)** 는 승인된 사용자 계정을 조회·수정하고 역할, 소속 부서, 계정 상태를 관리할 수 있어야 한다. | 최고관리자와 부서관리자 모두 사용자 관리 화면에 접근해 승인된 사용자 목록·상세를 조회할 수 있다. 부서관리자는 사원 계정만 관리할 수 있고 다른 관리자 계정(다른 부서관리자·최고관리자)은 수정할 수 없다. 또한 부서관리자는 사원 계정의 이름과 소속 부서만 수정할 수 있으며, 역할(role)과 계정 상태(accountStatus) 변경은 최고관리자만 가능하다. 프론트가 화면에서 막더라도 부서관리자가 직접 API 호출로 사원의 역할·계정 상태 변경을 시도하면 서버가 403으로 거절한다(요청 값이 대상의 현재 값과 실제로 달라질 때만 거절하며, 기존 값을 그대로 재전송하는 것은 허용한다). 최고관리자는 부서관리자를 사원으로 강등하거나 비활성화할 수 있다. 어떤 관리자도 자기 자신의 역할을 사원으로 강등하거나 자기 자신을 비활성화할 수 없다. 계정 상태 값은 활성화, 비활성화 두 가지이며 비활성화 계정은 로그인할 수 없다. 관리자가 비밀번호를 직접 변경하는 기능과 사용자 계정 삭제 기능은 제공하지 않는다. (가입 신청 조회·승인·거부는 최고관리자만 가능 — FR-USR-009) | 필수 |
| FR-USR-008 | 부서 관리 | 관리자는 부서를 생성·조회·수정·삭제하고 부서 관리 화면에서 부서별 관리자 1명을 지정 또는 해제할 수 있어야 한다. | 부서 관리자는 `APPROVED`·`ACTIVE` 상태의 `ADMIN` 중 선택한다. 한 부서는 관리자 최대 1명, 한 관리자는 부서 최대 1개를 담당하며 관리자 미지정도 허용한다. 부서 관리자가 사용자 관리에서 사원으로 강등되거나 비활성화되어 지정 자격(`APPROVED`·`ACTIVE`·`ADMIN`)을 잃으면 해당 부서장 지정은 자동으로 해제된다. 직원이 1명이라도 소속되거나 다른 데이터가 참조하는 부서는 삭제할 수 없다. | 필수 |
| FR-USR-009 | 가입 신청 관리 | **최고관리자**는 가입 신청을 가입 상태별로 조회하고 승인 또는 거부할 수 있어야 한다. | 가입 신청 조회·승인·거부는 최고관리자만 수행할 수 있으며, 부서관리자는 `role=ADMIN`이지만 이 권한이 없다. 가입 승인 시 시스템은 중복되지 않는 사번을 생성하고 `PENDING`에서 `APPROVED`·`ACTIVE`로 전환한다. 거부 시 `REJECTED`·`INACTIVE`로 전환해 행을 보존한다. `PENDING`이 아닌 신청의 승인·거부 요청은 충돌로 처리한다. | 필수 |
| FR-USR-010 | 가입용 부서 조회 | 시스템은 로그인 전 회원가입 화면에 가입 가능한 부서 목록을 제공해야 한다. | 인증 없이 부서 ID와 이름만 반환하며 관리자와 직원 정보는 노출하지 않는다. | 필수 |
| FR-USR-011 | 내 정보 조회 | 로그인한 사용자는 본인의 이름, 이메일, 부서, 사번, 역할, 가입 상태, 계정 상태와 최고관리자 여부를 조회할 수 있어야 한다. | 조회 전용이며 본인 정보(이름·이메일·부서) 수정과 사원 검색 기능은 제공하지 않는다(본인 비밀번호 변경은 FR-USR-013으로 제공). 응답에는 최고관리자 여부 `isSuperAdmin`(boolean)을 포함하며, 프론트는 새로고침 후 이 값으로 사용자 관리 메뉴/접근 권한을 복원한다. 프론트는 `role=admin`만으로 사용자 관리 권한을 판단하지 않고 `isSuperAdmin` 값으로 판단한다. | 필수 |
| FR-USR-012 | CSRF 토큰 발급 | 시스템은 프론트엔드가 상태 변경 요청에 사용할 CSRF 토큰을 발급해야 한다. | `XSRF-TOKEN` 쿠키는 JavaScript가 읽을 수 있으나 인증 정보가 아니며, POST·PUT·PATCH·DELETE 요청은 같은 값을 `X-XSRF-TOKEN` 헤더로 보내야 한다. | 필수 |
| FR-USR-013 | 로그인 상태 비밀번호 변경 | 로그인한 사용자는 현재 비밀번호를 확인한 뒤 본인 비밀번호를 변경할 수 있어야 한다. | 본인 계정만 변경할 수 있으며 대상 사용자를 지정하는 입력은 받지 않는다(인증 주체의 계정에만 적용). 현재 비밀번호가 일치해야 변경하며, 불일치 시 거부한다. 새 비밀번호는 회원가입·재설정과 동일한 정책(8자 이상 100자 이하)을 적용하고 현재 비밀번호와 같으면 거부한다. 새 비밀번호는 암호화해 저장한다. 비활성·미승인 계정은 로그인할 수 없으므로 이 기능에 접근할 수 없다. 이메일 인증번호 재설정(FR-USR-004)과는 별개 기능으로 함께 제공한다. MVP에서는 변경 후 현재 세션을 유지한다. | 필수 |

### 권한 및 공개 범위

| ID | 기능명 | 요구사항 | 예외/조건 | 우선순위 |
| --- | --- | --- | --- | --- |
| FR-ACL-001 | 역할 기반 접근 제어 | 시스템은 역할에 따라 접근 가능한 화면과 API를 제한해야 한다. | 권한 없는 메뉴는 표시하지 않고 권한 없는 API 요청은 거부한다. | 필수 |
| FR-ACL-002 | 사원 데이터 접근 | 사원은 전체 공개 자료와 본인 소속 부서에 공개된 문서·Wiki·일정만 조회할 수 있어야 한다. | 권한 없는 자료는 목록, 검색, 상세, 다운로드와 챗봇에서 제외한다. | 필수 |
| FR-ACL-003 | 관리자 업로드 권한 | 모든 관리자는 본인의 소속 부서와 관계없이 위키 원본 문서와 일정 문서를 업로드할 수 있어야 한다. | 관리자 소속 부서는 업로드 가능 범위를 제한하지 않는다. | 필수 |
| FR-ACL-004 | 공개 범위 지정 | 관리자는 위키 원본문서 업로드 시 공개 범위를 전체 또는 하나 이상의 부서로 선택할 수 있어야 한다. | 시스템은 전체를 `ALL`로, 부서를 선택한 경우 중복 제거 후 오름차순으로 정렬한 부서 ID 조합을 `scope_key`로 저장한다. 예: 부서 1·2는 `D1-D2`이다. | 필수 |
| FR-ACL-005 | Wiki 공개 범위 | 시스템은 같은 `scope_key`의 원본문서와 Wiki를 하나의 독립 Wiki 공간으로 관리해야 한다. | 같은 부서 조합은 기존 공간을 재사용하고 다른 조합의 문서·Wiki와 섞지 않는다. 사용자는 전체 공간과 자신의 부서 ID를 포함한 공간에 접근할 수 있다. | 필수 |
| FR-ACL-006 | 권한 정보 비노출 | 시스템은 사용자에게 권한이 없는 자료의 제목, 요약, 존재 여부를 노출하지 않아야 한다. | 챗봇 답변과 연관 Wiki·문서 안내에도 동일하게 적용한다. | 필수 |

### 문서 업로드 및 처리

| ID | 기능명 | 요구사항 | 예외/조건 | 우선순위 |
| --- | --- | --- | --- | --- |
| FR-DOC-001 | 파일 검증 | 시스템은 업로드 시 파일 형식, 개수, 개별 크기와 요청당 총 파일 크기를 검증해야 한다. | 파일 한 개는 최대 20MB, 파일 배열은 최대 20개이며 총 파일 크기는 최대 100MB이다. 문의 이미지는 최대 5개, 일정 원본문서는 한 요청에 1개로 제한한다. | 필수 |
| FR-DOC-002 | 위키 원본문서 업로드 | 관리자는 Wiki 생성에 사용할 사내 자료를 일정 문서와 분리된 화면에서 하나 이상 업로드할 수 있어야 한다. | 업로드 시 카테고리와 공개 범위를 직접 지정한다. 지원 형식은 TXT, MD, PDF, DOCX이며 한 번에 최대 20건·총 100MB, 파일당 최대 20MB이다. | 필수 |
| FR-DOC-003 | 일정 문서 업로드 | 관리자는 일정 추출에 사용할 문서를 Wiki 자료와 분리된 화면에서 한 번에 1개 업로드할 수 있어야 한다. | 지원 형식은 TXT, MD, DOCX, PDF, CSV, XLSX이며 최대 20MB이다. 일정 원본문서는 `document` 테이블에 저장하지 않고, 추출된 일정 행에 동일한 원본·파싱 파일 경로와 `source_group_key`를 저장한다. 일정 문서는 Wiki 생성, 일반 문서 검색과 Wiki 챗봇 근거로 사용하지 않는다. | 필수 |
| FR-DOC-004 | 위키 원본문서 메타데이터 | 시스템은 위키 원본문서의 메타데이터를 DB에 저장해야 한다. | 저장 항목은 문서 ID, 원본 파일명, 업로드자, 업로드 시각, 관리자 지정 카테고리, `scope_key`, 원본·파싱 파일 경로, MIME 타입, 파일 크기, 처리 상태, 실패 사유와 연결 Wiki ID JSON이다. | 필수 |
| FR-DOC-005 | 텍스트 추출 | 시스템은 업로드한 문서에서 텍스트를 추출해야 한다. | PDF·DOCX는 문서에서 텍스트를 추출하고, TXT·MD는 원문 텍스트를 그대로 사용한다. | 필수 |
| FR-DOC-014 | OCR 대체 추출 | 시스템은 텍스트 추출 결과가 없거나 이미지 기반으로 판단되는 PDF·DOCX에 OCR을 적용해 텍스트를 추출해야 한다. | OCR로도 텍스트를 확보할 수 없으면 실패 상태와 사유를 저장한다. OCR은 파싱 단계의 내부 처리이며 별도 처리 상태로 구분하지 않는다. | 필수 |
| FR-DOC-006 | 원본문서 카테고리 관리 | 관리자는 `scope_key`별 원본문서 카테고리를 생성·수정·삭제할 수 있어야 한다. | 원본문서 카테고리는 관리자가 관리하며 Wiki 카테고리는 에이전트가 별도로 관리한다. 카테고리는 파일 경로에 포함하지 않고 DB에만 저장한다. | 필수 |
| FR-DOC-007 | 카테고리 수동 지정 | 관리자는 문서 업로드 또는 메타데이터 수정 시 카테고리를 직접 지정해야 한다. | AI 자동 카테고리 분류는 제공하지 않는다. | 필수 |
| FR-DOC-008 | 공개 범위 수정 | 관리자는 문서의 전체·부서 공개 범위를 수정할 수 있어야 한다. | 새 `scope_key`의 카테고리를 다시 지정하고 문서 파일을 새 범위로 이동한 뒤, 기존 범위와 새 범위의 Wiki를 각각 최신 원본문서 기준으로 재처리한다. 변경 후 권한이 사라진 사용자는 해당 자료에 접근할 수 없다. | 필수 |
| FR-DOC-009 | 문서 처리 상태 | 시스템은 문서의 처리 상태를 관리하고 관리자가 확인할 수 있도록 표시해야 한다. | 상태는 업로드 완료, 파싱 중, 처리 중, 처리 완료, 실패, 취소로 관리한다. 파싱·AI 처리 실패는 실패 상태와 실패 사유로 구분하며 OCR은 파싱 단계 내부 처리로 별도 상태를 노출하지 않는다. | 필수 |
| FR-DOC-010 | 문서 검색 | 사용자는 권한이 있는 위키 원본 문서를 키워드, 파일 형식, 부서, 카테고리, 업로드 기간으로 검색할 수 있어야 한다. | 일정 문서는 일반 문서 검색 결과에 포함하지 않는다. | 필수 |

| DR-016 | 파일 경로 관리 | `/data/ajt`를 제외한 현재 상대 경로를 `document`, `wiki`, `wiki_scope`, `schedule` 테이블과 문의 첨부파일 JSON에 저장한다. 일정은 원본문서·파싱 파일 경로만 저장하며 별도 첨부 기능이 없으므로 `schedule`에는 `attachment_refs` 컬럼을 두지 않는다. 사용자 입력 파일명은 경로 구성에 사용하지 않는다. |
| DR-014 | 삭제 정책 | 사용자 계정과 거부된 가입 신청은 삭제하지 않는다. 승인된 사용자 계정은 계정 상태를 비활성화하고, 거부된 가입 신청은 `REJECTED` 상태로 보존한다. 문서, Wiki, 일정, 문의사항, 문의 답변과 카테고리 등 삭제 기능이 제공되는 나머지 업무 데이터는 관련 파일과 관계 데이터를 포함해 하드 삭제한다. NFR-LOG-001의 보존 대상 이력 데이터는 업무 데이터 삭제와 별도로 보존한다. |
| DR-013 | Wiki 본문 형식 | Wiki 본문은 Markdown 형식의 파일로 저장하며, 목차 파일명은 index.md로 한다. |
| DR-012 | 버전 미보존 | 기존 파일을 승인 안전성 확보를 위해 잠시 유지할 수 있으나 과거 버전 조회·복원용으로 제공하거나 영구 보존하지 않는다. |
| DR-018 | Wiki 범위 키 | 전체 Wiki는 `ALL`, 부서 Wiki는 중복 제거 후 오름차순으로 정렬한 부서 ID를 `D{id}` 형식으로 연결한 `scope_key`로 식별한다. `wiki_scope`에는 공개 유형, 부서 ID JSON과 현재 목차 경로를 저장하며 문서·Wiki·카테고리·AI 작업이 같은 키를 참조한다. 문서 공개 부서는 별도 관계 테이블에 중복 저장하지 않고 `document.scope_key`로 연결된 `wiki_scope.department_refs`를 기준으로 판단한다. |
| DR-019 | 카테고리 관리 주체 | 원본문서 카테고리는 관리자가, Wiki 카테고리는 에이전트가 `scope_key`별로 관리한다. 카테고리 이름과 설명은 DB에 저장하고 파일 경로에는 포함하지 않는다. |
| DR-020 | 문의 첨부파일 JSON | 문의 첨부 이미지의 원래 파일명, 상대 경로, MIME 타입과 크기는 문의 테이블 JSON 컬럼에 저장한다. PNG, JPG, JPEG를 최대 5개까지 허용하며 파일당 최대 20MB·요청당 총 100MB로 제한한다. |
| DR-021 | 답변 출처 저장 | 답변 하나는 `answer_source` 행을 여러 개 가질 수 있다. 각 행 생성 시 `wiki_id`, `schedule_id` 중 정확히 하나만 저장하고 출처 제목 스냅샷을 함께 저장한다. Wiki의 원본문서는 `answer_source`에 저장하지 않고 `wiki.document_refs`로 조회한다. 이후 Wiki 또는 일정이 하드 삭제되면 해당 FK는 `NULL`로 바꾸되 제목 스냅샷은 질문 이력 보존 기간 동안 유지한다. |
| DR-022 | 데이터베이스와 컬럼 타입 | 업무 DB는 MySQL 8.4 LTS를 사용한다. PK·FK는 `BIGINT UNSIGNED`, 시간은 UTC `DATETIME(6)`, 애플리케이션 상태는 `VARCHAR(30)`, 파일 경로는 `VARCHAR(500)`, 본문은 `TEXT`, 관계·첨부·작업 결과는 `JSON`으로 저장한다. PK는 자동 증가를 사용하고 비밀번호는 `password_hash`에 해시만 저장한다. |
| DR-023 | 질문 자료 선택 | Spring Boot는 사용자가 접근 가능한 공간별 `index.md` 내용과 승인 일정·본인 개인 일정의 요약만 1차 AI 요청에 전달한다. AI가 반환한 Wiki·일정 ID를 재검증한 뒤 선택한 Markdown 본문과 일정 내용만 2차 AI 요청에 전달한다. `MIXED` 질문은 두 종류를 모두 전달하고 `answer_source`에 함께 저장할 수 있다. |
| DR-026 | 가입 상태 저장 | `member`는 역할·계정 상태와 별도로 `signup_status`를 저장한다. 신규·재신청, 승인, 거부 상태 전환은 같은 회원 행에서 수행하며 거부 행을 재신청 시 재사용한다. |
| DR-027 | 문의 담당자 저장 | `inquiry.assignee_id`는 문의 등록자가 선택한 담당자 회원 ID를 저장한다. 문의에는 대상 부서 FK를 저장하지 않는다. 미처리 문의가 남은 담당자의 비활성화 또는 사원 전환은 충돌로 거부한다. |
| DR-028 | 질문 대화 저장 | `ai_question`은 대화를 식별하는 `conversation_key`를 저장한다. 같은 키의 질문은 생성 시점 순서로 묶으며 백엔드는 로그인한 사용자 본인의 대화만 조회하고 AI 문맥으로 전달한다. |
| DR-024 | Wiki 채팅 보존 | Wiki가 하드 삭제되어도 최소 1년의 채팅 보존 정책을 지킬 수 있도록 `wiki_chat_message.wiki_id`는 삭제 시 `NULL`로 바꾸고 `wiki_title_snapshot`은 유지한다. 새 메시지는 생성 시점의 Wiki 제목을 함께 저장한다. |
| DR-025 | AI Wiki 변경 계약 | FastAPI는 DB 명령과 실제 파일 경로 대신 `summary`, `categoryChanges`, `wikiChanges`, `relationChanges`, `indexEntries`로 구성된 변경 목록을 반환한다. `wikiChanges`는 선택적으로 원본문서 ID·각주·위치·인용으로 구성된 근거 배열을 포함할 수 있다. 근거 배열의 각주·위치·인용은 반영 전 기계 검증(FR-WIKI-001, NFR-AI-002)에만 쓰고 저장하지 않으며, 저장되는 것은 원본문서 ID뿐이다(DR-002, FR-WIKI-009). 새 Wiki·카테고리는 임시 참조를 사용하며 백엔드가 실제 ID와 경로로 치환한다. Wiki 병합은 대상 Wiki 수정, 병합 원본 삭제와 관계 이동의 조합으로 표현한다. 내부 API 소비자는 정의되지 않은 응답 필드를 무시한다. |
| DR-029 | Wiki 본문 검색 색인 | Wiki 본문 전문 검색을 위해 파생 검색 테이블을 둔다. Wiki ID, `scope_key`, 청크 순서, 헤더 경로, 청크 본문, 본문 해시와 색인 시각을 저장하고 한국어를 포함한 본문에 2글자 단위 전문 검색 색인을 적용한다. Markdown 파일이 정본이며 이 테이블은 정본에서 언제든 재생성할 수 있는 파생 데이터다. 반영이 완료된 Wiki만 색인하고 작업 공간의 검증 전 내용은 색인하지 않는다(DR-006). 사원 Wiki 검색과 에이전트 문맥 조회는 같은 색인을 사용하되 각자의 권한 검증을 통과한 뒤 조회한다. `wiki`는 현재 본문 해시와 색인이 반영한 본문 해시를 함께 저장해 색인이 낡았는지 판별한다. |
| DR-030 | 변환 스냅샷 버전 고정 | `wiki_scope`는 그 공간의 Wiki가 바뀔 때마다 같은 트랜잭션에서 증가하는 버전 번호를 저장한다. 과거 버전 조회·복원 용도가 아니라 변경 감지용이다. 백엔드는 변환 요청 시작에 현재 버전을 발급하고 반영 직전에 같은 값인지 확인해, 그 사이 같은 공간의 Wiki가 바뀌었으면 반영하지 않고 실패 또는 재처리 대상으로 기록한다. 버전 확인을 위해 DB 트랜잭션을 변환 실행 시간 동안 열어 두지 않는다. |

## 8. 확정 정책 요약

| 항목 | 확정 내용 |
| --- | --- |
| 관리자 권한 | 최초 전체 관리자와 이후 부서 관리자는 모두 같은 관리자 역할을 사용하며 별도 전체 관리자 역할·플래그를 두지 않는다. 모든 관리자는 소속 부서와 관계없이 문서를 업로드하고 공개 범위를 선택할 수 있다. |
| 공개 범위 | 전체 또는 하나 이상의 부서를 선택한다. 시스템은 선택 부서 ID를 정렬한 `scope_key`를 만들고 사원은 전체 및 자신의 부서 ID가 포함된 범위에 접근한다. |
| Wiki 공개 범위 | 같은 `scope_key`의 원본문서와 Wiki는 하나의 독립 공간을 공유한다. 같은 부서 조합은 기존 공간을 재사용하고 다른 조합과 섞지 않는다. |
| Wiki 반영 방식 | 사전 승인 절차를 두지 않는다. 에이전트가 문서 1건을 변환하면 즉시 Wiki에 반영하고, 관리자는 문서별 작업 요약을 확인한 뒤 필요 시 채팅으로 수정을 요청한다. |
| 일정 승인 단위 | Wiki와 달리 일정은 초안 1건 단위로 승인·거부한다. 한 문서에서 여러 일정이 추출된 경우 일부만 승인할 수 있다. |
| Wiki 운영 | 에이전트가 같은 `scope_key`의 전체 구조를 분석해 Wiki와 Wiki 카테고리의 생성·수정·병합·제거를 수행하며 관리자는 Wiki 상세 화면의 자연어 채팅으로 사후 수정한다. 삭제된 Wiki 복구는 제공하지 않는다. |
| 처리 순서 | AI 작업은 같은 `scope_key` 안에서 직렬로 실행하고 묶음 내에서도 업로드 순서대로 문서 1건씩 진행한다. 서로 다른 `scope_key`는 병렬로 실행할 수 있으며 전체 동시 실행 수에 상한을 둔다. |
| 관계 저장 | Wiki-원본문서, Wiki-Wiki 관계 모두 무방향으로 관리하며, 관련된 각 테이블(Wiki 테이블·문서 테이블)의 JSON 컬럼에 양쪽 ID를 함께 기록한다. |
| 출처 단위 | 답변에는 사용한 Wiki 또는 일정을 여러 개 표시한다. Wiki 출처의 원본문서는 Wiki 아래의 하위 근거로 표시하며 Wiki-문서 관계는 문서 전체 단위로 관리한다. |
| 질문 처리 | 같은 `conversationId`의 이전 질문·답변을 이어가는 멀티턴으로 처리한다. AI가 질문을 Wiki·일정·혼합으로 자동 분류하고 `index.md`와 일정 요약으로 자료를 선택한 뒤 백엔드가 선택 ID를 재검증하고 본문을 전달해 답변을 생성한다. |
| 저장 및 반영 | 변환 결과는 `/data/ajt/work/{jobId}`에서 작성·검증한 뒤 로컬 파일 이동·교체 방식으로 반영한다. 성공 작업 공간은 즉시, 실패·중단 작업 공간은 3일 후 삭제한다. |
| 로그 | 질문 이력, AI 작업·문서별 결과 JSON과 Wiki 상세 채팅을 DB에 저장한다. 일정 변경과 문의 처리의 별도 감사 이력은 MVP에서 제공하지 않는다. |
| 일정 | 일정 문서는 별도 업로드하며 승인된 초안만 공개하고 거부 초안은 삭제한다. 별도 첨부 기능은 없고 원본문서·파싱 파일만 관리자에게 제공한다. 관리자는 전체·부서 일정을, 사원은 개인 일정을 CRUD한다. |
| 가입 승인 | 회원가입은 사번 없이 승인 대기로 저장한다. 관리자가 승인하면 시스템이 사번을 생성하고 활성 계정으로 전환한다. 거부하면 행을 보존하며 거부 이메일의 재신청은 기존 행을 승인 대기로 갱신한다. |
| 사원 계정 화면 | 아이디 찾기·사원 검색·본인 정보(이름·이메일·부서) 수정은 제공하지 않는다. 내 정보는 조회 전용이며, 비밀번호는 로그인 상태에서 현재 비밀번호 확인 후 변경(FR-USR-013)하거나 로그인 불가 시 이메일 인증번호 재설정(FR-USR-004)으로 변경한다. |
| 문의사항 | 사원은 모든 승인·활성 관리자 중 담당자 1명을 이름과 소속 부서를 보고 선택한다. 지정 담당자만 조회·답변하며 답변 삭제 시 문의는 대기 상태로 돌아간다. 처리 이력·이메일 알림·답변 임시 저장·담당자 변경은 제공하지 않는다. |
| 카테고리 | 원본문서 카테고리는 관리자가, Wiki 카테고리는 에이전트가 `scope_key`별로 관리한다. |
| 데이터베이스 | MySQL 8.4 LTS를 사용하며 파일 본문은 DB가 아닌 `/data/ajt`에 저장한다. |
| 제외 기능 | Mattermost, 긴급 일정, 휴지통·복원, Wiki 비공개 전환, Git/JGit 및 버전관리는 제공하지 않는다. |

## 9. 상세설계 또는 추가 정책 결정 항목

| 항목 | 설명 |
| --- | --- |
| 검색 구현 기술 | index.md는 현재 Wiki 목차로 유지하지만 QMD, 벡터 DB, 전문 검색 엔진 등 구체적인 검색 구현 기술은 상세설계에서 선택한다. |
| OCR 엔진 및 품질 기준 | 스캔 문서에 OCR을 적용한다는 원칙은 확정되었으나 구체적인 OCR 엔진, 지원 언어, 인식률 기준과 저품질 스캔 처리 방식은 상세설계에서 정한다. |
| 문의 담당자 유효성 | 문의 등록 시 `APPROVED`·`ACTIVE` 상태의 모든 `ADMIN`을 담당자로 선택할 수 있다. 부서 관리자 지정 여부는 후보 조건에 사용하지 않으며 등록 후 담당자 관계는 고정한다. |

## 10. 인수 기준 요약

- 관리자가 위키 원본문서를 여러 건 업로드하고 전체 또는 복수 부서를 선택하면 동일한 부서 조합의 `scope_key` Wiki 공간을 생성 또는 재사용할 수 있다.
- 에이전트가 같은 `scope_key`의 현재 Wiki와 새 문서를 기반으로 Wiki·Wiki 카테고리의 생성·수정·병합·제거 및 관계 변경을 수행하고 즉시 반영할 수 있다.
- 관리자가 문서별 작업 요약을 확인하고 Wiki 상세 화면에서 수정 요청하면 에이전트가 해당 Wiki를 수정해 반영할 수 있다.
- 변환 중인 문서분은 반영이 끝나기 전까지 사원과 챗봇에 노출되지 않고, 진행 상태는 서버 재시작 후에도 유지된다.
- 작업 공간의 결과 검증이 실패하면 기존 Wiki가 유지되고 작업은 실패 사유와 함께 재처리 대상으로 표시된다.
- Wiki-원본문서 관계와 Wiki-Wiki 관계 모두 무방향으로 관리되며, Wiki 테이블과 문서 테이블 양쪽의 JSON 컬럼에 서로의 ID가 함께 저장되고 일관되게 유지된다.
- 원본문서 상세 화면에서 그 문서를 근거로 한 Wiki 목록을 확인할 수 있다(권한 없는 Wiki는 제외).
- 사원과 챗봇은 사용자가 접근 가능한 문서·Wiki·일정만 조회하며 권한 없는 자료의 존재도 노출되지 않는다.
- 질문 유형을 전달하지 않아도 에이전트가 Wiki·일정·혼합 질문을 자동 판단하고, 혼합 질문에는 검증된 Wiki와 일정 출처가 함께 표시된다.
- 첫 질문에서 생성된 `conversationId`를 후속 질문에 전달하면 같은 대화의 이전 질문·답변을 문맥으로 사용하고, ID를 생략하면 새 대화를 시작할 수 있다.
- 일정 문서에서 생성된 일정 초안은 관리자 승인 후에만 공개되고 일정 문서 원본은 사원에게 보이지 않는다.
- 일정에는 별도 첨부 기능이 없으며 관리자만 추출 일정의 원본문서를 조회할 수 있다.
- 한 일정 문서에서 여러 일정이 추출되며 관리자가 일부만 승인하면 거부한 나머지 초안은 하드 삭제된다.
- 관리자는 전체·부서 일정을 직접 관리하고 사원은 본인 개인 일정을 관리한다.
- Wiki 상세 대화와 AI 작업·문서별 결과 JSON은 DB에 저장되고 에이전트는 관련 기록만 사용한다.
- 이미지 기반 스캔 PDF·DOCX 문서는 OCR을 통해 텍스트가 추출되어 위키 원본 문서로 활용될 수 있다.
- 신규 회원가입은 사번 입력 없이 승인 대기로 저장되고 승인 시 시스템이 중복되지 않는 사번을 생성한다. 승인된 계정만 로그인할 수 있고, 거부된 가입 정보는 보존되며 같은 이메일로 재신청하면 기존 행이 승인 대기로 갱신된다.
- 로그인 전 가입 화면에서 부서 ID와 이름만 조회할 수 있고, 로그인한 사용자는 조회 전용 내 정보 화면에서 본인 계정을 확인할 수 있다.
- 최초 전체 관리자와 부서 관리자는 같은 관리자 역할을 사용하고, 부서 관리자는 부서 관리 화면에서 지정하거나 해제하며, 사용자 관리에서 사원으로 강등되거나 비활성화되면 해당 부서장 지정은 자동으로 해제된다.
- 사원이 모든 승인·활성 관리자 중 이름과 소속 부서를 확인해 담당자 1명을 선택하면 해당 담당자에게만 문의가 표시되고, 담당자의 답변으로 처리 완료된다.
- 여러 문서를 한 번에 업로드하면 에이전트가 문서 1건씩 순서대로 변환·반영하고 문서마다 작업 요약을 제공한다. 특정 문서 변환이 실패해도 나머지 문서 처리는 계속되고 실패 문서만 반영되지 않는다.
