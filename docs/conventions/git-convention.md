# Git Convention

# Git 브랜치·커밋·PR 컨벤션

> Jira 프로젝트 키: `S15P11B106`
> 
> 
> 기본 작업 브랜치: `develop`
> 
> 병합 방식: `Squash merge`
> 

## 1. 전체 작업 순서

모든 작업은 다음 순서로 진행한다.

```
Jira 티켓 생성
→ develop에서 작업 브랜치 생성
→ 개발 및 커밋
→ Pull Request 생성
→ 코드 리뷰
→ Squash merge
→ 작업 브랜치 삭제
```

운영 중인 서비스에 긴급한 문제가 발생한 경우에만 `master`에서 `hotfix` 브랜치를 생성한다.

`master`과 `develop`에는 직접 push하지 않는다.

---

## 2. **Branch Naming Convention**

### 브랜치 종류

| 브랜치 | 용도 |
| --- | --- |
| `master` | 실제 배포 가능한 코드 |
| `develop` | 다음 배포에 포함할 작업을 모으는 브랜치 |
| `feature/*` | 새로운 기능 개발 |
| `fix/*` | 개발 중 발견된 버그 수정 |
| `refactor/*` | 기능 변경 없이 코드 구조 개선 |
| `release/*` | 배포 전 최종 확인 및 버전 준비 |
| `hotfix/*` | 운영 환경의 긴급 오류 수정 |

### 브랜치 이름 ⭐

```
<브랜치 종류>/<Jira 이슈 키>-<작업 설명>
```

예시:

```
feature/S15P11B106-12-user-login
fix/S15P11B106-15-duplicate-nickname
refactor/S15P11B106-20-user-service
release/v1.0.0
hotfix/S15P11B106-30-login-error
```

작성 규칙:

- 기능 개발은 `feat/`가 아니라 `feature/`를 사용한다.
- Jira 이슈 키는 대문자를 그대로 사용한다.
- 작업 설명은 영어 소문자와 하이픈()으로 작성한다.
- 브랜치 이름에 작업자 이름이나 닉네임을 넣지 않는다.
- 하나의 브랜치에는 하나의 작업만 포함한다.

### 일반 작업 브랜치 생성

일반 작업은 최신 `develop`에서 시작한다.

```bash
git switch develop
git pull origin develop
git switch -c feature/S15P11B106-12-user-login
```

작업 중 `develop`의 최신 내용을 가져올 때는 다음 명령어를 사용한다.

```bash
git fetch origin
git merge origin/develop
```

기본적으로 rebase와 force push는 사용하지 않는다.

### 긴급 수정 브랜치 생성

운영 환경의 긴급 수정은 최신 `master`에서 시작한다.

```bash
git switch master
git pull origin master
git switch -c hotfix/S15P11B106-30-login-error
```

## 3. **Commit Message Convention**

### 커밋 메시지 형식 ⭐

```
<타입>(<선택적 범위>): <한국어 설명>
```

예시:

```
feat(auth): 사용자 로그인 기능 추가
fix(user): 닉네임 중복 검사 오류 수정
refactor(payment): 결제 검증 로직 분리
docs: API 사용 방법 수정
chore: 의존성 버전 업데이트
```

`auth`, `user`, `payment`처럼 변경 범위가 명확하면 괄호 안에 작성한다.

변경 범위가 명확하지 않거나 프로젝트 전체에 해당하면 생략한다.

```
docs: 프로젝트 실행 방법 수정
chore: 의존성 버전 업데이트
```

### 커밋 작성 규칙

- 타입은 영어 소문자로 작성한다.
- 설명은 한국어로 작성한다.
- 설명 끝에 마침표를 붙이지 않는다.
- 한 커밋에는 하나의 작업 목적만 담는다.
- Jira 이슈 키는 커밋 메시지에 작성하지 않는다.
- `수정`, `변경`, `업데이트`처럼 내용이 불분명한 표현만 사용하지 않는다.

잘못된 예:

```
fix: 버그 수정
chore: 변경
```

좋은 예:

```
fix(user): 탈퇴한 사용자 로그인 오류 수정
chore: Spring Boot 버전 업데이트
```

### 커밋 타입

| 타입 | 설명 | SemVer 영향 | 예시 |
| --- | --- | --- | --- |
| `feat` | 새로운 기능 추가 | MINOR | `feat(auth): 소셜 로그인 기능 추가` |
| `fix` | 버그 수정 | PATCH | `fix(cart): 수량 0 입력 시 오류 수정` |
| `docs` | 문서 변경 (README, 주석 등) | — | `docs: API 명세서 업데이트` |
| `style` | 코드 포맷, 세미콜론 등 (동작 변화 없음) | — | `style: 들여쓰기 통일` |
| `refactor` | 기능 변화 없는 코드 구조 개선 | — | `refactor(user): 서비스 레이어 분리` |
| `test` | 테스트 코드 추가 또는 수정 | — | `test(payment): 결제 실패 케이스 추가` |
| `chore` | 빌드 설정, 패키지 업데이트 등 잡무 | — | `chore: eslint 설정 변경` |
| `ci` | CI/CD 파이프라인 설정 변경 | — | `ci: GitHub Actions 배포 스크립트 수정` |
| `perf` | 성능 개선 | PATCH | `perf(search): 인덱스 쿼리 최적화` |
| `revert` | 이전 커밋 되돌리기 | — | `revert: feat(auth): 소셜 로그인 기능 추가` |

`style`은 화면 디자인이나 CSS 변경을 의미하지 않는다.

```
style: 코드 포맷터 적용
```

화면 디자인이나 UI 기능을 변경한 경우에는 작업 목적에 따라 `feat` 또는 `fix`를 사용한다.

```
feat(ui): 프로필 화면 디자인 변경
fix(ui): 모바일 화면 버튼 겹침 수정
```

## 4. Pull Request Convention ⭐

### PR 제목

```
<타입>(<선택적 범위>): <한국어 설명> [Jira 이슈 키]
```

예시:

```
feat(auth): 사용자 로그인 기능 추가 [S15P11B106-12]
fix(user): 닉네임 중복 검사 오류 수정 [S15P11B106-15]
docs: API 문서 수정 [S15P11B106-20]
```

PR 제목은 Squash merge 후 `master` 또는 `develop`에 남는 최종 커밋 메시지가 된다.

따라서 PR 전체 내용을 대표할 수 있도록 작성한다.

### PR 본문 템플릿(예시) ⭐

```markdown
## 📋 관련 이슈
- JIRA: PROJ-111

## 📝 작업 내용
- 닉네임 중복 체크 API 엔드포인트 추가
- 중복 시 사용자에게 안내 메시지 반환

## 🔍 변경 사항
- `UserService.checkNicknameDuplicate()` 메서드 추가
- `UserController`에 GET `/api/users/check-nickname` 엔드포인트 추가

## ✅ 테스트
- [ ] 단위 테스트 통과
- [ ] 통합 테스트 통과
- [ ] 로컬 환경 동작 확인

## 📸 스크린샷 (선택)
- (자료가 없다면, 없음이라고 적고 넘어가기)

## 💬 리뷰어 참고 사항
- 특별히 확인 요청 사항이 있다면 기재
```

- PR 본문은 한국어로 작성한다.
- PR 당 **하나의 기능 또는 수정 사항**만 포함한다.
- 비밀번호, API 키, 토큰, 개인정보 등 민감한 정보는 첨부하지 않는다.
- 작업이 완료되지 않았다면 Draft PR로 생성할 수 있다.

## 5. 코드 리뷰와 병합

### 리뷰 의견 작성

필요에 따라 다음 접두사를 사용한다.

```
must:
병합 전에 반드시 수정해야 하는 내용

suggestion:
작성자가 판단해서 반영할 수 있는 제안

question:
코드의 의도나 동작을 확인하는 질문
```

예시:

```
must: 사용자 입력값에 대한 서버 측 검증이 필요합니다.
```

```
suggestion: 이 로직을 별도 함수로 분리하면 읽기 쉬울 것 같습니다.
```

```
question: 이 경우 404 응답을 반환하도록 한 이유가 있을까요?
```

### 병합 조건 ⭐

다음 조건을 모두 만족해야 병합할 수 있다.

- PR 작성자 외 최소 1명이 승인해야 한다.
- 모든 `must:` 의견을 해결해야 한다.
- 해결되지 않은 리뷰 대화가 없어야 한다.
- 브랜치 충돌이 없어야 한다.
- 필수 CI 검사가 있다면 모두 통과해야 한다.

CI가 아직 없다면 직접 수행한 테스트 방법과 결과를 PR 본문에 작성한다.

### 병합 방식 ⭐

모든 PR은 Squash merge한다.

여러 개의 작업 커밋은 하나의 커밋으로 합쳐지며, PR 제목이 최종 커밋 메시지가 된다.

병합이 끝나면 작업 브랜치를 삭제한다.

## 6. 호환되지 않는 변경

기존 API, 데이터 구조 또는 사용 방법과 호환되지 않는 변경은 반드시 표시한다.

PR 또는 커밋 제목의 타입 뒤에 `!`를 붙인다.

```
feat(api)!: 로그인 응답 형식 변경
```

본문에는 변경 내용을 구체적으로 작성한다.

```
BREAKING CHANGE: 로그인 응답의 token 필드가 accessToken으로 변경되었습니다.
```

가능하면 다음 내용도 함께 작성한다.

- 무엇이 변경되었는지
- 어떤 기능이 영향을 받는지
- 기존 코드를 어떻게 수정해야 하는지

## 7. 버전 규칙

정식 릴리스를 시작한 이후부터 Semantic Versioning을 적용한다.

| 변경 내용 | 버전 변경 |
| --- | --- |
| 새로운 기능 추가 | MINOR |
| 버그 수정 | PATCH |
| 성능 개선 | PATCH |
| 호환되지 않는 변경 | MAJOR |

예시:

```
1.2.3
│ │ └─ PATCH: 버그 수정 및 성능 개선
│ └─── MINOR: 하위 호환되는 기능 추가
└───── MAJOR: 호환되지 않는 변경
```

프로젝트 초기에는 PR마다 버전을 변경하지 않는다.

`release/v1.0.0`과 같은 릴리스 브랜치를 실제로 운영하기 시작한 시점부터 적용한다.

## 8. 작업 전후 확인

### 작업 시작 전

- Jira 티켓을 생성했는지 확인한다.
- 최신 `develop`에서 브랜치를 생성한다.
- 브랜치 이름이 규칙에 맞는지 확인한다.

### PR 생성 전

- 하나의 작업 목적만 포함했는지 확인한다.
- 디버깅 코드를 제거한다.
- 불필요한 주석을 제거한다.
- 테스트를 수행한다.
- 최신 `develop`을 반영한다.
- Jira 티켓 상태를 업데이트한다.
- 민감정보가 포함되지 않았는지 확인한다.

### 병합 전

- 작성자 외 1명 이상의 승인을 받는다.
- 모든 `must:` 의견을 해결한다.
- 모든 리뷰 대화를 해결한다.
- 충돌이 없는지 확인한다.
- 필수 CI 검사가 통과했는지 확인한다.
