# 최고관리자 전용 부서 및 develop 초기화 설계

## 목적

develop 배포 환경의 기존 데이터와 업로드 파일을 완전히 제거하고, `최고관리자` 부서에 속한 최고관리자 계정 한 명만 생성한다. ERD와 `Role` 열거형은 변경하지 않는다.

## 백엔드 권한 모델 검토

백엔드는 별도의 `SUPER_ADMIN` 역할을 사용하지 않는다. `SuperAdminChecker`가 다음 조건을 모두 만족하는 회원을 최고관리자로 판별한다.

- `role=ADMIN`
- `signup_status=APPROVED`
- `account_status=ACTIVE`
- 회원 이메일이 실행 중인 백엔드의 `SUPER_ADMIN_EMAIL` 설정과 대소문자 구분 없이 일치

소속 부서명과 `department.manager_id`는 최고관리자 판별에 사용하지 않는다. 따라서 최고관리자를 `최고관리자` 부서에 소속시키되 이 부서의 `manager_id`는 비워 둔다. 기존 백엔드에는 최고관리자를 일반 부서장으로 지정하지 못하게 하는 보호 로직과, 로그인 응답·사용자 관리·가입 승인·문의 관리에서 동일한 최고관리자 판별기를 사용하는 테스트가 존재한다.

## 선택한 방식

`scripts/bootstrap-admin.sh`를 영구 수정한다.

1. 최고관리자 소속 부서를 `본사`가 아닌 `최고관리자`로 생성한다.
2. 스크립트 인수로 받은 이메일을 실행 중인 백엔드 컨테이너의 `SUPER_ADMIN_EMAIL`과 비교한다.
3. 값이 없거나 서로 다르면 회원을 생성하기 전에 실패한다.
4. 일치하면 기존처럼 암호학적으로 안전한 랜덤 비밀번호와 BCrypt 해시를 생성한다.
5. 최고관리자 회원을 `ADMIN`, `APPROVED`, `ACTIVE`로 생성한다.
6. 부서의 `manager_id`는 지정하지 않는다.

서버에서 일회성 SQL만 실행하는 방식은 다음 초기화 시 다시 `본사` 부서를 만들 수 있어 사용하지 않는다. ERD에 최고관리자 역할이나 전용 컬럼을 추가하는 방식도 현재 이메일 기반 권한 모델과 중복되므로 사용하지 않는다.

## 테스트

`scripts/tests/bootstrap-admin-test.sh`에 다음 동작을 검증한다.

- 잘못된 이메일은 DB 호출 전에 거절한다.
- 실행 중인 백엔드의 `SUPER_ADMIN_EMAIL`과 다른 이메일은 DB 호출 전에 거절한다.
- 이미 같은 이메일 회원이 존재하면 비밀번호를 새로 만들지 않는다.
- 성공 시 `최고관리자` 부서와 최고관리자 회원을 각각 한 번 생성한다.
- 생성 회원의 상태는 `ADMIN`, `APPROVED`, `ACTIVE`다.

기존 백엔드 최고관리자 테스트도 실행해 권한 판별 회귀가 없는지 확인한다.

## develop 서버 초기화 절차

초기화 대상은 Compose 프로젝트 `ajt-develop`로 한정한다.

1. 현재 컨테이너와 마운트에서 대상 볼륨이 `ajt-develop-mysql-data`, `ajt-develop-files`인지 읽기 전용 명령으로 확인한다.
2. 필요하면 초기화 직전 DB 백업을 생성한다.
3. `ajt-develop` 컨테이너를 중단하고 두 볼륨을 명시적으로 제거한다.
4. 443 운영 프로젝트 `s15p11b106`의 컨테이너와 볼륨은 건드리지 않는다.
5. Jenkins에서 최신 develop SHA 이미지를 빌드하고 수동 승인하여 재배포한다.
6. MySQL healthcheck와 백엔드 healthcheck 통과 후 최고관리자 부트스트랩을 한 번 실행한다.
7. 출력된 초기 비밀번호는 안전한 수단으로 즉시 보관한다.

## 완료 조건

- `department` 테이블에는 `최고관리자` 부서 한 건만 존재한다.
- `member` 테이블에는 설정된 이메일의 최고관리자 한 명만 존재한다.
- 최고관리자의 부서명이 `최고관리자`이고 해당 부서의 `manager_id`는 `NULL`이다.
- 로그인 응답의 `isSuperAdmin`이 `true`다.
- 가입 승인 및 관리자 전용 기능에 접근할 수 있다.
- 기존 문서 DB 기록과 실제 업로드 파일이 모두 제거되어 있다.
